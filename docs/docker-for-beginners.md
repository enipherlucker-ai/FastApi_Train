# Создание своего docker и docker.yml для чайников 😄

Цель: научиться самостоятельно писать **Dockerfile** и **Compose-файл**, понимать каждую строку и находить ошибки по логам.

Урок построен на этом репозитории: приложение лежит в `app/main.py`, зависимости — в `requirements.txt`. Нужны базовые знания Python и терминала. Пройди материал в три подхода: объяснения → запуск → самостоятельные задания. Не переписывай пример вслепую: сначала попробуй составить свой вариант.

## 1. Что именно мы создаём

«Написать докер» обычно означает подготовить два файла:

| Объект | Назначение | Аналогия |
|---|---|---|
| Dockerfile | Инструкции сборки образа | Рецепт |
| Образ (image) | Подготовленные файлы приложения, зависимости и настройки запуска | Заготовка по рецепту |
| Контейнер (container) | Запущенный экземпляр образа со своим процессом и окружением | Приготовленная порция |
| Compose-файл | Описание запуска сервисов: образы, порты, настройки, хранилища | План всей кухни |

Один образ можно использовать для нескольких контейнеров. Перезапуск контейнера не собирает новый образ.

Контейнер — не полноценная виртуальная машина: Linux-контейнеры используют ядро Linux-хоста. На Windows Docker Desktop предоставляет для них Linux-окружение. Внутри нашего образа будет Python для Linux, поэтому локальную Windows-папку `.venv` туда не переносим.

**Dockerfile отвечает: как собрать окружение? Compose отвечает: как его запустить?**

### Почему не вставлять код вручную на сервере

Обычный рабочий процесс: правишь файлы локально → сохраняешь в Git → собираешь образ → запускаешь его на нужной машине. Собирать можно локально, на сервере после получения репозитория или в CI. Готовые образы часто передают через registry — хранилище образов.

Docker не требует сначала вручную разворачивать Python-приложение на Ubuntu. Достаточно разобраться, какая команда его запускает: эту команду затем перенесёшь в контейнер.

## 2. Начни с вопросов, а не с Dockerfile

Перед сборкой любого приложения запиши:

1. Какой язык и версия среды нужны?
2. Где список зависимостей?
3. Какие файлы нужны для работы?
4. Из какой папки выполнять запуск?
5. Какая команда запускает приложение?
6. Какой порт слушает приложение?
7. Какие настройки и постоянные данные ему нужны?

Для нашего проекта:

| Вопрос | Ответ |
|---|---|
| Среда | Python; для учебного примера используем 3.12 |
| Зависимости | `requirements.txt` |
| Код | Папка `app/` |
| Рабочая папка внутри контейнера | `/code` — выбираем сами |
| Команда | `python -m uvicorn app.main:app --host 0.0.0.0 --port 8000` |
| Порт | 8000 внутри контейнера |
| Хранение | Сейчас список в памяти; базы данных нет |

`app.main:app` означает: импортировать модуль `app.main` и взять из него объект `app = FastAPI()`. Это не путь `app/main.py:app`.

**FastAPI описывает API. Uvicorn принимает HTTP-запросы и запускает это ASGI-приложение.**

## 3. Подготовь инструменты

Нужны Docker Engine и Docker Compose. На Windows можно использовать Docker Desktop с Linux-контейнерами. Установку для своей ОС смотри в [официальной инструкции](https://docs.docker.com/get-started/get-docker/).

Проверь в терминале:

```sh
docker version
docker compose version
```

В `docker version` должны быть доступны клиент и сервер. Ошибка подключения к daemon обычно означает, что Docker Engine не запущен или недоступен.

Дальше выполняй команды **из корня репозитория**, где находится `requirements.txt`. Примеры команд помещаются в одну строку и подходят для PowerShell и Linux shell.

### Добавь сервер в зависимости

В текущем `requirements.txt` есть FastAPI и Pydantic, но нет Uvicorn. Для выполнения урока добавь строку:

```text
uvicorn
```

Это учебный вариант без фиксации версии. Для рабочего проекта версии и транзитивные зависимости фиксируют согласно принятому в команде процессу. Не придумывай номера версий: используй реально доступные и совместимые, затем проверяй установку.

## 4. Переводим обычные действия в Dockerfile

Если бы ты готовил новое окружение вручную, то установил бы Python, выбрал папку, установил зависимости, положил код и запустил сервер.

| Обычное действие | Инструкция |
|---|---|
| Взять окружение с Python | `FROM` |
| Выбрать текущую папку | `WORKDIR` |
| Перенести файлы в образ | `COPY` |
| Выполнить команду при сборке | `RUN` |
| Задать переменную окружения | `ENV` |
| Указать порт приложения | `EXPOSE` |
| Задать команду запуска | `CMD` |

Создай **`Dockerfile` без расширения** в корне проекта:

```dockerfile
FROM python:3.12-slim

WORKDIR /code

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

COPY requirements.txt ./
RUN python -m pip install --no-cache-dir -r requirements.txt

COPY app/ ./app/

EXPOSE 8000

CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

### Разбираем решения

**FROM.** Берём готовый образ Python. `3.12` — выбранная версия, `slim` — уменьшенный вариант базового окружения. Тег может обновляться; для строгой повторяемости используют digest и управляемое обновление зависимостей.

**WORKDIR.** Создаёт рабочую директорию, если её нет, и задаёт её для дальнейших инструкций. Поэтому `./app/` внутри образа станет `/code/app/`.

**ENV.** Первая настройка отключает создание файлов bytecode `.pyc`; вторая помогает сразу видеть Python-вывод в логах. Эти настройки удобны, но не являются обязательными условиями работы Docker.

**COPY.** Источник берётся из контекста сборки, назначение — внутри образа. Сначала переносим зависимости, затем код.

**RUN.** Устанавливаем пакеты при сборке. `python -m pip` использует pip выбранного Python. `--no-cache-dir` отключает кэш pip; это не отключение кэша сборки Docker.

**EXPOSE.** Документирует порт. Сам по себе не делает API доступным на твоём компьютере.

**CMD.** Запускает сервер при старте контейнера. Используем список аргументов: каждый элемент — отдельный аргумент команды.

**0.0.0.0.** Сервер слушает все сетевые интерфейсы внутри контейнера. Если слушать только `127.0.0.1` внутри него, обычный проброс порта не обеспечит доступ с хоста.

### RUN и CMD — главное различие

```dockerfile
RUN python -m pip install -r requirements.txt
CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0"]
```

Установка нужна **при сборке**. Работающий сервер нужен **при запуске**.

Если поместить сервер в `RUN`, сборка будет ждать завершения сервера. Если устанавливать зависимости в `CMD`, каждый старт начнёт зависеть от повторной установки.

Для первого проекта хватит `CMD`. Позже изучи `ENTRYPOINT`: он задаёт основной исполняемый процесс, а `CMD` может задавать его аргументы по умолчанию.

### Почему порядок COPY важен

Если зависимости не изменились, Docker часто может использовать результат предыдущего шага установки. Изменение кода после этого шага не требует заново устанавливать пакеты.

Вариант `COPY . .` перед установкой зависимостей проще написать, но изменение любого скопированного файла может сбросить кэш установки. Кэш зависит также от базового образа и предыдущих инструкций.

## 5. Контекст сборки и .dockerignore

В команде:

```sh
docker build -t fastapi-train:local .
```

точка — **контекст сборки**, здесь текущая папка. Она не обозначает контейнер и не является именем Dockerfile.

`COPY app/ ./app/` ищет исходную папку `app/` в контексте. Обычный `COPY` не позволяет брать произвольные файлы за его пределами.

Создай `.dockerignore` в корне:

```text
.git
.venv
venv
__pycache__
*.pyc
.pytest_cache
.env
.env.*
```

Это исключения для контекста сборки. `.gitignore` управляет Git и не заменяет `.dockerignore`. В нашем примере код копируется явно, но исключения пригодятся при развитии Dockerfile.

Секреты не копируй в образ. Удаление секретного файла поздней инструкцией не гарантирует его удаления из предыдущих слоёв.

## 6. Сначала запуск без Compose

Собери образ:

```sh
docker build -t fastapi-train:local .
```

`-t` задаёт имя и тег. Успешная сборка означает, что инструкции сборки выполнились; работоспособность HTTP API нужно проверить отдельно.

Запусти:

```sh
docker run --rm --name fastapi-train -p 127.0.0.1:8000:8000 fastapi-train:local
```

| Часть | Значение |
|---|---|
| `--rm` | Удалить контейнер после его остановки |
| `--name` | Дать контейнеру удобное имя |
| `127.0.0.1:8000:8000` | IP хоста : порт хоста : порт контейнера |
| `fastapi-train:local` | Образ для запуска |

Адрес хоста `127.0.0.1` ограничивает доступ твоим компьютером. Это отдельный адрес от `0.0.0.0`, на котором слушает процесс внутри контейнера.

Открой [Swagger UI](http://localhost:8000/docs). Через **Try it out** создай пользователя и проверь получение, изменение и удаление.

В текущем API параметры создания передаются в query string: обычные аргументы функции `name`, `age`, `description` не образуют JSON-тело автоматически.

Останови запуск сочетанием Ctrl+C. В другом терминале можно выполнить:

```sh
docker stop fastapi-train
```

## 7. Теперь пишем Compose-файл

Compose удобен даже для одного сервиса: вместо длинной команды сохраняешь настройки запуска в репозитории.

Создай `compose.yaml`:

```yaml
services:
  api:
    build:
      context: .
      dockerfile: Dockerfile
    image: fastapi-train:local
    ports:
      - "127.0.0.1:8000:8000"
```

### Почему не docker.yml?

Предпочтительное имя — `compose.yaml`; поддерживаются также `compose.yml`, `docker-compose.yaml` и `docker-compose.yml`.

Назвать файл `docker.yml` тоже можно, но тогда указывай его явно:

```sh
docker compose -f docker.yml up --build
```

Для урока используем `compose.yaml`, чтобы не передавать имя каждый раз. Поле `version:` для современного Compose добавлять не нужно.

### Как прочитать YAML

`services` содержит сервисы. `api` — придуманное нами имя сервиса. Вложенные поля относятся к нему.

- `build.context`: откуда брать файлы для сборки.
- `build.dockerfile`: какой Dockerfile использовать; здесь запись явная, хотя это стандартное имя.
- `image`: имя собираемого образа.
- `ports`: публикация портов.

Отступы показывают вложенность. Используй пробелы, а не табуляцию. Два пробела — удобная договорённость. Дефис обозначает элемент списка. Строки с портами заключай в кавычки.

### Сопоставление запуска

| docker run | Compose |
|---|---|
| Имя образа | `image` |
| `-p` | `ports` |
| `-e NAME=value` | `environment` |
| `-v` / `--mount` | `volumes` |
| Команда после имени образа | `command`, переопределяет CMD |

Не добавляй все возможные поля заранее: каждое должно решать конкретную задачу.

### Проверяем и запускаем

```sh
docker compose config
docker compose up --build
```

Первая команда проверяет и выводит итоговую конфигурацию. Она не проверяет Python-код и не гарантирует успешный запуск.

Перед Compose останови предыдущий контейнер: два процесса не могут одновременно занять один и тот же порт хоста.

Фоновый запуск:

```sh
docker compose up -d --build
docker compose ps
docker compose logs -f api
```

Остановка и удаление контейнеров проекта:

```sh
docker compose down
```

### Когда требуется пересборка

| Что изменилось | Что делать в нашем примере |
|---|---|
| Python-код, скопированный через COPY | `docker compose up -d --build` |
| requirements.txt или Dockerfile | `docker compose up -d --build` |
| ports или environment в Compose | `docker compose up -d` для применения настроек |
| Ничего, нужен только перезапуск | `docker compose restart api` |

`restart` не пересобирает образ и не применяет изменённую конфигурацию Compose.

## 8. Режим разработки: код с компьютера

При разработке можно подключить папку к контейнеру, чтобы не пересобирать образ после каждой правки.

Для эксперимента добавь в сервис `api`:

```yaml
    volumes:
      - ./app:/code/app
    command: ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--reload"]
```

Здесь **bind mount** подключает локальную папку `app` по пути `/code/app`. Её содержимое перекрывает код из образа в этом месте. Uvicorn следит за изменениями благодаря `--reload`.

Зависимости остаются установленными в образе: после изменения `requirements.txt` всё ещё нужна пересборка. На отдельных системах отслеживание файлов требует дополнительной настройки.

Для запуска готового приложения обычно убирают bind mount к исходникам и `--reload`: код доставляется в образе.

## 9. Где данные и почему пользователи исчезают

В приложении:

```python
fake_user_database = []
```

Это оперативная память Python-процесса. При перезапуске процесса список пропадает. **Volume не превращает список в базу данных и не сохраняет RAM.**

| Механизм | Что сохраняет |
|---|---|
| Список Python | Данные только пока живёт процесс |
| Файлы в записываемом слое контейнера | До удаления этого контейнера |
| Bind mount | Файлы в подключённой папке хоста |
| Named volume | Файлы в отдельном хранилище Docker |

Чтобы сохранять пользователей, нужно изменить приложение: например, записывать данные в PostgreSQL или файл. Подключение пустого volume к текущему приложению ничего не изменит.

Не выполняй `docker compose down -v` без понимания: флаг `-v` удаляет связанные управляемые тома проекта и может уничтожить данные.

### Когда появится второй сервис

Если добавишь PostgreSQL как сервис `db`, API обычно подключается к `db:5432` в общей Compose-сети. Внутри API-контейнера `localhost` означает этот API-контейнер, а не соседний PostgreSQL и не компьютер.

Обычный `depends_on` задаёт порядок запуска, но сам по себе не гарантирует готовность БД принимать запросы. Для этого изучи healthcheck, условие `service_healthy` и повторные попытки подключения в приложении.

Переменные `environment` только передают значения процессу. Приложение должно действительно читать их; произвольный `APP_PORT` не изменит порт Uvicorn без соответствующей команды или кода.

## 10. Учимся диагностировать, а не перебирать строки

Сначала определи этап: **сборка → старт процесса → доступ по сети → поведение API**.

| Симптом | Что проверить |
|---|---|
| Cannot connect to Docker daemon | Запущен ли Docker Engine |
| COPY: файл не найден | Текущую папку, build context, путь, .dockerignore |
| No matching distribution found | Версии пакетов, версию Python, источник пакетов |
| No module named uvicorn | Есть ли Uvicorn в зависимостях; пересобран ли образ |
| Could not import module app.main | WORKDIR, COPY и фактический путь к модулю |
| Port is already allocated | Кто занял порт хоста; попробуй хостовый 8080 |
| Контейнер сразу завершился | Логи и команду запуска |
| Контейнер работает, браузер не подключается | ports, адрес прослушивания, адрес браузера |
| Правки не видны | Пересборку или bind mount; restart недостаточно |
| HTTP 500 | Traceback приложения; это не обязательно ошибка Docker |

Полезные команды:

```sh
docker compose ps -a
docker compose logs --tail 100 api
docker compose exec api sh
docker compose exec api python -m pip show uvicorn
```

`exec` работает с запущенным контейнером. Если он сразу падает, сначала прочитай логи; для отдельной диагностики можно запустить:

```sh
docker compose run --rm --no-deps api sh
```

Это отдельный временный контейнер. Его ручные изменения не становятся исправлением Dockerfile.

## 13. Как пользоваться документацией самостоятельно

Не нужно помнить весь синтаксис. Нужно уметь сформулировать задачу и найти нужную инструкцию.

| Хочешь сделать | Что искать |
|---|---|
| Перенести файл | Dockerfile COPY |
| Выполнить действие при сборке | Dockerfile RUN |
| Задать запуск | Dockerfile CMD |
| Изменить порты | Compose services ports |
| Подключить файлы | Compose services volumes |
| Передать настройку | Compose services environment |
| Проверить параметры команды | `docker compose up --help` |
