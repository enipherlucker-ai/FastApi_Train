# Создание своего docker и docker.yml для чайников 😄

**Цель урока:** после него ты пишешь `Dockerfile` и `compose.yaml` для Python-приложения **с пустого файла**, без копирования шаблона, и можешь объяснить каждую строку.

Урок построен на этом репозитории: приложение — `app/main.py`, зависимости — `requirements.txt`. Все команды выполняются **из корня репозитория** (там, где лежит `requirements.txt`) и одинаково работают в PowerShell и в Linux shell.

## 0. Как проходить урок

Чтобы научиться писать самому, а не узнавать чужой код, соблюдай четыре правила:

1. **Печатай руками.** Не копируй блоки кода из урока в файлы. Опечатки и ошибки — часть обучения.
2. **Одна инструкция — одна проверка.** Dockerfile собирается по шагам; после каждого шага ты собираешь образ и проверяешь, что внутри появилось именно то, что ожидал.
3. **Сначала предскажи — потом запусти.** Перед каждой командой скажи себе, что должно произойти. Расхождение с реальностью — самое ценное место урока.
4. **Ответы — в свёрнутых блоках.** Открывай их только после своей попытки.

План: понять модель (разделы 1–2) → сделать всё руками внутри контейнера (3–4) → превратить эти действия в Dockerfile по шагам (5) → выучить правила, на которых все ошибаются (6) → Compose (7–9) → диагностика (10) → тренировка с нарастающей сложностью (11) → повторение по памяти (12).

## 1. Что именно мы создаём

| Объект | Что это | Аналогия |
|---|---|---|
| Dockerfile | Инструкции сборки образа | Рецепт |
| Образ (image) | Неизменяемый результат сборки: ОС-окружение, Python, зависимости, код, команда запуска | Заготовка по рецепту |
| Контейнер (container) | Запущенный экземпляр образа со своим процессом | Приготовленная порция |
| Compose-файл | Описание того, как запускать один или несколько контейнеров | План всей кухни |

**Dockerfile отвечает на вопрос «как собрать окружение?». Compose отвечает на вопрос «как его запустить?».**

Ещё три факта, которые понадобятся дальше:

- Из одного образа можно запустить сколько угодно контейнеров. Перезапуск контейнера **не пересобирает** образ.
- Контейнер — не виртуальная машина: Linux-контейнер использует ядро Linux. На Windows Docker Desktop даёт для этого Linux-окружение (WSL 2). Поэтому внутри образа будет Python для Linux, и твоя Windows-папка `.venv` туда не нужна.
- Контейнер живёт, пока живёт его **главный процесс** (у нас — Uvicorn). Процесс завершился → контейнер остановился.

### Как это выглядит в реальной работе

Правишь код локально → коммитишь в Git → образ собирается (локально, на сервере или в CI) → готовый образ запускается на нужной машине. Код на сервер руками не копируют и Python на сервере руками не настраивают: всё окружение описано в Dockerfile и лежит в репозитории рядом с кодом.

## 2. Алгоритм: семь вопросов перед любым Dockerfile

Dockerfile не пишут «сверху вниз по памяти». Его пишут, **ответив на вопросы о приложении**. Запомни эти семь вопросов — это и есть навык:

1. Какая среда и какая версия нужны? → `FROM`
2. Где список зависимостей и как их установить? → `COPY` + `RUN`
3. Какие файлы нужны для работы? → `COPY`
4. Из какой папки запускать? → `WORKDIR`
5. Какая команда запускает приложение? → `CMD`
6. Какой порт слушает приложение? → `--host/--port` в команде, `EXPOSE`, `ports` в Compose
7. Какие настройки и постоянные данные нужны? → `environment`, `volumes` в Compose

Ответы для нашего проекта:

| Вопрос | Ответ |
|---|---|
| Среда | Python 3.12 |
| Зависимости | `requirements.txt`, установка через `python -m pip install -r requirements.txt` |
| Файлы | Папка `app/` |
| Рабочая папка в контейнере | `/code` — имя выбираем сами |
| Команда запуска | `python -m uvicorn app.main:app --host 0.0.0.0 --port 8000` |
| Порт | 8000 внутри контейнера |
| Настройки и данные | Пока нет: пользователи хранятся в списке в памяти |

Две вещи в команде запуска, которые нужно понимать, а не заучивать:

- `app.main:app` — это **имя модуля Python**, а не путь к файлу: «импортируй модуль `app.main` и возьми из него объект `app`». Импорт сработает, только если текущая папка — та, в которой лежит папка `app/`. Это напрямую определит `WORKDIR` и `COPY`.
- `--host 0.0.0.0` — слушать все сетевые интерфейсы контейнера. По умолчанию Uvicorn слушает `127.0.0.1`, то есть только «изнутри самого контейнера», и снаружи к нему не достучаться.

> **Проверь себя.** Почему команда `python -m uvicorn app/main.py:app` не сработает?
>
> <details><summary>Ответ</summary>Uvicorn ожидает имя модуля через точку (`app.main`), а не путь к файлу. Строку `app/main.py` он попытается импортировать как модуль и выдаст ошибку импорта.</details>

## 3. Подготовь инструменты

Нужны Docker Engine и Docker Compose. На Windows — Docker Desktop с Linux-контейнерами. Инструкция по установке: [Get Docker](https://docs.docker.com/get-started/get-docker/).

```sh
docker version
docker compose version
```

**Ожидаемый результат:** в выводе `docker version` есть **оба** блока — `Client` и `Server`.

Если есть только `Client`, а дальше ошибка вида `failed to connect to the docker API` / `Cannot connect to the Docker daemon` — клиент установлен, но движок недоступен. На Windows проверь по порядку:

1. Docker Desktop запущен и в нём написано, что Engine running.
2. Docker Desktop работает в режиме Linux containers (меню иконки в трее: если там пункт «Switch to Linux containers…», нажми его).
3. WSL 2 установлен: `wsl --status` в PowerShell.

Дальше в уроке ничего не заработает без работающего `Server`, поэтому добейся этого первым.

**Зависимости.** Открой `requirements.txt` и убедись, что там есть `uvicorn` — без него запускать FastAPI нечем. Если строки нет, добавь её.

## 4. Шаг ноль: сделай всё руками внутри пустого контейнера

Это главный приём для написания Dockerfile с нуля. **Dockerfile — это записанная история команд, которые ты бы выполнил руками в чистой Linux-системе с Python.** Поэтому сначала выполним их руками.

Запусти чистый контейнер с Python и подключи к нему папку проекта:

```sh
docker run -it --rm -p 127.0.0.1:8000:8000 -v "${PWD}:/src" python:3.12-slim bash
```

| Часть | Смысл |
|---|---|
| `-it` | Интерактивный терминал: ты окажешься внутри контейнера |
| `--rm` | Удалить контейнер после выхода |
| `-p 127.0.0.1:8000:8000` | Пробросить порт 8000 компьютера на порт 8000 контейнера |
| `-v "${PWD}:/src"` | Показать текущую папку проекта внутри контейнера как `/src` |
| `python:3.12-slim` | Базовый образ: Debian + Python 3.12 |
| `bash` | Команда вместо стандартной: открыть shell |

Приглашение терминала сменится на что-то вроде `root@3f2a1b...:/#`. Ты в Linux. Выполни по одной команде и смотри на результат:

```sh
python --version
ls /src
mkdir -p /code
cd /code
cp /src/requirements.txt .
python -m pip install -r requirements.txt
cp -r /src/app ./app
ls
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Предупреждение pip о запуске от root внутри контейнера здесь ожидаемо — продолжай.

**Ожидаемый результат:** в логе строка `Uvicorn running on http://0.0.0.0:8000`. Открой [http://localhost:8000/docs](http://localhost:8000/docs) — это Swagger твоего API.

Теперь останови сервер (Ctrl+C) и выйди: `exit`. Запусти ту же команду `docker run ...` ещё раз и выполни `ls /code`.

> **Предскажи до запуска:** что окажется в `/code`?
>
> <details><summary>Ответ</summary>Папки `/code` нет. Контейнер был удалён (`--rm`), а новый запущен из исходного образа `python:3.12-slim`, в котором нет ни твоих пакетов, ни кода. Всё, что делается в контейнере руками, пропадает. Чтобы получать готовое окружение каждый раз, действия нужно записать в рецепт — Dockerfile.</details>

Выйди (`exit`). Запиши на бумаге или в заметке список своих ручных действий — **следующий раздел превращает каждое из них в инструкцию**:

| Ручное действие | Инструкция Dockerfile |
|---|---|
| Взять систему с Python 3.12 | `FROM python:3.12-slim` |
| `mkdir -p /code` + `cd /code` | `WORKDIR /code` |
| `cp /src/requirements.txt .` | `COPY requirements.txt ./` |
| `python -m pip install -r requirements.txt` | `RUN python -m pip install ...` |
| `cp -r /src/app ./app` | `COPY app/ ./app/` |
| `python -m uvicorn ...` | `CMD [...]` |

Разница одна: `cp` копирует из подключённой папки `/src`, а `COPY` — из **контекста сборки** (папки, которую ты передаёшь в `docker build`; о ней в разделе 6).

## 5. Собираем Dockerfile по одной инструкции

Создай в корне проекта файл **`Dockerfile`** — именно так, с большой буквы и **без расширения** (не `Dockerfile.txt`: проверь, что Windows не дописал расширение).

На каждом шаге цикл одинаковый: **дописал → собрал → проверил содержимое образа**.

Ключевой приём проверки: **команда после имени образа в `docker run` заменяет `CMD`**. Так можно заглянуть внутрь любого образа:

```sh
docker run --rm fastapi-train:local pwd
docker run --rm fastapi-train:local ls -la
```

### Шаг 1. Базовое окружение — `FROM`

```dockerfile
FROM python:3.12-slim
```

`FROM` всегда первая инструкция: она говорит, на каком готовом образе строим свой. `3.12` — версия Python, `slim` — облегчённый вариант Debian без лишних пакетов.

Собери и проверь:

```sh
docker build -t fastapi-train:local .
docker run --rm fastapi-train:local python --version
```

**Ожидаемо:** `Python 3.12.x`.

- `-t fastapi-train:local` — имя (`fastapi-train`) и тег (`local`) образа.
- `.` в конце — контекст сборки (текущая папка). Его нельзя забывать.

> Запусти `docker run --rm -it fastapi-train:local` без команды. Что открылось и почему?
>
> <details><summary>Ответ</summary>Интерактивный Python (`>>>`). Своего `CMD` у нас пока нет, поэтому используется `CMD` базового образа `python:3.12-slim` — он запускает `python3`. Выход: `exit()`.</details>

### Шаг 2. Рабочая папка и зависимости — `WORKDIR`, `COPY`, `RUN`

Допиши:

```dockerfile
WORKDIR /code

COPY requirements.txt ./
RUN python -m pip install --no-cache-dir -r requirements.txt
```

- `WORKDIR /code` — создаёт папку, если её нет, и делает её текущей для **всех следующих инструкций** и для запущенного контейнера. Это `mkdir -p` + `cd` в одной инструкции. Пиши `WORKDIR`, а не `RUN cd /code`: эффект `cd` в `RUN` не переживает конец этой строки.
- `COPY requirements.txt ./` — слева путь **в контексте сборки**, справа путь **в образе**. `./` — относительно `WORKDIR`, то есть `/code/`.
- `RUN` выполняет команду **во время сборки**; результат (установленные пакеты) сохраняется в образе.
- `python -m pip` гарантирует, что используется pip именно этого Python. `--no-cache-dir` не сохраняет скачанные архивы pip в образе — образ получается меньше.

Собери и проверь:

```sh
docker build -t fastapi-train:local .
docker run --rm fastapi-train:local pwd
docker run --rm fastapi-train:local ls
docker run --rm fastapi-train:local python -m pip show uvicorn
```

**Ожидаемо:** `/code`; в списке файлов только `requirements.txt`; `pip show` выводит `Name: uvicorn` и версию.

### Шаг 3. Код — второй `COPY`

```dockerfile
COPY app/ ./app/
```

Почему зависимости и код копируются **отдельно и в таком порядке** — разберём в разделе 6 (кэш). Пока просто проверь результат:

```sh
docker build -t fastapi-train:local .
docker run --rm fastapi-train:local ls app
docker run --rm fastapi-train:local python -c "import app.main; print('import ok')"
```

**Ожидаемо:** `main.py` и `import ok`. Если импорт не прошёл — значит, файл оказался не там, где ты думаешь. Это самая частая ошибка, и вторая команда ловит её до запуска сервера.

### Шаг 4. Команда запуска — `CMD`

```dockerfile
CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

`CMD` **не выполняется при сборке**. Он записывается в образ как команда по умолчанию и выполняется **при каждом старте контейнера**. Каждый аргумент — отдельный элемент списка в **двойных** кавычках (это JSON).

```sh
docker build -t fastapi-train:local .
docker run --rm --name fastapi-train -p 127.0.0.1:8000:8000 fastapi-train:local
```

**Ожидаемо:** `Uvicorn running on http://0.0.0.0:8000`. Открой [Swagger](http://localhost:8000/docs), через **Try it out** создай пользователя, получи его, измени, удали. (Параметры в этом API передаются в query string, а не JSON-телом: так устроены функции в `main.py`, Docker тут ни при чём.)

Остановить: Ctrl+C или из другого терминала `docker stop fastapi-train`.

| Часть `docker run` | Значение |
|---|---|
| `--rm` | Удалить контейнер после остановки |
| `--name fastapi-train` | Имя, чтобы обращаться к контейнеру в `docker stop`, `docker logs` |
| `-p 127.0.0.1:8000:8000` | `IP хоста : порт хоста : порт контейнера` |
| `fastapi-train:local` | Какой образ запускать |

`127.0.0.1` в `-p` — адрес **на твоём компьютере**: API доступен только с него, а не со всей сети. `0.0.0.0` в `CMD` — адрес **внутри контейнера**. Это два разных места.

**Минимальный рабочий Dockerfile готов.** Обязательный скелет для Python-сервиса — пять инструкций: `FROM`, `WORKDIR`, `COPY`, `RUN`, `CMD`. Всё остальное — улучшения.

### Шаг 5. Улучшения — `ENV`, `EXPOSE`, `.dockerignore`

Добавляй их только понимая, какую задачу они решают:

```dockerfile
ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1
```

- `PYTHONDONTWRITEBYTECODE=1` — Python не создаёт файлы `.pyc` в контейнере.
- `PYTHONUNBUFFERED=1` — вывод `print()` сразу попадает в логи, а не копится в буфере. Без него логи могут появляться с задержкой.

Ставь их после `FROM`, перед `RUN` — тогда они действуют на всё, что ниже.

```dockerfile
EXPOSE 8000
```

`EXPOSE` — **только документация**: «приложение внутри слушает 8000». Порт он не открывает. Без `-p` / `ports` API снаружи недоступен, с ними — доступен и без `EXPOSE`.

Создай файл **`.dockerignore`** в корне:

```text
.git
.idea
.venv
venv
__pycache__
*.pyc
.pytest_cache
.env
.env.*
```

Он исключает файлы из **контекста сборки**: они не передаются в Docker и не попадут в образ даже через `COPY . .`. `.gitignore` для Docker ничего не значит — это отдельный файл.

### Итоговый Dockerfile

Сверь со своим. Комментарии — это то, что ты должен уметь сказать про каждую строку:

```dockerfile
# 1. Готовое окружение: Debian + Python 3.12
FROM python:3.12-slim

# 4. Рабочая папка: создать и перейти; дальше все пути относительно /code
WORKDIR /code

# Удобства Python в контейнере: без .pyc, логи без буфера
ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

# 2. Сначала только зависимости — чтобы кэш установки не сбрасывался при правке кода
COPY requirements.txt ./
RUN python -m pip install --no-cache-dir -r requirements.txt

# 3. Потом код
COPY app/ ./app/

# 6. Документация: приложение слушает 8000
EXPOSE 8000

# 5. Команда при старте контейнера (не при сборке)
CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

## 6. Правила, на которых ошибаются при написании с нуля

### Сборка против запуска: `RUN` и `CMD`

| | `RUN` | `CMD` |
|---|---|---|
| Когда выполняется | При `docker build` | При каждом старте контейнера |
| Сколько штук | Сколько угодно | Действует только последний |
| Результат | Сохраняется в образ | Работающий процесс |
| Пример | Установка пакетов | Запуск сервера |

Если поставить сервер в `RUN`, сборка зависнет: она будет ждать окончания команды, а сервер не заканчивается. Если поставить установку пакетов в `CMD`, каждый старт будет заново ставить пакеты — медленно и зависит от интернета.

### Форма записи `CMD`

```dockerfile
CMD ["python", "-m", "uvicorn", "app.main:app"]   # exec-форма — используй её
CMD python -m uvicorn app.main:app                 # shell-форма
```

В shell-форме Docker запускает `/bin/sh -c "..."`, и главным процессом становится `sh`, а не Uvicorn. Сигнал остановки получает `sh`, поэтому `docker stop` часто ждёт 10 секунд и убивает контейнер принудительно. В exec-форме сигнал получает сам Uvicorn и корректно завершается.

Ловушка: `CMD ['python', 'main.py']` с **одинарными** кавычками — не JSON. Docker молча воспримет это как shell-форму, и запуск сломается.

### `COPY`: что куда попадёт

Главное правило: **`COPY` папки копирует её содержимое, а не саму папку.** Пусть `WORKDIR /code`:

| Инструкция | Результат в образе | Импорт `app.main` |
|---|---|---|
| `COPY app/ ./app/` | `/code/app/main.py` | работает |
| `COPY app ./app` | `/code/app/main.py` | работает |
| `COPY app/ ./` | `/code/main.py` — содержимое высыпалось в `/code` | **падает** |
| `COPY app/ .` | то же, `/code/main.py` | **падает** |
| `COPY . .` | весь контекст (минус `.dockerignore`) в `/code` | работает |
| `COPY requirements.txt ./` | `/code/requirements.txt` | — |

Относительный путь справа считается от `WORKDIR`. Если `WORKDIR` не задан, это `/` — корень системы, и файлы разлетятся по корню.

### Контекст сборки

```sh
docker build -t fastapi-train:local .
```

Точка — **контекст сборки**: папка, содержимое которой Docker получает для `COPY`. Это не имя Dockerfile и не контейнер. Следствия:

- `COPY` видит только файлы внутри контекста. `COPY ../secret.txt ./` не сработает.
- Пути в `COPY` считаются от корня контекста, а не от места, где ты стоишь в терминале. Поэтому запускай сборку из корня проекта.
- Секреты (`.env`, ключи) в образ не копируй: любой, у кого есть образ, достанет их. Удаление файла более поздней инструкцией не помогает — он остаётся в предыдущем слое.

### Порядок инструкций и кэш

Образ собирается **слоями**: каждая инструкция — слой. Если инструкция и всё, что выше неё, не изменились, Docker берёт готовый слой из кэша (в выводе сборки — `CACHED`). Как только один слой изменился, **все слои ниже пересобираются**.

```dockerfile
COPY requirements.txt ./        # меняется редко
RUN python -m pip install ...   # долго — хотим кэшировать
COPY app/ ./app/                # меняется постоянно
```

Правка `main.py` пересобирает только последний `COPY` — секунды. Если написать `COPY . .` **перед** `pip install`, любая правка кода сбросит кэш установки, и каждая сборка будет заново качать все пакеты.

**Правило: что меняется реже — выше, что чаще — ниже.**

### Как посмотреть, что получилось

| Хочу узнать | Команда |
|---|---|
| Какие образы есть и их размер | `docker image ls fastapi-train` |
| Какие файлы лежат в образе | `docker run --rm fastapi-train:local ls -la /code` |
| Из каких слоёв состоит образ | `docker history fastapi-train:local` |
| Полный вывод сборки без сокращений | `docker build --progress=plain -t fastapi-train:local .` |
| Собрать без кэша | `docker build --no-cache -t fastapi-train:local .` |
| Зайти в shell собранного образа | `docker run --rm -it fastapi-train:local bash` |

## 7. Compose-файл: переводим команду `docker run`

Compose сохраняет параметры запуска в файл, чтобы не помнить длинную команду. Писать его с нуля проще всего **переводом рабочей команды `docker run`**. Возьми свою команду из шага 4:

```sh
docker build -t fastapi-train:local .
docker run --rm --name fastapi-train -p 127.0.0.1:8000:8000 fastapi-train:local
```

И переведи по частям:

| В команде | В Compose |
|---|---|
| `docker build .` | `build: .` |
| `-t fastapi-train:local` | `image: fastapi-train:local` |
| `-p 127.0.0.1:8000:8000` | `ports: ["127.0.0.1:8000:8000"]` |
| `-e NAME=value` | `environment` |
| `-v ./app:/code/app` | `volumes` |
| Команда после имени образа | `command` (заменяет `CMD`) |
| `--rm`, `--name` | Не нужны: Compose сам именует и управляет контейнерами |

Создай файл **`compose.yaml`** в корне:

```yaml
services:
  api:
    build: .
    image: fastapi-train:local
    ports:
      - "127.0.0.1:8000:8000"
```

### Как читать YAML

- `services` — список сервисов (контейнеров). `api` — имя сервиса, придумываешь сам. Им ты будешь пользоваться в командах (`docker compose logs api`), а другие сервисы — как именем хоста в сети.
- `build: .` — собрать образ из Dockerfile в текущей папке (контекст `.`). Полная форма, если Dockerfile называется иначе:

  ```yaml
      build:
        context: .
        dockerfile: Dockerfile
  ```

- `image` вместе с `build` — **какое имя дать** собранному образу.
- `ports` — список; дефис — элемент списка. Порты пиши в кавычках: YAML может прочитать запись вида `56:56` как число в шестидесятеричной системе.
- Вложенность задаётся **отступами пробелами** (табуляция — ошибка). Принято два пробела.
- Поле `version:` в начале файла устарело — не пиши его.

### Почему не `docker.yml`?

Compose сам находит файлы с именами `compose.yaml` (предпочтительное), `compose.yml`, `docker-compose.yaml`, `docker-compose.yml`. Файл можно назвать и `docker.yml`, но тогда в каждой команде придётся указывать его явно:

```sh
docker compose -f docker.yml up --build
```

Поэтому используем `compose.yaml`.

## 8. Команды Compose и когда пересобирать

Сначала останови контейнер из шага 4 — один порт компьютера не могут занять два процесса.

```sh
docker compose config
docker compose up --build
```

`config` проверяет синтаксис и показывает итоговую конфигурацию — удобно ловить ошибки отступов. Python-код он не проверяет.

| Задача | Команда |
|---|---|
| Собрать и запустить в фоне | `docker compose up -d --build` |
| Статус контейнеров | `docker compose ps` |
| Логи с продолжением | `docker compose logs -f api` |
| Остановить и удалить контейнеры | `docker compose down` |

Когда что нужно:

| Что изменилось | Что делать |
|---|---|
| Код в `app/` (скопирован через `COPY`) | `docker compose up -d --build` |
| `requirements.txt` или `Dockerfile` | `docker compose up -d --build` |
| `ports`, `environment` в `compose.yaml` | `docker compose up -d` — Compose пересоздаст контейнер |
| Ничего, нужен только перезапуск процесса | `docker compose restart api` |

`restart` **не пересобирает** образ и **не применяет** изменения `compose.yaml`. Это самая частая причина «я поправил, а ничего не изменилось».

## 9. Режим разработки, данные и второй сервис

### Код с компьютера без пересборки

Чтобы не пересобирать образ после каждой правки, подключи папку с кодом в контейнер. Добавь в сервис `api` (отступ — четыре пробела, на уровне `ports`):

```yaml
    volumes:
      - ./app:/code/app
    command: ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--reload"]
```

- **Bind mount** `./app:/code/app` — папка `app` с компьютера видна в контейнере по пути `/code/app` и **перекрывает** код, скопированный в образ.
- `command` заменяет `CMD` из Dockerfile; добавлен `--reload` — Uvicorn перезапускается при изменении файлов.

Зависимости по-прежнему внутри образа: после правки `requirements.txt` нужна пересборка. Если на Windows правки не подхватываются (обычно когда установлен `uvicorn[standard]` с пакетом `watchfiles`), добавь в сервис `environment: {WATCHFILES_FORCE_POLLING: "true"}`.

Это режим **только для разработки**. Для запуска на сервере bind mount исходников и `--reload` убирают: код должен приезжать внутри образа.

### Почему пользователи исчезают

```python
fake_user_database = []
```

Это список в памяти Python-процесса. Процесс перезапустился — список пуст.

| Механизм | Что хранит и сколько |
|---|---|
| Список Python | Пока жив процесс |
| Файлы, записанные внутри контейнера | Пока контейнер не удалён |
| Bind mount | Файлы в папке на компьютере |
| Named volume | Файлы в хранилище Docker, переживают удаление контейнера |

**Volume сохраняет файлы, а не оперативную память.** Подключение volume к текущему приложению ничего не изменит: чтобы данные переживали перезапуск, приложение должно писать их в файл или базу данных.

`docker compose down -v` удаляет ещё и named volumes проекта — вместе с данными. Не используй `-v` по привычке.

### Когда появится второй сервис

Если добавишь PostgreSQL как сервис `db`:

- API подключается к нему по адресу `db:5432` — имя сервиса работает как имя хоста в общей сети Compose.
- `localhost` внутри контейнера API — это сам контейнер API, а не база и не твой компьютер.
- `depends_on: [db]` задаёт только порядок старта, но не ждёт готовности базы. Для этого изучи `healthcheck` и `condition: service_healthy`.
- `environment` лишь передаёт переменные процессу. Приложение само должно их читать (`os.getenv`).

## 10. Диагностика: сначала найди этап

Любую проблему сначала относи к этапу: **сборка → старт процесса → сеть → поведение API**.

| Симптом | Этап | Что проверить |
|---|---|---|
| `Cannot connect to the Docker daemon` | до сборки | Запущен ли Docker Desktop / Engine |
| `COPY failed: ... not found` | сборка | Где запущена команда, контекст `.`, путь слева в `COPY`, `.dockerignore` |
| `No matching distribution found` | сборка | Версии в `requirements.txt` и версия Python в `FROM` |
| `No module named uvicorn` | старт | Есть ли `uvicorn` в зависимостях; пересобран ли образ |
| `Could not import module "app.main"` | старт | `WORKDIR`, правая часть `COPY`, `ls` внутри образа |
| Контейнер сразу завершился | старт | `docker compose logs api` — причина в последних строках |
| `port is already allocated` | старт | Порт хоста занят: останови другой контейнер или возьми 8080 |
| Контейнер работает, браузер не открывает | сеть | `ports`, `--host 0.0.0.0` в логе Uvicorn, адрес в браузере |
| Правки не видны | после сборки | Пересобран ли образ; `restart` не пересобирает |
| HTTP 500 | API | Traceback в логах — это ошибка Python, а не Docker |

Инструменты:

```sh
docker compose ps -a
docker compose logs --tail 100 api
docker compose exec api bash
docker compose run --rm --no-deps api bash
```

- `exec` — зайти в **работающий** контейнер.
- `run --rm ... bash` — запустить **новый временный** контейнер из того же образа с `bash` вместо `CMD`. Помогает, когда контейнер падает сразу при старте и `exec` недоступен.
- Всё, что ты исправил руками внутри контейнера, пропадёт. Найденное исправление переноси в Dockerfile.

## 11. Тренировка: от простого к переносу навыка

### Уровень 1. С пустого листа

Удали (или переименуй) свои `Dockerfile`, `.dockerignore`, `compose.yaml`. Не открывая урок, напиши их заново, опираясь только на семь вопросов из раздела 2. Засеки время.

**Критерий:** API открывается в Swagger, и ты вслух объясняешь каждую строку. Цель — уложиться в 10 минут.

### Уровень 2. Внешний порт

Сделай так, чтобы API открывался на `http://localhost:8080/docs`, а Uvicorn внутри по-прежнему слушал 8000. До запуска скажи: какое число меняется и в каком файле?

<details><summary>Ответ</summary>

В `compose.yaml`: `"127.0.0.1:8080:8000"`. Меняется левый порт — порт компьютера. Dockerfile и `CMD` не трогаются: приложение внутри всё так же на 8000.

</details>

### Уровень 3. Кэш

1. Собери образ два раза подряд (`docker build --progress=plain -t fastapi-train:local .`).
2. Поменяй строку в `main.py` и собери снова.
3. Добавь в `requirements.txt` пакет `httpx` и собери снова.

Для каждого раза найди в выводе, был ли шаг `RUN python -m pip install` взят из кэша.

<details><summary>Ответ</summary>

1. Вторая сборка: все шаги `CACHED`.
2. Шаг `pip install` — `CACHED`, заново выполняется только `COPY app/`.
3. `COPY requirements.txt` изменился → `pip install` и всё ниже выполняются заново.

Бонус: переставь `COPY app/ ./app/` выше `RUN pip install` и повтори пункт 2 — установка пакетов начнёт выполняться при каждой правке кода.

</details>

### Уровень 4. Сломай специально

По очереди внеси одну поломку, **предскажи симптом**, проверь, прочитай логи, верни рабочий вариант:

1. В `CMD` напиши `app.mian:app`.
2. Убери `uvicorn` из `requirements.txt` и пересобери.
3. В `ports` напиши `"127.0.0.1:8000:9000"`.
4. Убери из `CMD` `"--host", "0.0.0.0"`.
5. Замени `COPY app/ ./app/` на `COPY app/ ./`.
6. Запиши `CMD` с одинарными кавычками.

<details><summary>Ответ</summary>

1. Контейнер стартует и сразу завершается. В логах: `Error loading ASGI app. Could not import module "app.mian"`.
2. Сборка проходит, контейнер сразу завершается: `No module named uvicorn`.
3. Контейнер работает, в логах всё нормально (Uvicorn на 8000), но браузер получает сброс соединения или пустой ответ: Docker пробрасывает на порт 9000, где никто не слушает.
4. Контейнер работает, но в логе `Uvicorn running on http://127.0.0.1:8000`. Браузер не подключается: сервер принимает соединения только изнутри контейнера. Подсказку даёт адрес в логе.
5. Сборка проходит, контейнер падает: `Could not import module "app.main"`. Проверка `docker run --rm fastapi-train:local ls` покажет `main.py` прямо в `/code`, без папки `app`.
6. Контейнер падает с ошибкой shell вида `/bin/sh: ... not found`: строка не распознана как JSON и выполнилась как shell-команда вместе с кавычками.

</details>

### Уровень 5. Другая структура проекта

Код лежит в `src/api/server.py`, объект называется `application` (`application = FastAPI()`), зависимости — в `requirements.txt` в корне. Ответь на семь вопросов и напиши Dockerfile.

<details><summary>Ответ</summary>

```dockerfile
FROM python:3.12-slim
WORKDIR /code
COPY requirements.txt ./
RUN python -m pip install --no-cache-dir -r requirements.txt
COPY src/ ./src/
CMD ["python", "-m", "uvicorn", "src.api.server:application", "--host", "0.0.0.0", "--port", "8000"]
```

Модуль — путь от `WORKDIR` через точки: `src.api.server`, объект после двоеточия — `application`. Другой допустимый вариант: `"--app-dir", "src", "api.server:application"`.

</details>

### Уровень 6. Не HTTP-сервис

`worker.py` в корне проекта читает файлы, печатает отчёт и завершается. Зависимостей нет. Напиши Dockerfile. Нужны ли `EXPOSE` и `ports`? Что будет со статусом контейнера после работы?

<details><summary>Ответ</summary>

```dockerfile
FROM python:3.12-slim
WORKDIR /code
COPY worker.py ./
CMD ["python", "worker.py"]
```

`EXPOSE` и `ports` не нужны: программа не слушает сеть. `RUN pip install` не нужен: зависимостей нет. После работы контейнер завершается со статусом `Exited (0)` — это нормально: главный процесс закончился, и контейнер вместе с ним. Если ты понял это задание, ты применяешь принцип, а не шаблон FastAPI.

</details>

### Уровень 7. Настройка через переменную

Добавь в `main.py` эндпоинт `/hello`, который возвращает значение переменной окружения `GREETING` (по умолчанию `Hello`). Передай `GREETING=Привет` через Compose. Нужна ли пересборка, если потом поменять значение в `compose.yaml`?

<details><summary>Ответ</summary>

```python
import os

@app.get("/hello")
def hello():
    return {"greeting": os.getenv("GREETING", "Hello")}
```

```yaml
services:
  api:
    build: .
    image: fastapi-train:local
    ports:
      - "127.0.0.1:8000:8000"
    environment:
      GREETING: "Привет"
```

После первого добавления эндпоинта — `docker compose up -d --build` (изменился код). После смены только `GREETING` — достаточно `docker compose up -d`: образ тот же, Compose пересоздаст контейнер с новой переменной. `restart` не подойдёт. Аналог в `docker run`: `-e GREETING=Привет`.

</details>

### Уровень 8. Данные

Создай пользователя, выполни `docker compose restart api`, запроси `/users`. Объясни результат. Затем объясни, почему добавление `volumes: [app_data:/data]` ничего не исправит.

<details><summary>Ответ</summary>

Список пуст: перезапуск убил процесс, а данные жили только в его памяти. Volume сохраняет файлы в `/data`, но приложение туда ничего не пишет. Исправление — в коде: хранить пользователей в файле или в базе данных, путь к которой (на volume) или адрес которой передаётся через `environment`.

</details>
