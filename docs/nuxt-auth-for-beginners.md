## 0. Как проходить урок

Правила те же, что в [уроке по Docker](docker-for-beginners.md) и [уроке по ORM](orm-sqlalchemy-for-beginners.md):

1. **Печатай руками.** Не копируй блоки кода из урока в файлы. Опечатки и ошибки — часть обучения.
2. **Одна возможность — одна проверка.** После каждого шага сохраняй файл и смотри, что изменилось именно то, что ожидал.
3. **Сначала предскажи — потом запусти.** Перед каждой проверкой скажи себе, что должно произойти. Расхождение с реальностью — самое ценное место урока.
4. **Ответы — в свёрнутых блоках.** Открывай их только после своей попытки.

И два новых правила:

5. **Держи открытыми два терминала и инструменты разработчика.** В одном терминале работает бэкенд (Docker), в другом Nuxt. В браузере нажми **F12**: вкладка **Network** показывает каждый запрос, **Console** — ошибки JavaScript, **Application → Cookies** — cookie. Любой вопрос «почему не работает» начинается с этих трёх мест.
6. **Пароль — это радиоактивный груз.** Он живёт ровно столько, сколько нужно, чтобы его проверить: не попадает в логи, в ответы API, в `print` и в коммиты. Каждый раз, когда пишешь строку кода рядом с паролем, спроси себя: «куда он отсюда может утечь?»

План: что строим (раздел 1) → азбука веба для полного нуля (2) → где хранят пользователей и пароли (3) → семь вопросов перед экраном входа (4) → инструменты (5) → шаг ноль в песочнице (6) → бэкенд входа (7) → фронтенд по шагам (8) → проследить один вход целиком (9) → правила, на которых ошибаются (10) → диагностика (11) → тренировка (12) → повторение по памяти (13) → шпаргалка (14).

## 1. Что мы строим

В конце урока у тебя будет три программы, которые общаются по HTTP:

| Часть | Что это | Где работает | Порт |
|---|---|---|---|
| PostgreSQL | База: пользователи, хеши паролей, сессии | Docker, сервис `pg_database` | 5432 |
| FastAPI | API: проверяет пароль, создаёт сессию, говорит «кто ты» | Docker, сервис `api` | 8000 |
| Nuxt | Сайт: страница входа и закрытая главная страница | Node.js на твоём компьютере (`npm run dev`) | 3000 |

Схема одного входа:

```text
Браузер                       Nuxt :3000                    FastAPI :8000              PostgreSQL
   │  POST /api/auth/login        │                              │                         │
   │  {"login":..,"password":..}  │                              │                         │
   ├─────────────────────────────>│  POST /auth/login (прокси)   │                         │
   │                              ├─────────────────────────────>│  SELECT ... WHERE login │
   │                              │                              ├────────────────────────>│
   │                              │                              │  проверка хеша (argon2) │
   │                              │                              │  INSERT user_sessions   │
   │                              │                              ├────────────────────────>│
   │                              │  200 + Set-Cookie: session=… │                         │
   │  200 + Set-Cookie: session=… │<─────────────────────────────┤                         │
   │<─────────────────────────────┤                              │                         │
   │                                                                                         
   │  дальше браузер сам прикладывает Cookie: session=… к каждому запросу на localhost:3000
```

Как это будет выглядеть для человека:

1. Открываешь `http://localhost:3000/` — тебя перебрасывает на `/login`, потому что ты не вошёл.
2. Вводишь неправильный пароль — под формой красным «Неверный логин или пароль».
3. Вводишь правильный — попадаешь на `/` и видишь «Привет, Anna!».
4. Нажимаешь F5 — остаёшься на `/`: сайт помнит, кто ты.
5. Нажимаешь «Выйти» — снова на `/login`, и на `/` без входа больше не попасть.

**FastAPI отвечает на вопрос «кто ты и правда ли это ты?». Nuxt отвечает на вопрос «что показать человеку и куда его отправить?». PostgreSQL помнит пользователей и их сессии.**

### Как это выглядит в реальной работе

Почти у любого сайта есть ровно эти части: форма входа, эндпоинт, который проверяет пароль, хранилище сессий и «охранник», который не пускает на закрытые страницы. Меняется только, **кто проверяет пароль**: твоё приложение (как в этом уроке), корпоративный каталог (LDAP, Active Directory) или внешний сервис («Войти через Google»). Об этом — раздел 3.

## 2. Азбука веба для полного нуля

Этот раздел — словарь. Не нужно запоминать всё сразу: прочитай, ответь на вопросы в конце каждого пункта и возвращайся сюда, когда в коде встретится незнакомое слово.

### 2.1. HTTP: запрос и ответ

Браузер, Nuxt, FastAPI, Swagger, `curl`, Telegram-бот — все они разговаривают **одинаково**: один отправляет **запрос**, другой возвращает **ответ**. Это и есть HTTP. Других способов у них нет.

Запрос — это просто текст:

```text
POST /auth/login HTTP/1.1                       ← метод, путь, версия
Host: 127.0.0.1:8000                            ← заголовки: «имя: значение»
Content-Type: application/json
Cookie: theme=dark

{"login": "anna", "password": "correct-horse-42"}   ← тело (может не быть)
```

Ответ — тоже текст:

```text
HTTP/1.1 200 OK                                 ← статус
content-type: application/json                  ← заголовки
set-cookie: session=Qfeft5o...; HttpOnly; Max-Age=604800; Path=/; SameSite=lax

{"name": "Anna", "age": 30, "description": null, "id": 1}     ← тело
```

| Часть | Что это | Пример |
|---|---|---|
| Метод | Что хотим сделать | `GET` — получить, `POST` — создать или выполнить действие, `PUT` — заменить, `DELETE` — удалить |
| URL | Куда: схема, хост, порт, путь, query string | `http://127.0.0.1:8000/users?limit=10` |
| Заголовки | Служебные пары «имя: значение» | `Content-Type: application/json` — «в теле JSON» |
| Тело | Данные; у `GET` обычно нет | JSON с логином и паролем |
| Статус | Число-итог в ответе | `200` всё хорошо, `401` ты не вошёл, `404` нет такого |

Статусы, которые встретятся в уроке:

| Код | Значит | Кто у нас его вернёт |
|---|---|---|
| 200 OK | Всё получилось | Вход, «кто я» |
| 201 Created | Создано | Регистрация |
| 204 No Content | Получилось, тела нет | Выход |
| 302 Found | «Иди по другому адресу» (редирект) | Nuxt, когда не пускает на `/` |
| 401 Unauthorized | «Я не знаю, кто ты» — не вошёл или сессия кончилась | Неверный пароль, `/auth/me` без cookie |
| 403 Forbidden | «Знаю, кто ты, но тебе нельзя» | В уроке не будет, но не путай с 401 |
| 409 Conflict | Конфликт с тем, что уже есть | Логин уже занят |
| 422 Unprocessable Content | Запрос не подходит под схему Pydantic | Пароль короче 8 символов |
| 500 Internal Server Error | Сервер упал внутри | Ошибка в твоём коде — смотри логи |

**HTTP ничего не помнит.** Каждый запрос — с чистого листа: сервер не знает, что пять секунд назад ты вводил пароль. Чтобы «запомнить» человека, придумали **cookie**:

1. Сервер в ответе пишет заголовок `Set-Cookie: session=abc123`.
2. Браузер сохраняет эту пару у себя.
3. В **каждом** следующем запросе на тот же сайт браузер сам добавляет заголовок `Cookie: session=abc123`.
4. Сервер видит `abc123`, находит в базе, чья это сессия, — и «узнаёт» тебя.

Атрибуты после `;` в `Set-Cookie` говорят браузеру, как обращаться с cookie:

| Атрибут | Что делает |
|---|---|
| `HttpOnly` | JavaScript на странице **не может** прочитать cookie. Если на сайт внедрят вредный скрипт, он не украдёт сессию |
| `Max-Age=604800` | Сколько секунд хранить (604800 = 7 дней). Без него cookie живёт до закрытия браузера |
| `Path=/` | Для каких путей на сайте отправлять. `/` — для всех |
| `SameSite=Lax` | Не отправлять cookie, когда запрос к твоему сайту делает **чужой** сайт (кроме обычного перехода по ссылке). Защита от подделки запросов (CSRF) |
| `Secure` | Принимать и отправлять только по HTTPS. Исключение — `localhost`: Chrome и Firefox считают его безопасным и принимают такую cookie и по `http`. А вот по `http` на любом другом адресе (сервер без HTTPS, компьютер в локальной сети по IP) cookie просто не сохранится |

**Origin и «сайт».** Origin — это схема + хост + порт: `http://localhost:3000`. Для браузера `http://localhost:3000` и `http://127.0.0.1:8000` — **разные** origin и даже **разные сайты** (у них разные хосты). Отсюда в разделе 8 появится прокси: браузер будет ходить только на `localhost:3000`, а уже Nuxt — в FastAPI.

> **Проверь себя.**
>
> 1. Ты отправил `POST /auth/login` с пустым телом. Какой статус ждёшь от FastAPI?
> 2. Чем 401 отличается от 403?
> 3. Почему сервер «помнит» тебя после входа, если HTTP ничего не помнит?
>
> <details><summary>Ответ</summary>
>
> 1. **422**: FastAPI не смог разобрать тело по схеме Pydantic, и функция эндпоинта даже не вызывалась.
> 2. 401 — «не знаю, кто ты» (нет входа или сессия кончилась). 403 — «знаю, кто ты, но этого тебе нельзя» (например, обычному пользователю зайти в админку).
> 3. Помнит не HTTP, а **браузер** (хранит cookie и прикладывает её к каждому запросу) и **база** (хранит, чья это сессия). Сам сервер между запросами ничего не держит в голове.
>
> </details>

### 2.2. HTML: из чего состоит страница

HTML — это текст с **тегами**. Тег открывается `<имя>` и закрывается `</имя>`, внутри — содержимое. У тега бывают **атрибуты**: `имя="значение"` внутри открывающего тега.

```html
<form>
  <h1>Вход</h1>

  <label>
    Логин
    <input autocomplete="username" required>
  </label>

  <label>
    Пароль
    <input type="password" autocomplete="current-password" required>
  </label>

  <button type="submit">Войти</button>
</form>
```

| Тег или атрибут | Что делает |
|---|---|
| `<form>` | Форма: объединяет поля и кнопку. Enter в любом поле «отправляет» форму |
| `<h1>` | Заголовок первого уровня |
| `<label>` | Подпись к полю. Если поле лежит внутри `<label>`, клик по подписи ставит курсор в поле |
| `<input>` | Поле ввода. Закрывающего тега нет |
| `type="password"` | Поле показывает точки вместо букв |
| `autocomplete="username"`, `"current-password"` | Подсказка менеджеру паролей браузера: «здесь логин», «здесь пароль». С ними браузер предлагает сохранить и подставить пароль |
| `required` | Браузер не даст отправить форму, пока поле пустое |
| `<button type="submit">` | Кнопка, которая отправляет форму |
| `<main>`, `<p>` | Основное содержимое страницы; абзац текста |
| `class="card"` | Имя для CSS: по нему стили находят элемент |

Важная деталь: **если ничего не сделать, браузер при отправке формы перезагружает страницу**. В разделе 8 мы это отменим и отправим данные сами, через JavaScript.

### 2.3. CSS: как страница выглядит

CSS — это список правил «**кого** покрасить → **как**»:

```css
.card {
  width: 320px;
  padding: 24px;
  background: white;
}
```

- `.card` — **селектор**: «все элементы с `class="card"`». Бывают ещё селекторы по тегу (`input`, `button`) и по состоянию (`button:disabled` — выключенная кнопка, `input:focus` — поле, в котором сейчас курсор).
- `width: 320px;` — **свойство** и **значение**. `px` — пиксели.

Три идеи, на которых держится почти вся вёрстка:

1. **Коробки.** Каждый элемент — прямоугольник. Внутри — содержимое, вокруг него `padding` (внутренний отступ), потом `border` (рамка), потом `margin` (внешний отступ до соседей).
2. **Flex.** `display: flex` превращает элемент в «полку»: его дети выстраиваются в ряд (`flex-direction: row`) или в столбик (`column`). `gap: 16px` — расстояние между детьми. `justify-content: center` и `align-items: center` ставят детей по центру.
3. **Каскад.** Если два правила задают одно свойство одному элементу, побеждает более точное, а при равенстве — то, что ниже.

Цвета пишут как `#2563eb` (шестнадцатеричный код: красный, зелёный, синий) или `rgba(0, 0, 0, 0.08)` (то же плюс прозрачность от 0 до 1).

### 2.4. JavaScript: язык, который выполняет браузер

Python ты знаешь, поэтому JavaScript проще всего учить сравнением:

| Python | JavaScript | Заметка |
|---|---|---|
| `name = "Anna"` | `const name = 'Anna'` | `const` — переменную нельзя переприсвоить |
| `count = 0`, потом `count = 1` | `let count = 0`, потом `count = 1` | `let` — можно переприсвоить. `var` не используй |
| `f"Привет, {name}"` | `` `Привет, ${name}` `` | Обратные кавычки и `${...}` |
| `None` | `null` (и ещё `undefined` — «вообще не задано») | |
| `True`, `False` | `true`, `false` | С маленькой буквы |
| `{"login": "anna"}` (dict) | `{ login: 'anna' }` (объект) | Кавычки у ключей не нужны |
| `user["name"]` | `user.name` | |
| `[1, 2, 3]` (list) | `[1, 2, 3]` (массив) | |
| `def add(a, b): return a + b` | `function add(a, b) { return a + b }` | Блоки — фигурные скобки, а не отступы |
| `lambda a: a + 1` | `(a) => a + 1` | «Стрелочная функция» |
| `if x == 1:` | `if (x === 1) {` | Сравнивай **тремя** `===`: двойное `==` приводит типы и даёт сюрпризы |
| `and`, `or`, `not` | `&&`, `\|\|`, `!` | |
| `try: ... except: ...` | `try { ... } catch (error) { ... }` | |
| `finally:` | `finally { ... }` | Выполнится всегда |
| `print(x)` | `console.log(x)` | Видно в F12 → Console |
| `async def`, `await` | `async function`, `await` | Работают так же, как в FastAPI |
| `user and user.name` | `user?.name` | «Если `user` есть — возьми `name`, иначе `undefined`» |
| `a if cond else b` | `cond ? a : b` | |

**`async` / `await`.** Запрос по сети идёт долго. Функция, которая его делает, сразу возвращает «обещание результата» (Promise), а `await` ждёт, пока оно выполнится. Всё как в твоём FastAPI-коде: `await session.commit()`.

### 2.5. TypeScript: JavaScript с типами

TypeScript — это JavaScript плюс подписи типов, как type hints в Python. Браузер типов не понимает: перед запуском Nuxt их просто стирает. Нужны они **тебе и редактору**: редактор подчеркнёт `user.nmae` красным до того, как ты откроешь браузер.

```ts
type User = {
  id: number
  name: string
  age: number
  description: string | null
}
```

| Python | TypeScript |
|---|---|
| `int`, `float` | `number` |
| `str` | `string` |
| `bool` | `boolean` |
| `str \| None` | `string \| null` |
| `list[User]` | `User[]` |
| `class User(BaseModel): ...` | `type User = { ... }` |

Ещё две записи, которые встретятся:

- `$fetch<User>(...)` — угловые скобки после функции: «ответ будет типа `User`». Это обещание **редактору**; что реально пришлёт сервер, TypeScript не проверяет.
- `error as { statusCode?: number }` — «поверь мне, у этого объекта может быть поле `statusCode`». `?` — поле необязательное.

### 2.6. Vue: страница из компонентов

Nuxt построен на Vue. Во Vue страница собирается из **компонентов** — файлов `.vue`. В каждом до трёх блоков:

```vue
<script setup lang="ts">
// Логика на TypeScript: переменные, функции
const login = ref('')
</script>

<template>
  <!-- HTML, в котором можно использовать переменные из script -->
  <input v-model="login">
  <p>Ты ввёл: {{ login }}</p>
</template>

<style scoped>
/* CSS только для этого компонента */
p { color: gray; }
</style>
```

Главная идея Vue — **реактивность**: ты меняешь переменную, Vue сам перерисовывает всё, что от неё зависит. Не нужно искать элемент на странице и вписывать туда текст.

| Запись | Что делает |
|---|---|
| `const login = ref('')` | Реактивная переменная со стартовым значением `''` |
| `login.value` | Чтение и запись в **script**: `login.value = 'anna'` |
| `{{ login }}` | Вставить значение в **template**. Здесь `.value` писать не нужно — Vue подставит сам |
| `v-model="login"` | Двусторонняя связь: ввод в поле меняет `login`, изменение `login` меняет поле |
| `v-if="errorText"` | Показать элемент, только если условие истинно |
| `:disabled="loading"` | Двоеточие — значение атрибута берётся из JavaScript, а не пишется буквально |
| `@submit.prevent="onSubmit"` | `@` — «при событии». `submit` — отправка формы, `.prevent` — отменить перезагрузку страницы |
| `@click="onLogout"` | Вызвать функцию при клике |

### 2.7. Nuxt: что он добавляет к Vue

Vue умеет рисовать компоненты. Nuxt превращает набор компонентов в **сайт**:

| Возможность | Что это значит для тебя |
|---|---|
| Маршруты из файлов | `app/pages/login.vue` автоматически становится адресом `/login`. Таблицу адресов писать не нужно |
| Автоимпорт | `ref`, `useState`, `navigateTo`, `$fetch` и твои функции из `app/composables/` доступны везде без `import` |
| SSR | При открытии страницы её код **сначала выполняется на Nuxt-сервере** (Node.js), и браузер получает готовый HTML. Потом тот же код запускается в браузере и «оживляет» кнопки — это **гидратация** |
| `useState` | Общая на весь сайт переменная, которая к тому же переезжает с сервера в браузер при гидратации. Мы храним в ней «кто вошёл» |
| Middleware | Функция, которая выполняется **перед** открытием каждой страницы и может перенаправить. Наш «охранник» |
| Свой сервер (Nitro) | Nuxt — не только страницы, но и HTTP-сервер. Он умеет проксировать: принимать `/api/...` и пересылать в FastAPI |

**Код страницы выполняется в двух местах — на сервере Nuxt и в браузере.** Это самое непривычное в Nuxt и источник главной ловушки урока (раздел 10). Запомни сейчас, разберёмся по ходу.

## 3. Где и как хранят пользователей и пароли

Распространённое представление: «Пароли в базе не хранят, их держат где-то в LDAP». На самом деле всё наоборот, и разобраться в этом важнее, чем в любом теге Nuxt.

**Пользователей и пароли почти всегда хранят в базе данных. Вопрос только — в чьей базе и в каком виде.** Пароль хранят не сам по себе, а его **хеш**. А LDAP — это тоже база, просто особая и чужая для твоего приложения.

### 3.1. Не пароль, а хеш

**Хеш-функция** превращает любую строку в «отпечаток» фиксированной длины. Обратно её не развернуть: из отпечатка нельзя получить исходную строку. Одинаковый вход всегда даёт одинаковый отпечаток.

Как тогда проверить пароль при входе? Не нужно его «расшифровывать»: берём то, что ввёл человек, хешируем тем же способом и **сравниваем отпечатки**.

```text
Регистрация:   "correct-horse-42" ──hash──> "$argon2id$v=19$m=65536,t=3,p=4$naAf...$mC3U..."  → в базу
Вход:          "correct-horse-42" ──hash с той же солью──> совпало?  → пустить
```

Четыре способа хранить пароль, от худшего к правильному:

| Способ | Что лежит в базе | Что будет при утечке базы |
|---|---|---|
| Как есть (plain text) | `correct-horse-42` | Все пароли сразу у злоумышленника. А люди используют один пароль везде — и почта тоже под угрозой. Так утекли 32 миллиона паролей RockYou в 2009 году |
| Шифрование | Пароль, зашифрованный ключом | Ключ обычно лежит рядом (в коде, в настройках) и утекает вместе с базой. Шифрование обратимо — в этом и проблема. Так в 2013 году пострадал Adobe |
| Быстрый хеш (MD5, SHA-1, SHA-256) | `ef92b778bafe...` | Видеокарта перебирает **миллиарды** быстрых хешей в секунду. Все короткие и популярные пароли находятся за минуты. А без соли одинаковые пароли дают одинаковые хеши — один подобранный хеш раскрывает тысячи аккаунтов. Так в 2012 году LinkedIn потерял миллионы паролей с хешами SHA-1 без соли |
| **Медленный хеш с солью** (argon2id, bcrypt, scrypt) | `$argon2id$v=19$m=65536,t=3,p=4$соль$хеш` | Каждая попытка подбора стоит заметных времени и памяти. Перебор становится дорогим, а у каждого пароля своя соль |

**Соль** — случайная строка, которую добавляют к паролю перед хешированием и хранят **рядом с хешем, в открытую**. Её задача — не секретность, а уникальность: у двух людей с паролем `qwerty123` хеши получатся разными, и подбирать каждый придётся отдельно.

**Медленный хеш** специально сделан дорогим: argon2id для одной проверки берёт десятки миллисекунд и 64 МБ памяти. Для входа одного человека это незаметно, а для перебора миллиардов вариантов — неподъёмно.

Разберём строку, которую ты увидишь в своей базе:

```text
$argon2id$v=19$m=65536,t=3,p=4$naAftTUZfSJi7hWnefAwaw$mC3U+Ahjz8u0M9JcCM9uIDNeIlt/vXFXORIsasUmsZY
 └──┬───┘ └─┬─┘ └──────┬──────┘ └──────────┬──────────┘ └───────────────────┬──────────────────────┘
алгоритм  версия   параметры:          соль (случайная,               сам хеш
                m — память (КБ),       своя у каждого)
                t — число проходов,
                p — потоков
```

Всё, что нужно для проверки, хранится в одной строке. Поэтому в таблице достаточно одной колонки `password_hash`, а параметры можно со временем усилить: новые хеши будут с новыми параметрами, старые продолжат проверяться.

Какой алгоритм выбрать:

| Алгоритм | Когда |
|---|---|
| **argon2id** | По умолчанию для нового проекта. Рекомендация OWASP (сообщество по безопасности веб-приложений) |
| bcrypt | Очень распространён, встретишь в чужих проектах. Учитывает только первые 72 байта пароля — а одна русская буква занимает 2 байта |
| scrypt | Хороший вариант, если argon2 недоступен |
| PBKDF2 | Когда требуются сертифицированные алгоритмы (государственные стандарты) |

В уроке используем библиотеку `pwdlib` с argon2 — её же советует документация FastAPI.

> **Проверь себя.**
>
> 1. Зачем хранить соль, если она лежит в открытую рядом с хешем?
> 2. Можно ли по хешу из базы восстановить пароль и отправить пользователю на почту «напоминание»?
> 3. Почему SHA-256 хорош для проверки целостности файла, но плох для паролей?
>
> <details><summary>Ответ</summary>
>
> 1. Соль нужна не для секретности, а чтобы одинаковые пароли давали разные хеши. Без неё злоумышленник посчитает хеш `qwerty123` один раз и найдёт всех, у кого такой пароль. С солью — для каждого человека отдельно.
> 2. Нет. Хеш необратим. Если сайт присылает тебе твой старый пароль — значит, он хранит его в открытом или зашифрованном виде, и это плохой знак. Правильно — отправить ссылку на **смену** пароля.
> 3. SHA-256 очень быстрый. Для файлов это плюс, а для паролей — минус: быстрый хеш быстро перебирается.
>
> </details>

### 3.2. Где хранят: три мира

Кто именно хранит хеш и проверяет пароль — зависит от того, **для кого** приложение.

**Мир 1. Своя таблица в базе приложения.** Интернет-магазины, соцсети, почти все сайты для обычных людей и наш учебный проект. Таблица `users` с колонкой `password_hash`, проверку делает твой код.

**Мир 2. Каталог: LDAP и Active Directory.** Внутри компании. Каталог — это специальная база **сотрудников**: учётные записи, пароли, группы («бухгалтерия», «админы»), почта, телефоны, отделы.

| Термин | Что это |
|---|---|
| LDAP | **Протокол** (как HTTP), по которому программы спрашивают каталог: «найди сотрудника `ivanov`», «правда ли у него такой пароль?», «в каких он группах?» |
| OpenLDAP, FreeIPA | Серверы каталога, которые говорят по LDAP. Часто в Linux-инфраструктуре |
| Active Directory (AD) | Каталог Microsoft. Почти в каждой компании на Windows: им же проверяется вход в рабочий компьютер. Умеет говорить по LDAP |

И вот главное: **каталог — это тоже база, и пароли в ней лежат в виде хешей.** Active Directory хранит их в файле базы `NTDS.dit` на контроллерах домена, OpenLDAP — в атрибуте `userPassword`. Отличие от мира 1 не в том, что «пароли не в базе», а в том, что:

- база **одна на всю компанию**, а не своя у каждой программы;
- твоё приложение **никогда не видит хеш**: оно пересылает каталогу логин и пароль («LDAP bind») и получает ответ «да» или «нет»;
- уволили сотрудника — отключили одну учётную запись в каталоге, и он не может войти никуда.

Когда что-то «авторизуется через LDAP», внутри происходит примерно это:

```text
Приложение ──LDAP bind: uid=ivanov, пароль=…──> Каталог (AD / OpenLDAP)
           <────────── успех / неудача ─────────
Приложение ──поиск: в каких группах ivanov?───> Каталог
           <──── cn=accounting, cn=vpn-users ───
```

**Мир 3. Единый вход (SSO): OAuth 2.0 и OpenID Connect.** Кнопки «Войти через Google», «через Яндекс ID», «через Госуслуги»; в компаниях — Keycloak или Microsoft Entra ID. Пароль вводится **на сайте провайдера**, твоё приложение пароль вообще не получает:

```text
1. Пользователь нажимает «Войти через Google» → браузер уходит на google.com
2. Google спрашивает пароль (и второй фактор) у себя
3. Google возвращает браузер на твой сайт с одноразовым кодом
4. Твой бэкенд меняет код на подписанный документ «это user 1234567, email anna@…» (ID-токен)
5. Твой бэкенд находит или создаёт у себя пользователя с этим внешним ID и создаёт сессию
```

- **OAuth 2.0** — протокол «разреши приложению действовать от твоего имени» (например, читать твой календарь).
- **OpenID Connect (OIDC)** — надстройка над OAuth 2.0 именно для входа: «скажи приложению, кто я».
- Таблица `users` у приложения при этом **остаётся**: в ней id, email, имя, внешний ID у провайдера. Нет только колонки с паролем.

Часто миры складываются: Keycloak проверяет пароль по корпоративному Active Directory (мир 2), а приложения компании входят через Keycloak по OIDC (мир 3).

| | Своя таблица | LDAP / AD | SSO (OIDC) |
|---|---|---|---|
| Кто хранит хеш пароля | Твоя база | Каталог компании | Провайдер (Google, Keycloak) |
| Кто проверяет пароль | Твой код | Каталог | Провайдер |
| Видит ли приложение пароль | Да, в момент входа | Да, пересылает каталогу | Нет |
| Типичное применение | Сайты для всех | Внутренние системы компании | И то и другое |
| Что сложно | Всё на тебе: хеши, сброс пароля, защита от перебора | Нужен каталог и админ, который им управляет | Регистрация приложения у провайдера, редиректы |

Мы делаем мир 1: он ничего не требует, кроме PostgreSQL, и на нём видно каждую деталь. Когда-нибудь ты будешь подключать LDAP или OIDC — и узнаешь в них те же части: проверку пароля и сессию после неё.

> **Проверь себя.**
>
> 1. Друг говорит: «У нас всё по-взрослому, пароли не в базе, а в Active Directory». Что ты ему ответишь?
> 2. В компании 30 внутренних сайтов. Почему не сделать у каждого свою таблицу пользователей?
> 3. Твой сайт работает только со входом через Яндекс ID. Нужна ли тебе таблица `users`?
>
> <details><summary>Ответ</summary>
>
> 1. Active Directory — это тоже база, и пароли в ней лежат в виде хешей. Просто это одна общая база на всю компанию, а не своя у приложения.
> 2. Тридцать паролей у каждого сотрудника, тридцать мест, где их надо сменить или отключить при увольнении, тридцать реализаций хеширования, в каждой из которых может быть ошибка. Каталог или SSO решают это в одном месте.
> 3. Да. Хранить пароль не нужно, но нужно где-то хранить, какой внешний ID Яндекса соответствует какому пользователю твоего сайта, и связывать с ним его данные (у нас — чеки).
>
> </details>

### 3.3. После входа: сессия или токен

Пароль проверяется **один раз** — при входе. Дальше нужно как-то узнавать человека в каждом запросе, не спрашивая пароль снова. Способов два.

**Сессия на сервере (stateful).** После входа сервер создаёт случайную строку (токен сессии), записывает в свою базу «эта строка — Anna, до такого-то числа» и отдаёт строку браузеру в cookie. В каждом запросе сервер ищет строку в базе.

**Самодостаточный токен — JWT (stateless).** После входа сервер собирает документ «это Anna, действует до 18:00», **подписывает** его секретным ключом и отдаёт клиенту. В каждом запросе сервер проверяет подпись — в базу ходить не нужно.

| | Сессия в базе | JWT |
|---|---|---|
| Что у клиента | Случайная строка без смысла | Документ с данными и подписью (его можно прочитать, но не подделать) |
| Нужна ли база в каждом запросе | Да, найти сессию | Нет, проверить подпись |
| Выйти, «выкинуть» украденную сессию | Удалить строку из таблицы — и всё | Сложно: токен действует, пока не истечёт срок. Поэтому делают короткий срок и второй «refresh»-токен |
| Где обычно | Сайты, где фронтенд и бэкенд — одно целое | Связь сервис—сервис, мобильные приложения, большие системы с множеством бэкендов |

Где клиент хранит токен — не менее важно:

| Где | Риск |
|---|---|
| Cookie с `HttpOnly` | JavaScript страницы его не видит. Внедрённый вредный скрипт сессию не украдёт |
| `localStorage` | Любой JavaScript на странице может прочитать и отправить злоумышленнику. Для токенов входа — не надо |

В документации FastAPI вход показан на JWT. Мы выбираем **сессию в PostgreSQL и cookie с `HttpOnly`**: это проще, выход работает честно (удалили строку — сессии нет), а у нас один сайт и один бэкенд.

И последняя деталь: в таблице сессий мы храним не сам токен, а его **хеш SHA-256**. Если копия базы утечёт, злоумышленник не сможет войти чужими сессиями. Медленный argon2 тут не нужен: токен — это 32 случайных байта, а не придуманный человеком пароль, и перебрать его невозможно даже быстрым хешем.

> **Проверь себя.**
>
> 1. У пользователя украли ноутбук. Как в нашей схеме выкинуть вора из аккаунта?
> 2. Почему токен сессии хешируют SHA-256, а пароль — argon2?
>
> <details><summary>Ответ</summary>
>
> 1. Удалить строки этого пользователя из `user_sessions` (уровень 6 тренировки). Следующий же запрос вора получит 401.
> 2. Пароль придумывает человек: он короткий и часто предсказуемый, поэтому нужен медленный хеш. Токен — 32 случайных байта (2²⁵⁶ вариантов): его не перебрать ни с каким хешем, поэтому достаточно быстрого.
>
> </details>

## 4. Семь вопросов перед экраном входа

Экран не пишут «сверху вниз по памяти». Его пишут, **ответив на вопросы о данных и действиях**. Эти семь вопросов — сам навык:

1. Какие данные показываю или отправляю и как они выглядят? → `type` в TypeScript, схема Pydantic
2. Какой эндпоинт за это отвечает: метод и URL? → `method`, адрес
3. Где параметры: в пути, в query string, в теле, в cookie? → `body: {...}`, cookie браузер приложит сам
4. Когда делать запрос: при открытии страницы или по действию пользователя? → middleware или функция на кнопке
5. Что видит пользователь, пока ждёт, и что — при ошибке? → `loading`, `errorText`
6. Что должно измениться после успеха? → куда перейти, что запомнить
7. С какого адреса на какой идёт запрос и дойдёт ли cookie? → прокси `/api`

Ответы для нашего экрана:

| Вопрос | Ответ |
|---|---|
| Данные | Отправляем: `login`, `password`. Получаем: `User` — `id`, `name`, `age`, `description` (без пароля и хеша!) |
| Эндпоинты | Войти — `POST /auth/login`; кто я — `GET /auth/me`; выйти — `POST /auth/logout`; регистрация — `POST /auth/register` |
| Параметры | Логин и пароль — в **JSON-теле** (никогда не в URL: адреса попадают в историю браузера и логи серверов). Сессия — в **cookie** |
| Когда | «Кто я» — перед открытием любой страницы (middleware). Вход и выход — по кнопке |
| Ожидание и ошибки | Кнопка «Входим…» и выключена; «Неверный логин или пароль» на 401; «Сервер не отвечает» на всё остальное |
| После успеха | Запомнить пользователя в `useState`, перейти на `/` |
| Адреса | Браузер → `localhost:3000/api/...` → прокси Nuxt → `127.0.0.1:8000/...`. Для браузера это один сайт, поэтому cookie ходит без CORS |

### 6.1. Хеш пароля в Python

Поставь библиотеку в локальное окружение (активируй `.venv`, как в прошлых уроках):

```sh
python -m pip install "pwdlib[argon2]"
```

Кавычки нужны: без них квадратные скобки PowerShell и некоторые shell понимают по-своему. `[argon2]` значит «вместе с поддержкой argon2».

Создай **`sandbox/hash_try.py`**:

```python
import hashlib
import time

from pwdlib import PasswordHash

hasher = PasswordHash.recommended()
password = "correct-horse-42"

print("SHA-256 два раза:")
print(hashlib.sha256(password.encode()).hexdigest())
print(hashlib.sha256(password.encode()).hexdigest())

print("argon2 два раза:")
first = hasher.hash(password)
second = hasher.hash(password)
print(first)
print(second)

print("Проверка:", hasher.verify(password, first), hasher.verify(password, second), hasher.verify("qwerty123", first))

start = time.perf_counter()
for _ in range(100_000):
    hashlib.sha256(password.encode()).hexdigest()
print(f"100 000 SHA-256: {time.perf_counter() - start:.2f} с")

start = time.perf_counter()
for _ in range(10):
    hasher.verify(password, first)
print(f"10 проверок argon2: {time.perf_counter() - start:.2f} с")
```

- `PasswordHash.recommended()` — хешер с алгоритмом и параметрами, которые авторы библиотеки считают правильными сейчас (argon2id).
- `.encode()` — превратить строку в байты: хеш-функции работают с байтами.
- `time.perf_counter()` — точный секундомер.

> **Предскажи до запуска:**
>
> 1. Одинаковы ли две строки SHA-256? А две строки argon2?
> 2. Что напечатает строка «Проверка»?
> 3. Что быстрее: 100 000 SHA-256 или 10 argon2?
>
> <details><summary>Ответ</summary>
>
> Запусти `python sandbox/hash_try.py`. Примерно так:
>
> ```text
> SHA-256 два раза:
> 04fb8b28a8996c4b3bdf8e1ad753713531f11cd52af8aa45fd1148ec6fb0c000
> 04fb8b28a8996c4b3bdf8e1ad753713531f11cd52af8aa45fd1148ec6fb0c000
> argon2 два раза:
> $argon2id$v=19$m=65536,t=3,p=4$DWBDJJ2Ywm1ON+B77ABiNA$OBMLvst4iYPS776kBgn8jenQouLRguPX0DTC9DtIkh8
> $argon2id$v=19$m=65536,t=3,p=4$Tc+5lTtzDCWA6bLAsVP8RA$xn4iD4BZJciGVJ230+RJUBy8vpPr+dOLnoaXtpldhTs
> Проверка: True True False
> 100 000 SHA-256: 0.05 с
> 10 проверок argon2: 0.59 с
> ```
>
> 1. SHA-256 одинаковые: соли нет, одинаковый вход — одинаковый выход. argon2 **разные**: при каждом `hash` генерируется новая соль (часть между последними `$`).
> 2. `True True False`. Оба разных хеша подходят к паролю, потому что `verify` берёт соль из самой строки хеша. Чужой пароль не подходит.
> 3. 100 000 SHA-256 — в десять раз быстрее, чем 10 argon2. То есть один argon2 примерно в **сто тысяч раз** медленнее одного SHA-256. Для тебя 60 мс при входе незаметны, а для перебора миллиардов вариантов — это годы.
>
> </details>

Попробуй сам: замени в `verify` пароль на `"Correct-horse-42"` (одна заглавная буква). Что получится?

### 6.2. Страница без Nuxt

Чтобы оценить, что делает за тебя Vue, сделай форму «по-старинке» — один HTML-файл. Создай **`sandbox/login.html`**:

```html
<!doctype html>
<html lang="ru">
<head>
  <meta charset="utf-8">
  <title>Песочница</title>

    .error { color: red; }
```

> **Предскажи:** что появится на странице и в консоли? Дойдёт ли запрос до FastAPI?
>
> <details><summary>Ответ</summary>
>
> На странице сначала мелькнёт «Ты ввёл: anna», потом красное **«Ошибка: TypeError: Failed to fetch»**. В консоли:
>
> ```text
> Access to fetch at 'http://127.0.0.1:8000/users' from origin 'null' has been blocked by CORS policy:
> No 'Access-Control-Allow-Origin' header is present on the requested resource.
> ```
>
> Самое интересное — в `docker compose logs api`: там есть строка `"GET /users HTTP/1.1" 200 OK`. **Запрос дошёл, и сервер ответил.** Это браузер не отдал ответ твоему JavaScript: страница с одного origin (здесь `null` — у файлов с диска origin нет) не может читать ответы другого origin, пока тот явно не разрешит это заголовками CORS.
>
> </details>

Это правило — **политика одного источника (same-origin policy)**. Она защищает тебя: иначе любой открытый сайт мог бы из твоего браузера читать твою почту, где ты уже вошёл. Обойти её можно двумя путями:

| Путь | Как | Что с cookie |
|---|---|---|
| CORS | Бэкенд добавляет заголовки «origin `http://localhost:3000` можно» | Для cookie нужны ещё `allow_credentials=True` на бэкенде, `credentials: 'include'` во всех запросах и совпадение «сайтов» у фронтенда и API. Много мест, где ошибиться |
| **Прокси** | Браузер ходит только на свой origin `localhost:3000/api/...`, а Nuxt-сервер пересылает запрос в FastAPI | Для браузера это один сайт: cookie просто работает. CORS не нужен вообще |

В разделе 8 мы выберем прокси. Так же делают многие настоящие сайты: фронтенд и API снаружи видны под одним адресом.

### Шаг 1. Таблицы — `05_auth.sql`

Создай **`database/init/05_auth.sql`**:

```sql
ALTER TABLE payment_statistic.users
    ADD COLUMN login         TEXT UNIQUE,
    ADD COLUMN password_hash TEXT;

CREATE TABLE payment_statistic.user_sessions
(
    id         SERIAL PRIMARY KEY,
    token_hash TEXT        NOT NULL UNIQUE,
    user_id    INTEGER     NOT NULL REFERENCES payment_statistic.users (id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at TIMESTAMPTZ NOT NULL
);
```

- `login TEXT UNIQUE` — двух одинаковых логинов база не допустит. Колонка может быть пустой (`NULL`): у админа из `02_table_users.sql` и у пользователей из `POST /create_user` логина нет, войти они не смогут — и это нормально.
- `password_hash` — **не** `password`. Название колонки само напоминает, что в ней лежит.
- `ON DELETE CASCADE` — удалили пользователя, база сама удалит его сессии.
- `TIMESTAMPTZ` — дата и время **с часовым поясом**. Для сроков действия только так: иначе сервер в одном часовом поясе и база в другом разойдутся на несколько часов.

> **Предскажи:** скрипты из `database/init/` выполняет сам контейнер Postgres. Выполнится ли новый `05_auth.sql`, если просто перезапустить `docker compose up -d`?
>
> <details><summary>Ответ</summary>
>
> Нет. Как ты помнишь из [урока по Postgres](postgres-docker-for-beginners.md), скрипты из `/docker-entrypoint-initdb.d` выполняются **только при первом запуске на пустом volume**. Твоя база уже существует, поэтому новый файл нужно выполнить руками один раз. А на чистой установке (у другого человека или после `docker compose down -v`) он выполнится сам — по порядку после `04_...`.
>
> </details>

Выполни скрипт в работающем контейнере:

```sh
docker compose exec pg_database sh -c 'psql -U $POSTGRES_USER -d $POSTGRES_DB -f /docker-entrypoint-initdb.d/05_auth.sql'
```

**Ожидаемо:** `ALTER TABLE` и `CREATE TABLE`. Файл виден внутри контейнера, потому что `./database/init` подключена туда через `volumes` в `compose.yaml`.

Проверь: зайди в psql (команда из раздела 5) и выполни `\d payment_statistic.users` и `\d payment_statistic.user_sessions`. Выход из psql — `\q`.

### Шаг 4. Безопасность — `app/security.py`

Создай **`app/security.py`** — все операции с секретами в одном месте:

```python
import hashlib
import secrets

from pwdlib import PasswordHash

password_hasher = PasswordHash.recommended()

# Хеш случайного пароля: проверяем его, когда логина нет, чтобы ответ шёл столько же времени
DUMMY_HASH = password_hasher.hash(secrets.token_urlsafe(32))


def hash_password(password: str) -> str:
    return password_hasher.hash(password)


def verify_password(password: str, password_hash: str) -> bool:
    return password_hasher.verify(password, password_hash)


def new_session_token() -> str:
    return secrets.token_urlsafe(32)


def hash_token(token: str) -> str:
    return hashlib.sha256(token.encode()).hexdigest()
```

- `secrets` — модуль для **криптографически стойких** случайных чисел. Обычный `random` для токенов не годится: его последовательность можно предсказать.
- `token_urlsafe(32)` — 32 случайных байта, записанные буквами, цифрами, `-` и `_`. Такую строку можно класть в cookie как есть.
- `DUMMY_HASH` — зачем он, разберём в шаге 8.

### Шаг 5. Репозитории

В `app/repositories/user.py` добавь в `UserRepository` метод:

```python
    async def get_by_login(self, login: str) -> User | None:
        stmt = select(User).where(User.login == login)
        return await self.session.scalar(stmt)
```

`scalar` возвращает первую найденную строку или `None`. Больше одной не будет: логин уникален.

Создай **`app/repositories/user_session.py`**:

```python
from datetime import datetime, timezone

from sqlalchemy import select

from app.models import UserSession
from app.repositories.base import BaseRepository


class UserSessionRepository(BaseRepository[UserSession]):
    model = UserSession

    async def get_active(self, token_hash: str) -> UserSession | None:
        stmt = select(UserSession).where(
            UserSession.token_hash == token_hash,
            UserSession.expires_at > datetime.now(timezone.utc),
        )
        return await self.session.scalar(stmt)

    async def get_by_token_hash(self, token_hash: str) -> UserSession | None:
        stmt = select(UserSession).where(UserSession.token_hash == token_hash)
        return await self.session.scalar(stmt)
```

- `get_active` — сессия с таким хешем, **срок которой ещё не истёк**. Просроченная сессия для нас то же самое, что её отсутствие.
- `get_by_token_hash` — любая, даже просроченная: пригодится при выходе, чтобы удалить строку.
- `datetime.now(timezone.utc)` — текущее время **с часовым поясом**. Без `timezone.utc` Python вернёт «наивное» время, и сравнение с `TIMESTAMPTZ` упадёт.

Допиши `UserSessionRepository` в `app/repositories/__init__.py`.

```python
def get_user_session_repository(session: SessionDep) -> UserSessionRepository:
    return UserSessionRepository(session)

UserSessionRepoDep = Annotated[UserSessionRepository, Depends(get_user_session_repository)]


async def get_current_user(
        users: UserRepoDep,
        user_sessions: UserSessionRepoDep,
        token: Annotated[str | None, Cookie(alias=SESSION_COOKIE)] = None,
) -> User:
    if token is None:
        raise HTTPException(status_code=401, detail="Not authenticated")
```

### Шаг 8. Эндпоинты — `app/api/auth.py`

Создай **`app/api/auth.py`**:

```python
from datetime import datetime, timedelta, timezone
from typing import Annotated

from fastapi import APIRouter, Cookie, HTTPException, Response

from app.api.dependencies import CurrentUserDep, SessionDep, UserRepoDep, UserSessionRepoDep
from app.config import get_settings
from app.constants import SESSION_COOKIE, SESSION_DAYS
from app.models import User
from app.schemas import LoginIn, RegisterIn, UserRead
from app.security import DUMMY_HASH, hash_password, hash_token, new_session_token, verify_password

router = APIRouter(prefix="/auth", tags=["auth"])
settings = get_settings()


@router.post("/register", response_model=UserRead, status_code=201)
async def register(data: RegisterIn, users: UserRepoDep, session: SessionDep) -> User:
    if await users.get_by_login(data.login) is not None:
        raise HTTPException(status_code=409, detail="Login already taken")
    user = await users.create(
        **data.model_dump(exclude={"password"}),
        password_hash=hash_password(data.password),
    )
    await session.commit()
    return user
```

- `prefix="/auth"` — все пути роутера начинаются с `/auth`: `@router.post("/register")` — это `POST /auth/register`.
- `data.model_dump(exclude={"password"})` — словарь из схемы **без пароля**: `name`, `age`, `description`, `login`. Пароль в модель не передаём — у неё и поля такого нет, — вместо него кладём хеш.
- `response_model=UserRead` — FastAPI отдаст клиенту только поля `UserRead`. Даже если в объекте `User` есть `password_hash`, в ответ он не попадёт.

Допиши в тот же файл вход:

```python
@router.post("/login", response_model=UserRead)
async def login(
        data: LoginIn,
        response: Response,
        users: UserRepoDep,
        user_sessions: UserSessionRepoDep,
        session: SessionDep,
) -> User:
    user = await users.get_by_login(data.login)
    stored_hash = user.password_hash if user is not None and user.password_hash else DUMMY_HASH
    if not verify_password(data.password, stored_hash) or user is None:
        raise HTTPException(status_code=401, detail="Wrong login or password")

    token = new_session_token()
    await user_sessions.create(
        token_hash=hash_token(token),
        user_id=user.id,
        expires_at=datetime.now(timezone.utc) + timedelta(days=SESSION_DAYS),
    )
    await session.commit()

    response.set_cookie(
        key=SESSION_COOKIE,
        value=token,
        max_age=SESSION_DAYS * 24 * 60 * 60,
        httponly=True,
        samesite="lax",
        secure=settings.app_env != "dev",
    )
    return user
```

Разберём по строкам — здесь каждая важна:

- **Один ответ на «нет такого логина» и «неверный пароль».** Если отвечать по-разному («нет такого пользователя» / «неверный пароль»), злоумышленник сможет проверить, какие логины существуют, и подбирать пароль только к ним.
- **`DUMMY_HASH`.** Если логина нет и сразу ответить 401, ответ придёт за 1 мс, а при существующем логине — за 60 мс (argon2). По времени ответа снова видно, есть ли логин. Поэтому при отсутствии пользователя мы всё равно проверяем пароль — против хеша случайной строки, который никогда не совпадёт. Время ответа одинаковое.
- `or user is None` — подстраховка: `verify_password` с `DUMMY_HASH` и так вернёт `False`, но эта проверка говорит редактору, что ниже `user` точно не `None`.
- `response: Response` — объект ответа, в который можно дописать заголовки. FastAPI соединит его с тем, что вернёт функция.
- `set_cookie(...)` — заголовок `Set-Cookie` с атрибутами из раздела 2.1. **В cookie — сам токен, в базе — его хеш.**
- `secure=settings.app_env != "dev"` — на боевом сервере с HTTPS (`APP_ENV=prod`) cookie будет ходить только по HTTPS. На твоём компьютере сайт работает по `http`: Chrome и Firefox сделали бы для `localhost` исключение, но стоит открыть сайт по IP или в другом браузере — и вход молча перестанет работать. Поэтому в режиме `dev` выключаем.

Допиши выход и «кто я»:

```python
@router.post("/logout", status_code=204)
async def logout(
        response: Response,
        user_sessions: UserSessionRepoDep,
        session: SessionDep,
        token: Annotated[str | None, Cookie(alias=SESSION_COOKIE)] = None,
) -> None:
    if token is not None:
        user_session = await user_sessions.get_by_token_hash(hash_token(token))
        if user_session is not None:
            await user_sessions.delete(user_session)
            await session.commit()
    response.delete_cookie(SESSION_COOKIE)


@router.get("/me", response_model=UserRead)
async def me(user: CurrentUserDep) -> User:
    return user
```

- Выход **удаляет строку сессии из базы**. Просто стереть cookie в браузере мало: если токен успели скопировать, он остался бы рабочим.
- `delete_cookie` — это тоже `Set-Cookie`, только с `Max-Age=0`: «забудь эту cookie сейчас же».
- Выход отвечает 204 даже без cookie: выйти, если ты не вошёл, — не ошибка.
- `/auth/me` — самый короткий эндпоинт урока. Вся работа — в `CurrentUserDep`.

Подключи роутер в `app/main.py`: импорт `from app.api.auth import router as auth_router` и строка `app.include_router(auth_router)` рядом с остальными.

> **Не добавляй сюда `logs.logs_add(..., input_data=str(data), ...)`**, как в `create_user`. `str(data)` у `RegisterIn` и `LoginIn` содержит пароль открытым текстом — он навсегда ляжет в таблицу `logs.api_logs`. Если логировать вход, то только логин и результат.

Допиши **в начало** `app/pages/login.vue`:

В шаблоне свяжи поля с переменными и форму — с функцией:




- `<script setup lang="ts">` — логика компонента на TypeScript. Всё, что тут объявлено, доступно в шаблоне.

> <details><summary>Ответ</summary>

> Нет, только в консоли браузера. ### Шаг 5. Мост к API — прокси в `nuxt.config.ts`

Приведи `nuxt.config.ts` к виду:

```ts
// https://nuxt.com/docs/api/configuration/nuxt-config
export default defineNuxtConfig({
  compatibilityDate: '2025-07-15',
  devtools: { enabled: true },
  routeRules: {
    '/api/**': { proxy: 'http://127.0.0.1:8000/**' },
  },
})
```

(Строку `compatibilityDate` оставь такой, какую создал мастер.)

- `routeRules` — правила для адресов Nuxt-сервера.
- `'/api/**'` — любой адрес, начинающийся с `/api/`. `**` — «что угодно дальше, сколько угодно уровней».
- `proxy: 'http://127.0.0.1:8000/**'` — переслать запрос туда, подставив вместо `**` то, что было после `/api/`. Запрос `localhost:3000/api/auth/login` уйдёт в `127.0.0.1:8000/auth/login` — с тем же методом, телом и cookie. Ответ, включая `Set-Cookie`, вернётся браузеру.
- `127.0.0.1`, а не `localhost`: на некоторых системах `localhost` сначала превращается в IPv6-адрес `::1`, а Docker опубликовал порт API только на IPv4 `127.0.0.1`.

Перезапусти Nuxt (Ctrl+C и снова `npm run dev`): правки `nuxt.config.ts` надёжнее применять перезапуском.

**Проверь в браузере** (просто открой адреса):

- `http://localhost:3000/api/users` — JSON со списком пользователей. Это ответ FastAPI, но адрес — Nuxt.
- `http://localhost:3000/api/auth/me` — `{"detail":"Not authenticated"}`: cookie ещё нет.

> **Предскажи:** если в песочнице из раздела 6.2 открыть `sandbox/login.html` и поменять адрес в `fetch` на `http://localhost:3000/api/users`, ошибка CORS пропадёт?
>
> <details><summary>Ответ</summary>
>
> Нет. Файл с диска — это всё ещё origin `null`, а `localhost:3000` — другой origin. Прокси помогает только страницам, которые **сами** открыты с `localhost:3000`, то есть страницам Nuxt. Для них `/api/...` — свой же адрес.
>
> </details>

### Шаг 6. Вход — `$fetch`, ошибки, ожидание

Теперь `onSubmit` по-настоящему отправит логин и пароль. Замени `<script setup>` в `login.vue`:

```vue
<script setup lang="ts">
const login = ref('')
const password = ref('')
const errorText = ref('')
const loading = ref(false)

async function onSubmit() {
  errorText.value = ''
  loading.value = true
  try {
    await $fetch('/api/auth/login', {
      method: 'POST',
      body: { login: login.value, password: password.value },
    })
    await navigateTo('/')
  } catch (error) {
    const status = (error as { statusCode?: number }).statusCode
    if (status === 401) {
      errorText.value = 'Неверный логин или пароль'
    } else {
      errorText.value = 'Сервер не отвечает, попробуй позже'
    }
  } finally {
    loading.value = false
  }
}
</script>
```

В шаблоне — сообщение об ошибке над кнопкой и «живая» кнопка:

```vue
      <p v-if="errorText" class="error">{{ errorText }}</p>

      <button type="submit" :disabled="loading">
        {{ loading ? 'Входим…' : 'Войти' }}
      </button>
```

- `$fetch(адрес, настройки)` — HTTP-запрос. `method: 'POST'` — метод. `body: {...}` — тело: `$fetch` сам превратит объект в JSON и поставит заголовок `Content-Type: application/json`. Путь начинается с `/api` — запрос идёт на свой origin и через прокси.
- Если сервер ответил 4xx или 5xx, `$fetch` **бросает ошибку** — выполнение прыгает в `catch`. В ошибке есть поле `statusCode` с кодом ответа. Если сервер не ответил вообще (Docker выключен), `statusCode` будет другим или его не будет.
- `finally` выполнится и после успеха, и после ошибки: кнопка снова станет активной.
- `navigateTo('/')` — перейти на главную без перезагрузки страницы.
- `:disabled="loading"` — пока идёт запрос, кнопку не нажать второй раз.
- `loading ? 'Входим…' : 'Войти'` — тернарный оператор: «если идёт загрузка — один текст, иначе другой».

**Проверь, держа открытой вкладку Network:**

1. Неверный пароль → под формой «Неверный логин или пароль». В Network — запрос `login` со статусом **401**. Нажми на него: вкладка **Payload** показывает тело, которое ушло; **Response** — что вернул FastAPI.
2. Правильный пароль (`anna` / `correct-horse-42`) → переход на «Главную». В Network у запроса `login` статус **200**, а в **Headers → Response Headers** — `set-cookie: session=...`.
3. Открой **Application → Cookies → http://localhost:3000**. Там cookie `session`, в колонке **HttpOnly** — галочка.
4. В **Console** набери `document.cookie` и нажми Enter.
5. Останови бэкенд (`docker compose stop api`), вернись на `/login` и попробуй войти. Потом снова `docker compose start api`.

> **Предскажи:** что вернёт `document.cookie` в пункте 4? Что увидишь в пункте 5?
>
> <details><summary>Ответ</summary>
>
> 4. Пустую строку `''`. Cookie есть, браузер её отправляет, но JavaScript страницы её не видит — это и есть `HttpOnly`.
> 5. «Сервер не отвечает, попробуй позже». Nuxt-прокси не достучался до FastAPI и вернул браузеру ошибку 5xx — это не 401, значит, ветка `else`.
>
> </details>

Обрати внимание: если зайти на `/login` уже войдя, форма покажется снова, а на «Главную» можно попасть и **без** входа. Охранника ещё нет — это шаги 7 и 8.

### Шаг 7. Кто вошёл — тип, `useState`, выход

Создай **`app/types/user.ts`** — копию схемы `UserRead` из FastAPI на TypeScript:

```ts
export type User = {
  id: number
  name: string
  age: number
  description: string | null
}
```

Сверь с `app/schemas/user.py`: Python `int` → `number`, `str` → `string`, `str | None` → `string | null`. `export` — «этот тип можно импортировать из других файлов».

Создай **`app/composables/useCurrentUser.ts`**:

```ts
import type { User } from '~/types/user'

export function useCurrentUser() {
  return useState<User | null>('current-user', () => null)
}

export async function loadCurrentUser() {
  const currentUser = useCurrentUser()
  const requestFetch = useRequestFetch()
  try {
    currentUser.value = await requestFetch<User>('/api/auth/me')
  } catch {
    currentUser.value = null
  }
}
```

- Папка `composables/` особенная: всё, что экспортировано из её файлов, Nuxt **автоматически** делает доступным во всех компонентах, страницах и middleware. Импортировать `useCurrentUser` нигде не придётся.
- `~` — это папка `app/`. `~/types/user` — файл `app/types/user.ts`. `import type` — импорт только типа, в браузерный код он не попадёт.
- `useState<User | null>('current-user', () => null)` — общая переменная по ключу `'current-user'`: кто бы её ни вызвал, получит **ту же самую**. Стартовое значение — `null` («никто не вошёл»). Тип: пользователь или `null`.
- `loadCurrentUser` спрашивает `/api/auth/me`: 200 — запоминаем пользователя, 401 — запоминаем `null`.
- **`useRequestFetch()`** вместо `$fetch` — главная тонкость урока. На шаге 8 увидишь, зачем он нужен; а в разделе 10 — что будет без него.

В `login.vue` запомни пользователя после входа. Вверху script добавь:

```ts
import type { User } from '~/types/user'
```

и рядом с остальными переменными:

```ts
const currentUser = useCurrentUser()
```

А строку запроса поменяй так, чтобы ответ сохранялся:

```ts
    currentUser.value = await $fetch<User>('/api/auth/login', {
```

FastAPI в ответ на вход возвращает пользователя (`response_model=UserRead`) — сохраняем его, чтобы главная страница сразу знала имя.

Перепиши **`app/pages/index.vue`**:

```vue
<script setup lang="ts">
const currentUser = useCurrentUser()

async function onLogout() {
  await $fetch('/api/auth/logout', { method: 'POST' })
  currentUser.value = null
  await navigateTo('/login')
}
</script>

<template>
  <main>
    <h1>Привет, {{ currentUser?.name }}!</h1>
    <button @click="onLogout">Выйти</button>
  </main>
</template>
```

- `currentUser?.name` — «имя, если пользователь есть». Без `?.` при `null` шаблон упал бы с ошибкой.
- Выход: запрос на бэкенд (он удалит сессию и cookie), затем забываем пользователя у себя и уходим на `/login`.

**Проверь:** войди — на главной «Привет, Anna!». Нажми «Выйти» — попадаешь на `/login`, в Application → Cookies cookie `session` пропала. Теперь войди снова и нажми **F5** на главной.

> **Предскажи:** что будет написано после F5?
>
> <details><summary>Ответ</summary>
>
> «Привет, !» — без имени. Cookie на месте и сессия в базе жива, но `useState` после перезагрузки страницы начинается заново с `null`, а `/api/auth/me` пока никто не вызывает. Это и сделает охранник.
>
> </details>

### Шаг 8. Охранник — middleware

Создай **`app/middleware/auth.global.ts`**:

```ts
export default defineNuxtRouteMiddleware(async (to) => {
  const currentUser = useCurrentUser()
  if (currentUser.value === null) {
    await loadCurrentUser()
  }

  if (currentUser.value === null && to.path !== '/login') {
    return navigateTo('/login')
  }
  if (currentUser.value !== null && to.path === '/login') {
    return navigateTo('/')
  }
})
```

- Файлы в `app/middleware/` — функции, которые Nuxt вызывает **перед** открытием страницы. `.global` в имени файла значит «для всех страниц».
- `to` — куда человек идёт. `to.path` — путь: `'/'`, `'/login'`.
- Если мы ещё не знаем, кто вошёл, — спрашиваем бэкенд.
- Не вошёл и идёшь не на `/login` → на `/login`. Вошёл и идёшь на `/login` → на главную.
- `return navigateTo(...)` — **отменить** переход и отправить в другое место. Если функция ничего не вернула — переход разрешён.

**Проверь все пять сценариев из раздела 1:**

1. Выйди, затем открой `http://localhost:3000/` — оказываешься на `/login`.
2. Неверный пароль — «Неверный логин или пароль».
3. Верный — «Привет, Anna!».
4. **F5** — «Привет, Anna!» остаётся.
5. Открой руками `http://localhost:3000/login` — тебя возвращает на главную. «Выйти» — на `/login`, и на `/` больше не пускает.

> **Предскажи:** после F5 на главной страница сначала рендерится на Nuxt-сервере. Middleware — тоже на сервере. Откуда у Nuxt-сервера cookie, если её хранит браузер?
>
> <details><summary>Ответ</summary>
>
> Браузер приложил cookie к запросу **страницы** `GET /` на `localhost:3000`. Nuxt-сервер получил её в заголовках этого запроса. `useRequestFetch()` — это `$fetch`, который **пересылает заголовки текущего запроса страницы** (в том числе `Cookie`) дальше, в `/api/auth/me`. Обычный `$fetch` на сервере их не пересылает: он делает запрос «от себя», без cookie, и получает 401. В браузере разницы нет — там cookie прикладывает сам браузер.
>
> </details>

Страница входа готова. 🎉

## 9. Проследи один вход целиком

Возьми самый сложный сценарий — **F5 на главной, когда ты уже вошёл** — и пройди его по шагам. Если сможешь рассказать эту цепочку вслух, ты понимаешь урок.

```text
1. Браузер: GET http://localhost:3000/   Cookie: session=Qfeft5o...
2. Nuxt-сервер: какая страница? pages/index.vue. Перед ней — middleware auth.global.ts
3. middleware: useState('current-user') = null → loadCurrentUser()
4. useRequestFetch: GET /api/auth/me   Cookie: session=Qfeft5o...   (переслал cookie из шага 1)
5. routeRules proxy: GET http://127.0.0.1:8000/auth/me   Cookie: session=Qfeft5o...
6. FastAPI: get_current_user → hash_token("Qfeft5o...") → SELECT ... FROM user_sessions
            WHERE token_hash = '2982b2...' AND expires_at > now() → user_id = 1 → SELECT ... FROM users
7. FastAPI → 200 {"id": 1, "name": "Anna", ...}
8. middleware: currentUser = Anna, путь '/' → пропустить
9. Nuxt-сервер рендерит index.vue → HTML «Привет, Anna!» + состояние useState внутри страницы
10. Браузер показывает HTML, загружает JavaScript, гидратация: useState уже Anna (пришло с сервера),
```

Проверь это сам:

- Шаги 5–6: в `docker compose logs -f api` при F5 появляется строка `"GET /auth/me HTTP/1.1" 200 OK`.
- Шаг 9: F12 → Network → самый первый запрос (`localhost`) → **Response**. В HTML уже есть «Привет, Anna!» — браузер получил готовую страницу.
- Шаг 10: в Network при F5 нет отдельного запроса `me` от браузера: его сделал Nuxt-сервер.

> **Проверь себя.** А что происходит при нажатии «Войти» на `/login`? Распиши шаги в том же стиле. Где выполняется `onSubmit` — на сервере или в браузере? Кто ставит cookie?

>
> 1. Браузер: `onSubmit` (только в браузере) → `POST http://localhost:3000/api/auth/login` с JSON-телом.
> 2. Прокси Nuxt-сервера → `POST http://127.0.0.1:8000/auth/login`.

## 10. Правила, на которых ошибаются

### `$fetch` против `useRequestFetch` на сервере

Это главная ловушка урока. Попробуй её руками: в `useCurrentUser.ts` замени `await requestFetch<User>(...)` на `await $fetch<User>(...)`, войди и нажми F5 на главной с открытой вкладкой Network.

> **Предскажи, что увидишь.**
>
> <details><summary>Ответ</summary>
>
> Первый запрос `localhost` отвечает **302** с переходом на `/login`: на Nuxt-сервере `$fetch` спросил `/api/auth/me` **без cookie** и получил 401, и middleware решил, что ты не вошёл. Потом в браузере middleware на `/login` снова спрашивает `/api/auth/me` — уже с cookie, потому что запрос делает сам браузер, — получает Anna и перебрасывает на `/`. Итог: при каждом F5 мелькает страница входа, а в Network — лишняя пара переходов.
>
> </details>

Правило: **запросы, которые могут выполниться на Nuxt-сервере во время открытия страницы и которым нужна cookie, делай через `useRequestFetch()`** (или `useFetch` — он внутри делает так же). В обработчиках кнопок (`onSubmit`, `onLogout`) можно `$fetch`: они выполняются только в браузере.

Верни `requestFetch` обратно.

### Почему прокси, а не CORS

С CORS вход тоже можно сделать, но для cookie нужно, чтобы всё совпало сразу: `allow_credentials=True` в FastAPI, точный список origin без `*`, `credentials: 'include'` в каждом `$fetch`, а ещё фронтенд и API должны быть одним «сайтом» для `SameSite`. `localhost:3000` и `127.0.0.1:8000` — **разные** сайты (разные хосты), и cookie с `SameSite=Lax` в такие запросы браузер не положит. Прокси убирает весь этот класс ошибок: браузер видит один origin.

### `localhost` и `127.0.0.1` — разные адреса для cookie

Cookie привязана к хосту. Вошёл на `http://localhost:3000` — на `http://127.0.0.1:3000` ты не вошёл. Открывай сайт всегда по одному адресу: `http://localhost:3000`.

### Токен не в `localStorage`

В интернете много примеров «сохрани токен в `localStorage` и добавляй в заголовок». Так токен может прочитать любой скрипт на странице. Cookie с `HttpOnly` — недоступна скриптам, и прикладывать её руками не нужно.

### `ref` и `.value`

В `<script>` — `login.value`, в `<template>` — `login`. Частые ошибки: `login = 'anna'` в script (ты заменил саму коробку, а не значение — Vue об изменении не узнает) и `{{ login.value }}` в шаблоне (покажет пустоту).

### Забыл `.prevent`

Страница перезагружается при отправке, а в Network запрос `login` появляется с пометкой **(canceled)**. Всегда `@submit.prevent`.

### Охранник на фронтенде — не защита

Middleware решает, **что показать**. Защищает **данные** только бэкенд: любой может отправить запрос в API в обход Nuxt, через `curl`. Поэтому каждый эндпоинт с чужими данными должен требовать `CurrentUserDep` — проверять на фронтенде мало.

### Пароль не путешествует дальше, чем нужно

- Не в URL и не в query string — только в теле `POST`.
- Не в логах: никаких `print(data)`, `logger.info(data)`, `input_data=str(data)` для схем с паролем.
- Не в ответах: у каждого эндпоинта, возвращающего `User`, есть `response_model=UserRead`.
- Тонкость: ответ 422 от Pydantic содержит поле `input` с тем, что прислали, — в том числе слишком короткий пароль. Его видит только тот, кто его прислал, но если когда-нибудь будешь логировать ответы — помни об этом.

### Одна ошибка на «нет логина» и «неверный пароль»

И одинаковое время ответа (`DUMMY_HASH`). Иначе API подсказывает, какие логины существуют.

### Новый скрипт в `database/init` не выполнится сам

На существующем volume — только руками (раздел 7, шаг 1). Если забыть, при входе будет 500 и `column users.login does not exist` в логах API.

### Не закрывай сразу старые эндпоинты

Соблазнительно добавить `CurrentUserDep` во все эндпоинты. Но Telegram-бот ходит в API **без** cookie, и после этого `POST /create_receipt` перестанет у него работать. Для бота нужен свой способ входа (например, отдельный секретный токен сервиса в заголовке). Это отдельная задача, не часть этого урока.

## 11. Диагностика: сначала найди этап

Любая проблема со входом живёт на одном из этапов: **браузер → Nuxt → прокси → FastAPI → база**. Найди этап по признаку, потом чини.

| Признак | Этап | Что делать |
|---|---|---|
| `npm create nuxt` или `npm install`: `Cannot read properties of null (reading 'edgesOut')` | установка | Ошибка старой версии npm. Обнови: `npm install -g npm@latest` (или однократно `npx npm@11 install` в `frontend/`) |
| `git status` показывает `frontend` одной строкой, `git add` ругается на `embedded git repository` | установка | Мастер создал вложенный репозиторий. Удали папку `frontend/.git` |
| Любая страница Nuxt: 500 `Either manifest or precomputed data must be provided` (Windows) | запуск | Баг Nuxt 4.6.0 на Windows. Обнови Nuxt (`npm i nuxt@latest` в `frontend/`) или добавь в `nuxt.config.ts` блок `nitro: { externals: { inline: [/[\\/]node_modules[\\/]nuxt[\\/]dist[\\/]/] } }` и перезапусти `npm run dev` |
| `http://localhost:3000/api/users` — 404 от Nuxt | прокси | Нет `routeRules` или опечатка в `'/api/**'`. Перезапусти `npm run dev` после правки `nuxt.config.ts` |
| `/api/...` — 502 Bad Gateway | прокси → FastAPI | API не запущен (`docker compose ps`) или в `proxy` не тот адрес/порт. Проверь `http://127.0.0.1:8000/docs` напрямую |
| В Console `blocked by CORS policy` | браузер | Запрос идёт напрямую на `127.0.0.1:8000`, мимо прокси. Адрес в `$fetch` должен начинаться с `/api/` |
| `/api/auth/login` — 404 | FastAPI | Роутер не подключён в `main.py` или нет `prefix="/auth"` |
| `/api/auth/login` — 422 | FastAPI, схема | Посмотри Payload в Network: тело не JSON или нет поля. Частая причина — `body: login` вместо `body: { login: ..., password: ... }` |
| `/api/auth/login` — 500, в логах `column users.login does not exist` | база | Не выполнен `05_auth.sql` (раздел 7, шаг 1) |
| 500, в логах `can't compare offset-naive and offset-aware datetimes` | FastAPI | Где-то `datetime.now()` без `timezone.utc` |
| 500, в логах `ModuleNotFoundError: No module named 'pwdlib'` | Docker | Не пересобран образ после правки `requirements.txt`: `docker compose up -d --build api` |
| Правильный пароль, но 401 | FastAPI | Логин регистрировался с другим регистром или пробелом? Посмотри `SELECT login FROM payment_statistic.users` |
| Вход 200, но в Application → Cookies пусто | cookie | Сайт открыт по `http` не через `localhost` (по IP), а у cookie `Secure`. Проверь `APP_ENV` в `.env`: для локальной работы `dev` или переменной нет совсем |
| Вход 200, но `/api/auth/me` всё равно 401 | cookie | Сайт открыт как `127.0.0.1:3000`, а вошёл на `localhost:3000` (или наоборот). Или в `get_current_user` ищешь сам токен, а не его хеш |
| После F5 мелькает `/login` | SSR | `$fetch` вместо `useRequestFetch` в `loadCurrentUser` (раздел 10) |
| «Привет, !» без имени | состояние | Не сохраняешь ответ входа в `currentUser` или нет middleware |
| Страница перезагружается при «Войти», запрос `(canceled)` | форма | Нет `.prevent` у `@submit` |
| Страница не открывается, браузер пишет о слишком большом числе переадресаций | middleware | Условия не исключают `/login`: охранник перенаправляет с `/login` на `/login` |
| Красные подчёркивания в PyCharm, а `npx nuxi typecheck` чист | редактор | Редактор не подхватил типы Nuxt. Перезапусти Nuxt (`npm run dev` создаёт `.nuxt/`) и PyCharm. Источник правды — `nuxi typecheck` |

## 12. Тренировка: от простого к переносу навыка

### Уровень 1. С пустого листа

Удали (или переименуй) `pages/login.vue`, `middleware/auth.global.ts` и `composables/useCurrentUser.ts`. Напиши их заново **по памяти**, глядя только на «семь вопросов» из раздела 4. Подглядывать в урок можно, но каждое подглядывание запиши: это список того, что ещё не выучено.

### Уровень 2. Регистрация

Сделай страницу `/register`: поля логин, пароль, повтор пароля, имя, возраст. Отправляет `POST /api/auth/register`, при успехе — сразу входит (`POST /api/auth/login` с теми же данными) и переходит на `/`.

- Где проверить, что пароль и повтор совпадают — на фронтенде или на бэкенде?
- Что показать на 409 и на 422?
- Что поменять в middleware, чтобы на `/register` пускало без входа?

<details><summary>Подсказки</summary>

- Совпадение двух полей — проверка удобства, её делают на фронтенде до отправки: `if (password.value !== password2.value) { errorText.value = 'Пароли не совпадают'; return }`. На бэкенд повтор пароля не отправляют.
- 409 → «Такой логин уже занят». 422 → «Проверь поля: логин из латиницы, пароль от 8 символов».
- Возраст из `<input type="number" v-model.number="age">` — `.number` превращает строку в число.
- В middleware замени `to.path !== '/login'` на проверку по списку: `const publicPages = ['/login', '/register']` и `!publicPages.includes(to.path)`.
- На странице входа добавь ссылку: `<NuxtLink to="/register">Регистрация</NuxtLink>`. `NuxtLink` — ссылка, которая переходит без перезагрузки страницы.

</details>

### Уровень 3. Показать пароль

Добавь у поля пароля кнопку-глазик «показать»: она переключает `type` поля между `password` и `text`.

<details><summary>Подсказка</summary>

`const showPassword = ref(false)`, у поля — `:type="showPassword ? 'text' : 'password'"`, у кнопки — `type="button"` (иначе она отправит форму!) и `@click="showPassword = !showPassword"`.

</details>

### Уровень 4. Сломай специально

По одному: сломай, предскажи, что увидишь в браузере и в Network, проверь, верни.

1. Убери `httponly=True` в `set_cookie`, войди заново и набери в Console `document.cookie`.
2. Поставь `secure=True` и войди через `http://localhost:3000`. Сработает ли вход по `http`?
3. Поставь `SESSION_DAYS = 0`, войди и обнови страницу.
4. В `routeRules` поменяй порт на `8001`.
5. В `get_current_user` ищи `get_active(token)` вместо `get_active(hash_token(token))`.
6. Удали в psql все строки из `user_sessions` (`DELETE FROM payment_statistic.user_sessions;`) и обнови страницу в браузере.

<details><summary>Ответы</summary>

1. Видишь `session=...` — теперь сессию может прочитать любой скрипт на странице.
2. В Chrome и Firefox — сработает: для `localhost` они делают исключение. В Application → Cookies у `session` появится галочка **Secure**. Но открой тот же сайт по IP твоего компьютера с телефона — и вход перестанет работать: по `http` на обычном адресе браузер `Secure`-cookie не сохраняет. Верни как было.
3. Сессия создаётся уже просроченной: `get_active` её не находит → 401. Плюс `Max-Age=0` — браузер сразу удаляет cookie.
4. Любой `/api/...` — 502 Bad Gateway, вход показывает «Сервер не отвечает».
5. Вход вроде бы работает (имя на главной взято из ответа входа), но после F5 снова `/login`: `/auth/me` всегда 401, потому что в базе лежат хеши, а ищешь сам токен.
6. 401 и переход на `/login`. Так работает «выйти на всех устройствах» и выкинуть вора — уровень 6.

</details>

### Уровень 5. Профиль

Сделай страницу `/profile` с именем, возрастом и описанием текущего пользователя и ссылку на неё с главной. Данные бери из `useCurrentUser()` — запрос не нужен. Потом добавь кнопку «Сохранить описание»: новый эндпоинт `PUT /auth/me` на бэкенде принимает `{"description": "..."}` и меняет описание **текущего** пользователя (не по `user_id` из пути!).

<details><summary>Подсказка</summary>

Почему не существующий `PUT /users/update/{user_id}`: он меняет любого пользователя по id — кто угодно поменяет чужой профиль. Новый эндпоинт берёт пользователя из `CurrentUserDep`, поэтому меняет только себя. После ответа обнови `currentUser.value` тем, что вернул сервер.

</details>

### Уровень 6. Выйти на всех устройствах

Эндпоинт `POST /auth/logout-all`: удаляет **все** сессии текущего пользователя. Кнопка на главной. Проверь: войди в двух браузерах (или в обычном и в окне инкогнито), нажми кнопку в одном — во втором после F5 попадаешь на `/login`.

<details><summary>Подсказка</summary>

Метод в `UserSessionRepository`: `delete(UserSession).where(UserSession.user_id == user_id)` и `await self.session.execute(stmt)`. Импорт `delete` из `sqlalchemy`. Не забудь `commit`.

</details>

### Уровень 7. Защита от перебора

Сейчас пароль можно подбирать бесконечно. Сделай так, чтобы после 5 неудачных попыток входа для логина 15 минут любой вход отвечал 429 Too Many Requests.

- Где хранить счётчик неудач? Чем плохо хранить его в переменной Python?
- Что показать на фронтенде на 429?

<details><summary>Подсказка</summary>

Переменная Python обнуляется при каждом перезапуске Uvicorn (а `--reload` перезапускает его на каждое сохранение) и не общая у нескольких процессов. Храни в базе: таблица `login_attempts (login, created_at)`; при входе считай строки за последние 15 минут. При успешном входе удаляй попытки этого логина.

</details>

### Уровень 8. Перенос навыка: LDAP на бумаге

Кода не будет. Представь, что компания просит: «вход на этот сайт — по учётке Active Directory». Ответь письменно:

1. Какие части урока останутся без изменений?
2. Какая функция поменяется и что она будет делать вместо `verify_password`?
3. Нужна ли колонка `password_hash`? А таблица `users`?
4. Как сайт узнает, что сотрудника уволили?

<details><summary>Ответ</summary>

1. Почти всё: форма входа, прокси, cookie `HttpOnly`, таблица сессий, `get_current_user`, middleware, выход.
2. Поменяется проверка пароля в `login`: вместо `verify_password` — «LDAP bind» к контроллеру домена с логином и паролем (на Python, например, библиотекой `ldap3`, по защищённому LDAPS). Успех bind — пароль верный.
3. `password_hash` не нужна — хеш хранит AD. Таблица `users` нужна: в ней связь «логин AD → наш пользователь» и его данные (чеки). Обычно запись создают при первом входе.
4. Его учётку отключат в AD — новый bind не пройдёт. Но **уже выданные** сессии продолжат работать до истечения срока. Поэтому для корпоративных сайтов делают короткий срок сессии или периодически перепроверяют пользователя в каталоге.

</details>

### Самопроверка

<details><summary>1. Где на самом деле хранятся пароли, если «в LDAP»?</summary>В базе каталога (Active Directory — `NTDS.dit` на контроллерах домена), в виде хешей. LDAP — протокол, по которому приложение спрашивает каталог «правильный ли пароль», а не «место без базы».</details>

<details><summary>2. Чем хеш отличается от шифрования?</summary>Шифрование обратимо ключом, хеш — нет. Для паролей нужен необратимый медленный хеш с солью.</details>

<details><summary>3. Почему в cookie лежит токен, а в базе — его хеш?</summary>Чтобы утечка базы не дала готовых рабочих сессий. Сервер хеширует пришедший токен и ищет хеш.</details>

<details><summary>4. Что даёт <code>HttpOnly</code>? А <code>SameSite=Lax</code>?</summary><code>HttpOnly</code> — JavaScript страницы не видит cookie. <code>SameSite=Lax</code> — браузер не прикладывает cookie к запросам, которые к твоему сайту делает чужой сайт (кроме обычного перехода по ссылке).</details>

<details><summary>5. Зачем прокси <code>/api</code>?</summary>Чтобы для браузера фронтенд и API были одним origin: нет CORS, cookie работает без дополнительных настроек.</details>

<details><summary>6. Когда нужен <code>useRequestFetch</code>, а когда хватит <code>$fetch</code>?</summary><code>useRequestFetch</code> — когда запрос может выполниться на Nuxt-сервере при открытии страницы и ему нужна cookie пользователя (middleware, setup страницы). <code>$fetch</code> — в обработчиках кнопок, они работают только в браузере.</details>

<details><summary>7. Почему middleware — не защита данных?</summary>Он работает на фронтенде, который можно обойти, отправив запрос в API напрямую. Защищает бэкенд: <code>CurrentUserDep</code> в эндпоинте.</details>

<details><summary>8. Чем сессия в базе лучше JWT для нашего сайта?</summary>Выход и отзыв работают мгновенно — удалили строку. JWT действует до истечения срока, и отозвать его сложно.</details>

```python
from pwdlib import PasswordHash
hasher = PasswordHash.recommended()        # argon2id
h = hasher.hash("пароль")                  # "$argon2id$v=19$..." — в базу
hasher.verify("пароль", h)                 # True / False

import secrets, hashlib
token = secrets.token_urlsafe(32)          # в cookie
hashlib.sha256(token.encode()).hexdigest() # в базу
```
