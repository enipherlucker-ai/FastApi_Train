# Домен, сайт на сервере и SSH-туннель к базе — для чайников 😄

**Цель урока.** Сейчас на сервере работают API, база и бот, а страница входа на Nuxt есть только у тебя на компьютере. После урока:

1. У проекта есть адрес `https://cometa-analytics.com` с замком в адресной строке.
2. По этому адресу открывается твоя страница входа, и вход работает.
3. Ты открываешь боевую базу в PyCharm или DBeaver и смотришь таблицы, но база при этом **не открыта** в интернет.

Урок написан по коду, который лежит в ветке `dev`. Каждый шаг устроен одинаково:

- **Файл** — какой файл открыть.
- **Сейчас там** — что в нём написано сейчас (скопировано из `dev`).
- **Что не так** — что плохого случится, если оставить как есть. Не «так принято», а конкретная история.
- **Что сделать** — что поменять.
- **Как проверить** — что запустить и что должно получиться.
- **Ответ** — готовый код в свёрнутом блоке. Открывай его только после своей попытки.

**Готового кода в репозитории нет.** Всё пишешь ты. Весь код из ответов я собрал и проверил у себя 24.10.2026: сборка Nuxt 4.6 в Docker, Caddy 2, PostgreSQL 18, вход через HTTPS, коды ошибок, workflow через `actionlint`, туннель к базе.

## 0. Как проходить урок

1. **Печатай руками**, не копируй.
2. **Одна правка — одна проверка.** Поправил файл — проверил. Не делай пять правок подряд: если что-то сломается, не поймёшь, какая виновата.
3. **Сначала предскажи, потом запусти.** Перед проверкой скажи себе, что должно получиться. Если получилось другое — это самое ценное место урока, разберись.
4. **Коммить по одной правке.** Все правки — в ветку `dev`. На каждый push в `dev` GitHub Actions проверит код (`lint` и `build`), но на сервер ничего не выкатит: выкатка запускается только из `main`.

План:

| Раздел | Что делаем | Где |
|---|---|---|
| 1 | Карта: что есть сейчас и что будет в конце | читаем |
| 2 | Шаг ноль: проверки, которые ничего не меняют | твой компьютер |
| 3 | Домен и DNS: что ты уже сделал и почему это работает | кабинет Beget |
| 4 | Доводим вход до состояния «можно в интернет» | `app/`, `frontend/` |
| 5 | Nuxt в Docker | `frontend/Dockerfile` |
| 6 | Сервер: сайт, HTTPS и порт базы | `deploy/` |
| 7 | CI/CD: третий образ | `.github/workflows/ci-cd.yml` |
| 8 | Выкатка и первый пользователь | сервер |
| 9 | SSH-туннель к базе | сервер + PyCharm/DBeaver |
| 10–15 | Ловушки, диагностика, тренировка, повторение, шпаргалка, источники | |

Нормально проходить за 3–4 вечера.

### 1.3. Словарь

| Слово | Что значит |
|---|---|
| **Домен** | Имя вроде `cometa-analytics.com`. Его не покупают навсегда, а арендуют на год и продлевают. |
| **Регистратор** | Компания, у которой арендован домен. У тебя это Beget. |
| **DNS** | «Телефонная книга» интернета: по имени находит IP-адрес сервера. |
| **A-запись** | Строка в этой книге: «имя → IPv4-адрес». |
| **TTL** | Сколько секунд другие компьютеры могут помнить ответ DNS, прежде чем спросить снова. |
| **HTTPS** | HTTP, зашифрованный так, что посторонние в сети (провайдер, кафе с Wi-Fi) не видят пароль и cookie. |
| **Сертификат** | «Паспорт» сайта: доказывает браузеру, что сервер правда `cometa-analytics.com`. Без него нет HTTPS. Бесплатно выдаёт Let's Encrypt. |
| **Caddy** | Программа, которая стоит перед сайтом: принимает HTTPS, сама получает и продлевает сертификат и передаёт запросы дальше в Nuxt. |
| **Прокси** | Посредник: принимает запрос и пересылает его дальше. Caddy — прокси перед Nuxt, а Nuxt — прокси перед API. |
| **Порт** | Номер «двери» на компьютере. Одна программа слушает одну дверь: Postgres — 5432, API — 8000, Nuxt — 3000, HTTPS — 443. |
| **`127.0.0.1`** | «Этот же компьютер». Порт на `127.0.0.1` доступен только программам на этом же компьютере, из интернета — нет. |
| **SSH-туннель** | Труба внутри SSH-соединения: программа на твоём компьютере стучится в свою дверь, а попадает в дверь на сервере. |

## 2. Шаг ноль: проверки, которые ничего не меняют

### 2.1. Файл настроек SSH

Чтобы не писать каждый раз `ssh jenifer@cometa-analytics.com`, в файле `C:\Users\Jenifer\.ssh\config` заводят короткое имя. Важно, чтобы файл назывался **ровно** `config`, без `.txt`. Блокнот любит молча дописывать `.txt`, а Проводник по умолчанию скрывает расширения, и ты этого не увидишь.

Надёжный способ в PowerShell:

```powershell
New-Item -ItemType File -Force $HOME\.ssh\config
notepad $HOME\.ssh\config
```

Первая команда создаёт пустой файл с правильным именем, вторая открывает именно его. Напиши внутри:

```text
Host fastapi
    HostName cometa-analytics.com
    User jenifer
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 30
    ServerAliveCountMax 3
```

Сохрани и проверь:

```powershell
Get-ChildItem $HOME\.ssh
ssh -G fastapi | Select-String "^hostname|^user "
ssh fastapi
```

| Строка конфига | Что значит |
|---|---|
| `Host fastapi` | Короткое имя, которое ты пишешь в `ssh fastapi`. Придумываешь сам. |
| `HostName` | Настоящий адрес сервера. |
| `User` | Под каким пользователем входить. |
| `IdentityFile` | Каким ключом. `~` — твоя домашняя папка. |
| `ServerAliveInterval 30` | Раз в 30 секунд слать серверу «я жив». Без этого роутер обрывает тихое соединение, и туннель к базе «умирает» через несколько минут без дела. |
| `ServerAliveCountMax 3` | Если сервер не ответил 3 раза подряд — считать соединение разорванным. |

<details><summary>Что должно получиться и что делать, если нет</summary>

- `Get-ChildItem` показывает файл `config` **без** расширения. Если видишь `config.txt` — переименуй: `Rename-Item $HOME\.ssh\config.txt config`.
- `ssh -G fastapi` печатает настройки, которые ssh реально применит. Должно быть `hostname cometa-analytics.com` и `user jenifer`. Если там `hostname fastapi`, ssh не прочитал твой файл (неправильное имя или не та папка).
- `ssh fastapi` пускает на сервер.

Если в ошибке написано `connect to host fastapi port 22`, ssh пытается соединиться с компьютером, который буквально называется `fastapi`. Значит, файл не прочитан.

Если файл создавался в PowerShell через `echo ... > config`, он записан в кодировке UTF-16, и ssh его не поймёт (`Bad configuration option` или пустые настройки). Пересоздай через `New-Item` и Блокнот.

При первом входе по имени ssh спросит `Are you sure you want to continue connecting`. Для него `cometa-analytics.com` — новое имя, хотя сервер тот же. Отвечай `yes`.
</details>

### 2.2. Первый туннель: Swagger боевого API

На сервере API слушает только `127.0.0.1:8000`, из интернета его не видно. Проверь это сам, в PowerShell:

```powershell
Test-NetConnection cometa-analytics.com -Port 8000
```

Предскажи ответ до запуска.

<details><summary>Ответ</summary>

`TcpTestSucceeded : False`. Дверь 8000 на сервере открыта только для самого сервера.
</details>

Теперь открой туннель:

```powershell
ssh -N -L 18000:127.0.0.1:8000 fastapi
```

Окно «зависнет» без вывода. Так и должно быть: туннель работает, пока окно открыто. Открой в браузере `http://127.0.0.1:18000/docs` — это Swagger **боевого** API. Закрой туннель через `Ctrl+C` и обнови страницу: она перестанет открываться.

Разберём команду по кусочкам:

| Кусочек | Что значит |
|---|---|
| `ssh ... fastapi` | Обычный вход на сервер. |
| `-N` | «Не открывай мне командную строку сервера, мне нужен только туннель». |
| `-L` | **L**ocal: дверь открывается на **моём** компьютере. |
| `18000` | Номер двери на твоём компьютере. Любой свободный. |
| `127.0.0.1:8000` | Куда сервер передаст всё, что пришло в трубу. Адрес **с точки зрения сервера**: для сервера `127.0.0.1` — он сам, а на нём API. |

```text
браузер ──► 127.0.0.1:18000 (твой компьютер)
               ║ SSH, порт 22, всё зашифровано
               ▼
            сервер ──► 127.0.0.1:8000 (API)
```

> ⚠️ В этом Swagger вызывай только `GET`. Это настоящая база.

### 2.3. Собранный сайт у себя

Дома ты запускаешь Nuxt командой `npm run dev`. Это **режим разработки**: правишь файл — страница сама обновляется, ошибки подробные. На сервере будет **собранный** сайт: Nuxt один раз превращает твои `.vue` и `.ts` файлы в готовые файлы в папке `.output`, и дальше работает только она.

Посмотри на собранный сайт у себя. Сначала запусти бэкенд (`docker compose up -d` в корне проекта), потом в папке `frontend`:

```powershell
npm run build
node .output/server/index.mjs
```

Открой `http://localhost:3000/login` и войди. Всё работает так же, как в `npm run dev`. Останови через `Ctrl+C`.

<details><summary>Чем собранный сайт отличается от npm run dev</summary>

- Поменял файл — ничего не изменится, нужно снова `npm run build`.
- Ошибки короткие, без подробностей: посторонним незачем видеть устройство твоего кода.
- Всё из `nuxt.config.ts` (в том числе адрес API, раздел 4.7) **запекается** в `.output` при сборке. Поменять потом без пересборки нельзя.

Поэтому «работает в `npm run dev`» ещё не значит «работает на сервере». Перед выкаткой всегда проверяй собранный сайт.
</details>

## 3. Домен и DNS

Ты уже купил `cometa-analytics.com` у Beget и настроил записи. Этот раздел объясняет, что именно ты сделал, почему так, и как проверить. Если когда-нибудь будешь покупать второй домен — здесь же чек-лист.

### 3.1. Как браузер находит сервер по имени

Когда ты вводишь `cometa-analytics.com`:

1. Компьютер спрашивает DNS-сервер (провайдера или `1.1.1.1`): «какой IP у `cometa-analytics.com`?»
2. Тот по цепочке выясняет, что записи этого домена хранит Beget, и спрашивает у Beget.
3. Beget отвечает: «A-запись = IP твоего сервера, TTL 600».
4. Ответ запоминается на 600 секунд (10 минут), браузер идёт на этот IP, на порт 443.

### 3.2. Что ты сделал в панели DNS и почему

| Запись | Что было | Что стало | Почему |
|---|---|---|---|
| `cometa-analytics.com` A | IP Beget и IP твоего сервера | только IP твоего сервера | При двух A-записях браузер выбирает **случайную**. Половина посетителей попадала бы на заглушку Beget. А Let's Encrypt, проверяя домен, через раз попадал бы не на твой сервер, и сертификат не выдавался бы. |
| `www.cometa-analytics.com` A | IP Beget | IP твоего сервера | Люди по привычке пишут `www.`. Caddy будет перенаправлять `www` на адрес без `www` (6.3), но для этого запрос должен дойти до твоего сервера. |
| MX, TXT, `autoconfig`, `autodiscover` | — | как было | Это почта на Beget. Сайту они не мешают и не помогают. Удаляй, только если точно не будешь заводить почту `@cometa-analytics.com` у Beget. |
| AAAA | не было | не было | AAAA — адрес в формате IPv6. Если её добавить, а сервер по IPv6 не отвечает, часть посетителей не откроет сайт, а Let's Encrypt (он проверяет сначала IPv6) не выдаст сертификат. Без уверенности — без AAAA. |

### 3.3. Проверка

В PowerShell:

```powershell
Resolve-DnsName cometa-analytics.com -Server 1.1.1.1
Resolve-DnsName www.cometa-analytics.com -Server 8.8.8.8
Resolve-DnsName cometa-analytics.com -Type AAAA -Server 1.1.1.1
```

<details><summary>Что должно быть</summary>

- Первые две команды: ровно **одна** строка `A` с IP твоего сервера. Ты это уже получил.
- Третья: записи `AAAA` нет (будет ответ про `SOA` или пусто).

`-Server 1.1.1.1` и `-Server 8.8.8.8` — спросить конкретные публичные DNS-серверы (Cloudflare и Google), а не свой роутер. Так видно, что новая запись дошла до всего интернета, а не только до тебя. Если два сервера отвечают по-разному — подожди TTL, и ответы сравняются.

Если у тебя открывается старый адрес, а `Resolve-DnsName -Server 1.1.1.1` уже показывает новый — это кеш Windows. Сбрось: `ipconfig /flushdns`.
</details>

### 3.5. Если будешь покупать ещё один домен

Коротко, что важно знать в России в 2026 году:

- **Зона `.com` (как у тебя)** не требует ничего, кроме оплаты.
- **Зоны `.ru`, `.рф`, `.su`**: с 1 сентября 2026 года действует закон № 569-ФЗ. Владелец домена подтверждает личность через Госуслуги в кабинете регистратора. Без этого новый домен не зарегистрируют. Для тех, кто не успел, переходный период до 18 января 2027 года.
- Сравнивай регистраторов по цене **продления**, а не первого года: в мае 2026 года продление `.ru` стоило от ~320 ₽ до 1200 ₽ и дороже у разных регистраторов.
- Оплата картой МИР и по СБП принимается у российских регистраторов почти всегда. У зарубежных (Namecheap, Porkbun, Cloudflare) российская карта не пройдёт.

## 4. Доводим вход до состояния «можно в интернет»

Дома вход работает. Но в интернете к форме придёшь не только ты. Придут боты: они перебирают пароли, присылают мусор и ищут ошибки. Каждый пункт ниже закрывает одну конкретную дыру.

Как проверять в этом разделе: дома запущен бэкенд (`docker compose up -d` в корне проекта; благодаря `--reload` в `compose.yaml` правки в `app/` подхватываются сами) и Nuxt (`npm run dev` в `frontend`). Swagger дома: `http://127.0.0.1:8000/docs`.

### 4.1. Длина логина и пароля при входе

**Файл:** `app/schemas/auth.py`

**Сейчас там:**

```python
Login = Annotated[str, Field(min_length=3, max_length=50, pattern=r"^[a-zA-Z0-9_.-]+$", examples=["anna"])]
Password = Annotated[str, Field(min_length=8, max_length=128, examples=["correct-horse-42"])]


class RegisterIn(UserBase):
    login: Login
    password: Password


class LoginIn(BaseModel):
    login: str
    password: str
```

Посмотри внимательно, где здесь ограничения и **кому** они достаются.

- `Login` и `Password` — это не поля, а **типы**: «строка от 3 до 50 символов» и «строка от 8 до 128 символов». Сами по себе они ничего не проверяют. Проверка срабатывает только там, где поле объявлено с этим типом.
- В `RegisterIn` поля объявлены как `login: Login` и `password: Password`. Значит, при **регистрации** ограничения работают.
- В `LoginIn` поля объявлены как `login: str` и `password: str` — просто строка, **любой** длины. `/auth/login` использует именно `LoginIn`. Значит, при **входе** ограничений нет.

<details><summary>Проверь сам, что при входе ограничений нет</summary>

В Swagger открой `POST /auth/login`, нажми **Try it out** и отправь:

```json
{"login": "a", "password": "b"}
```

Ответ — `401 wrong user or password`, а не `422`. Если бы ограничения работали, логин из одной буквы не прошёл бы проверку `min_length=3`, и ответ был бы `422`. То же самое с паролем из 1000 символов: `401`, а не `422`.
</details>

**Что не так.** Пароли хранятся как хеши argon2. Argon2 — **специально медленная** функция: на одну проверку пароля уходит заметное время процессора и десятки мегабайт памяти. Так сделано нарочно, чтобы украденные хеши было долго перебирать. Но у этого есть обратная сторона. Смотри, что делает `login()` в `app/api/auth.py`:

```python
    user = await users.get_by_login(data.login)
    stored_hash = user.password_hash if user is not None else DUMMY_HASH
    if not verify_password(data.password, stored_hash) or user is None:
```

Пароль проверяется **всегда**, даже если такого пользователя нет (тогда с `DUMMY_HASH`). Это правильно, иначе по времени ответа можно было бы узнать, какие логины существуют. Но значит, бот может без всякого логина присылать пароли по несколько мегабайт, и каждый такой запрос заставит сервер честно считать argon2. Сотня запросов одновременно — и два ядра твоего сервера заняты только этим, сайт и бот не отвечают. Это называется **отказ в обслуживании** (DoS).

Ограничение длины проверяет Pydantic **до** того, как запрос дойдёт до функции `login()`. Слишком длинный пароль получит `422` мгновенно, без argon2.

**Что сделать.** Дай полям `LoginIn` ограничение **только по максимальной длине**: логин до 50 символов, пароль до 128. Так же, как в `Login` и `Password`, через `Field(max_length=...)`.

<details><summary>Почему только max_length, без min_length и pattern?</summary>

- `min_length` при входе ничего не защищает: короткий пароль просто не совпадёт с хешем, и человек получит обычный `401`.
- `pattern` и `min_length` у логина при входе даже вредны для понятности: человек с опечаткой в логине получил бы `422` вместо «неверный логин или пароль».
- `max_length` защищает сервер: отсекает огромные строки до argon2.

Можно было бы написать `login: Login`, но тогда при входе заработали бы и `min_length`, и `pattern` — см. выше.
</details>

**Как проверить.** Сохрани файл (API перезапустится сам) и в Swagger:

1. `POST /auth/login` с паролем из 200 символов → `422`.
2. С неправильным паролем нормальной длины → `401`.
3. С правильным → `200`.

<details><summary>Ответ</summary>

```python
class LoginIn(BaseModel):
    login: str = Field(max_length=50)
    password: str = Field(max_length=128)
```

`Field` уже импортирован в начале файла. Проверено: пароль из 300 символов → `422`, неправильный → `401`, правильный → `200`.
</details>

Коммит: `git add app/schemas/auth.py`, `git commit -m "Вход: ограничение длины логина и пароля"`.

### 4.2. Пользователь с логином, но без пароля

**Файл:** `app/api/auth.py`, функция `login()`

**Сейчас там:**

```python
    user = await users.get_by_login(data.login)
    stored_hash = user.password_hash if user is not None else DUMMY_HASH
    if not verify_password(data.password, stored_hash) or user is None:
        raise HTTPException(status_code=401, detail="wrong user or password")
```

**Что не так.** Посмотри на `database/init/02_table_users.sql`: колонки `login` и `password_hash` могут быть `NULL` (у них нет `NOT NULL`). Представь пользователя, у которого `login` заполнен, а `password_hash` пустой. Такое бывает: например, ты руками в базе поставил логин админу, а пароль забыл.

Пройди по коду для такого пользователя:

1. `users.get_by_login(...)` находит его, `user` не `None`.
2. `stored_hash = user.password_hash` → `None`.
3. `verify_password(data.password, None)` — библиотека `pwdlib` падает с ошибкой `TypeError: hash must be str or bytes` (проверено).
4. Ошибку никто не ловит → FastAPI отвечает `500 Internal Server Error`.

Две проблемы. Первая: на странице человек увидит «Сервер не отвечает» вместо «неверный логин или пароль». Вторая, важнее: для несуществующего логина ответ `401`, а для этого — `500`. По разнице посторонний узнаёт, что такой логин **существует**.

**Что сделать.** Пользователь без хеша должен вести себя так же, как несуществующий: проверка с `DUMMY_HASH` (чтобы время ответа было тем же) и `401`.

Подсказка: заведи переменную `has_password`, которая равна `True`, только если пользователь найден **и** хеш у него не `None`. Используй её в обеих строках вместо `user is not None` и `user is None`.

**Как проверить.**

1. Поставь админу логин без пароля:

   ```powershell
   docker compose exec pg_database psql -U <твой_POSTGRES_SETTINGS__USER> -d <твоя_база> -c "update payment_statistic.users set login = 'nohash' where id = 20260308"
   ```

   Имя пользователя и базы возьми из своего `.env` (`POSTGRES_SETTINGS__USER`, `POSTGRES_SETTINGS__DATABASE`).

2. **До правки:** в Swagger `POST /auth/login` с `{"login": "nohash", "password": "что-угодно"}` → `500`, в `docker compose logs api` трейсбек с `TypeError`.
3. **После правки:** то же самое → `401`, трейсбека нет.
4. Верни как было: `... -c "update payment_statistic.users set login = NULL where id = 20260308"`.

<details><summary>Ответ</summary>

```python
    user = await users.get_by_login(data.login)
    has_password = user is not None and user.password_hash is not None
    stored_hash = user.password_hash if has_password else DUMMY_HASH
    if not verify_password(data.password, stored_hash) or not has_password:
        raise HTTPException(status_code=401, detail="wrong user or password")
```

Проверено: `nohash` → `401`. `ruff check app bot` проходит.
</details>

Коммит: `"Вход: 401 для пользователя без пароля"`.

### 4.3. Понятные сообщения об ошибках на странице входа

**Файл:** `frontend/app/pages/login.vue`, функция `onSubmit`

**Сейчас там:**

```ts
  try {
    currentUser.value = await $fetch<User>('/api/auth/login', {
      method: 'POST',
      body: {login: login.value, password: password.value},
    })
    await navigateTo('/')
  } catch (error) {
    const status = (error as {statusCode?: number}).statusCode
    if (status === 401) {
      errorText.value = 'Неверный логин или пароль'
    } else {
      errorText.value = 'Сервер не отвечает'
    }
  }
```

Сначала разберём, что здесь вообще происходит.

- `$fetch(...)` отправляет запрос. Если сервер ответил кодом 200–299, `$fetch` возвращает тело ответа. Если код 400 и выше **или** ответа нет вовсе, `$fetch` **выбрасывает ошибку**, и выполнение прыгает в `catch`.
- В `catch` попадает объект ошибки. У него есть поле `statusCode` — код ответа сервера. Если сервер вообще не ответил (у человека пропал интернет), поля нет, и `status` равен `undefined`.
- `(error as {statusCode?: number})` — подсказка для TypeScript: «считай, что у этого объекта может быть поле `statusCode` с числом». На работу программы не влияет, только на проверку типов.

**Что не так.** Всё, что не `401`, превращается в «Сервер не отвечает». Но причины бывают очень разные, и человеку нужно делать разное:

| Что случилось | Кто ответил и каким кодом | Что делать человеку |
|---|---|---|
| Неверный логин или пароль | API: `401` (это твой `raise HTTPException(status_code=401, ...)`) | проверить ввод |
| Пароль длиннее 128 символов (после 4.1) | API: `422` (это Pydantic отклонил `LoginIn`) | ввести короче |
| API лежит (перезапускается при деплое, упал) | Nuxt: `502 Bad Gateway`. Nuxt пытался переслать запрос в API, а там никого нет | подождать |
| Ошибка в коде API | API: `500` | ничего, это твоя проблема |
| У человека пропал интернет | никто, ответа нет: `statusCode` = `undefined` | проверить Wi-Fi |

`502` — не выдумка, это проверено: и в `npm run dev`, и в собранном сайте при остановленном API вход отвечает `502`.

**Посмотри сам, как это выглядит.** Это важный навык: все ответы сервера видны в браузере.

1. Открой `http://localhost:3000/login`, нажми **F12**, вкладка **Network**.
2. Введи неправильный пароль, нажми «Войти». В списке появится строка `login`. Колонка **Status** — `401`. Кликни по строке → вкладка **Response**: `{"detail":"wrong user or password"}`.
3. Останови API: `docker compose stop api`. Снова «Войти». Status — `502`. На странице — «Сервер не отвечает».
4. Запусти API обратно: `docker compose start api`.

**Что сделать.**

1. В `catch` разбери все строки таблицы: `401`, `422`, `502` и `503` (одно сообщение на оба), `undefined`, и «всё остальное». Для «всего остального» покажи код в тексте, например `Что-то сломалось на сервере (код 500)`: тогда по скриншоту от пользователя ты сразу поймёшь, что случилось.
2. Перед отправкой убирай пробелы по краям **логина**: `login.value.trim()`. Телефоны любят дописывать пробел после автоподстановки, и человек не понимает, почему «неверный логин». Пароль **не трогай**: пробел в пароле может быть настоящим.

<details><summary>Подсказка: как написать «если ... иначе если ... иначе»</summary>

```ts
if (status === 401) {
  // ...
} else if (status === 422) {
  // ...
} else if (status === 502 || status === 503) {
  // ...
} else if (status === undefined) {
  // ...
} else {
  // ...
}
```

`||` значит «или». Строку с кодом внутри удобно собирать через обратные кавычки: `` `код ${status}` `` — на место `${status}` подставится число.
</details>

**Как проверить.** Каждую строку таблицы:

| Как вызвать | Что должно появиться |
|---|---|
| Неправильный пароль | «Неверный логин или пароль» |
| Пароль из 200 символов (вставь в поле длинную строку) | «Слишком длинный логин или пароль» |
| `docker compose stop api`, потом «Войти» | «Сервер не отвечает, попробуй позже» |
| F12 → Network → выпадающий список **No throttling** → **Offline**, потом «Войти» | «Нет связи. Проверь интернет» |

После проверки верни **No throttling** и `docker compose start api`.

<details><summary>Ответ</summary>

```ts
  try {
    currentUser.value = await $fetch<User>('/api/auth/login', {
      method: 'POST',
      body: {login: login.value.trim(), password: password.value},
    })
    await navigateTo('/')
  } catch (error) {
    const status = (error as {statusCode?: number}).statusCode
    if (status === 401) {
      errorText.value = 'Неверный логин или пароль'
    } else if (status === 422) {
      errorText.value = 'Слишком длинный логин или пароль'
    } else if (status === 502 || status === 503) {
      errorText.value = 'Сервер не отвечает, попробуй позже'
    } else if (status === undefined) {
      errorText.value = 'Нет связи. Проверь интернет'
    } else {
      errorText.value = `Что-то сломалось на сервере (код ${status})`
    }
  } finally {
    loading.value = false
  }
```
</details>

Коммит: `"Страница входа: сообщения для каждой ошибки"`.

### 4.4. Кнопка «Выйти», когда сервер не ответил

**Файл:** `frontend/app/pages/index.vue`

**Сейчас там:**

```ts
async function onLogout(){
  await $fetch('/api/auth/logout', {method: 'POST'})
  currentUser.value = null
  await navigateTo('/login')
}
```

**Что не так.** Если API в этот момент лежит (например, идёт деплой), `$fetch` выбросит ошибку. `try`/`catch` здесь нет, поэтому функция просто оборвётся на первой строке. На экране ничего не произойдёт, и человек будет жать «Выйти» снова и снова, не понимая, что происходит. Ошибка уйдёт только в консоль браузера (F12 → Console), которую обычный человек не открывает.

<details><summary>Вопрос. А почему бы при ошибке всё равно не очистить currentUser и не перейти на /login?</summary>

Потому что сервер не подтвердил выход, а значит, cookie сессии осталась и сессия в базе жива. Дальше:

1. Ты переходишь на `/login`.
2. Срабатывает `auth.global.ts`: `currentUser` пустой → вызывает `loadCurrentUser()` → `/api/auth/me` (API уже поднялся) → cookie действует → пользователь найден.
3. Middleware видит: пользователь вошёл и пришёл на `/login` → `navigateTo('/')`.

Человек нажал «Выйти» и оказался на главной, всё ещё вошедшим. Это путает сильнее, чем честное «не получилось». Правило: **страница не должна показывать результат, которого сервер не подтвердил.**
</details>

**Что сделать.**

1. Заведи `const logoutError = ref('')`.
2. Оберни `$fetch` в `try`/`catch`. В `catch` запиши в `logoutError` текст «Не получилось выйти, попробуй ещё раз» и выйди из функции (`return`), **не** трогая `currentUser`.
3. В шаблоне покажи `logoutError`, если он не пустой (`v-if`), так же, как `errorText` на странице входа.
4. В начале `onLogout` очищай `logoutError`, чтобы старое сообщение не висело после успешной попытки.

**Как проверить.** Войди, `docker compose stop api`, нажми «Выйти» → сообщение, ты остался на главной. `docker compose start api`, снова «Выйти» → сообщение пропало, ты на `/login`.

<details><summary>Ответ</summary>

```vue
<script setup lang="ts">
const currentUser = useCurrentUser()
const logoutError = ref('')

async function onLogout() {
  logoutError.value = ''
  try {
    await $fetch('/api/auth/logout', {method: 'POST'})
  } catch {
    logoutError.value = 'Не получилось выйти, попробуй ещё раз'
    return
  }
  currentUser.value = null
  await navigateTo('/login')
}
</script>

<template>
  <main>
    <h1>Привет, {{ currentUser?.name }}!</h1>
    <p v-if="logoutError">{{ logoutError }}</p>
    <button @click="onLogout">Выйти</button>
  </main>
</template>
```

`catch` без `(error)` — когда сама ошибка не нужна, её можно не называть.
</details>

Коммит: `"Главная: сообщение, если выйти не получилось"`.

### 4.7. Белый список: что сайт пересылает в API

Это самый важный пункт раздела.

**Файл:** `frontend/nuxt.config.ts`

**Сейчас там:**

```ts
  routeRules: {
    '/api/**': { proxy: 'http://127.0.0.1:8000/**' },
  },
```

Что это значит: «любой запрос, который начинается с `/api/`, перешли в API на `127.0.0.1:8000`, отрезав `/api`». `**` — «что угодно дальше». Браузер просит у Nuxt `/api/auth/login`, Nuxt пересылает в API `/auth/login`. Так браузер общается только с Nuxt, и cookie работает без сложностей.

**Что не так — на сервере.** Сайт будет открыт всему интернету. С правилом `/api/**` через сайт станет доступно **всё**, что умеет API, а не только вход. Открой у себя `app/api/user.py` и `app/api/receipt.py`: там эндпоинты без проверки входа (их вызывает бот, у которого нет cookie). Значит, любой человек сможет:

- `/api/auth/register` — завести себе пользователя и войти на твой сайт;
- `/api/users...` — читать и менять пользователей;
- `/api/create_receipt` — добавлять чеки в твою базу, и каждый такой запрос тратит твои деньги на OpenAI и сервис проверки чеков;
- `/api/docs` — получить подробную карту всего перечисленного.

**Что сделать.** Заменить «всё подряд» на **белый список** — три точных пути, которые нужны страницам: `login`, `logout`, `me`. Всё остальное API остаётся доступным только внутри сервера (для бота). Если когда-нибудь понадобится новый эндпоинт на сайте, ты допишешь его сюда осознанно (и закроешь входом).

И вторая проблема: адрес `127.0.0.1:8000`. Дома он правильный. Но на сервере Nuxt будет работать **в своём Docker-контейнере**, а для контейнера `127.0.0.1` — это он сам, а не API. Внутри Docker-сети API доступен по имени сервиса: `http://api:8000`. Поэтому адрес нужно сделать настраиваемым: брать из переменной окружения `API_PROXY_TARGET`, а если её нет — `http://127.0.0.1:8000`, как дома.

Подсказки:

- В самом начале файла, **перед** `export default`, заведи константу: `const apiTarget = process.env.API_PROXY_TARGET ?? 'http://127.0.0.1:8000'`. `process.env.X` — переменная окружения `X`. `??` — «если слева пусто (`undefined`), возьми справа».
- В `routeRules` три правила вида `'/api/auth/login': { proxy: \`${apiTarget}/auth/login\` }`. Обрати внимание на обратные кавычки: внутри них `${apiTarget}` заменится значением константы.

<details><summary>Почему адрес «запекается» при сборке, и что из этого следует</summary>

`routeRules` читаются во время `npm run build` и записываются внутрь готовой папки `.output`. Когда сайт уже собран, `API_PROXY_TARGET` никто больше не читает. Поэтому переменную надо задать **во время сборки** образа (в Dockerfile, раздел 5), а не при запуске контейнера. Если задать её только при запуске, сайт будет стучаться в `127.0.0.1:8000` внутри своего контейнера, и вход сломается с «Сервер не отвечает».
</details>

**Как проверить.** Дома, на собранном сайте:

```powershell
npm run build
node .output/server/index.mjs
```

1. Вход и выход работают.
2. Открой `http://localhost:3000/api/docs` и `http://localhost:3000/api/users`. Swagger и список пользователей **не** показываются: тебя перекинет на `/login` (если не вошёл) или покажет «Страница не найдена» (если вошёл). Ни один из этих запросов не дошёл до API.
3. Swagger у тебя по-прежнему есть, но напрямую: `http://127.0.0.1:8000/docs`. На сервере — через туннель (2.2).

<details><summary>Ответ (nuxt.config.ts целиком)</summary>

```ts
// https://nuxt.com/docs/api/configuration/nuxt-config
const apiTarget = process.env.API_PROXY_TARGET ?? 'http://127.0.0.1:8000'

export default defineNuxtConfig({
  compatibilityDate: '2025-07-15',
  devtools: { enabled: true },
  app: {
    head: {
      htmlAttrs: { lang: 'ru' },
      title: 'Cometa',
    },
  },
  routeRules: {
    '/api/auth/login': { proxy: `${apiTarget}/auth/login` },
    '/api/auth/logout': { proxy: `${apiTarget}/auth/logout` },
    '/api/auth/me': { proxy: `${apiTarget}/auth/me` },
  },
})
```

Проверено на собранном сайте за Caddy: `/api/auth/login` и `/api/auth/me` доходят до API, а `/api/users`, `/api/docs` и `POST /api/auth/register` получают `302` на `/login` от самого Nuxt.
</details>

## 5. Nuxt в Docker

На сервере всё работает в Docker: `api`, `bot`, `pg_database`. Сайт тоже станет контейнером — сервис `web`. Для этого нужен его Dockerfile.

### 5.1. `frontend/Dockerfile`

**Файл:** `frontend/Dockerfile` — **новый**.

Сравни с тем, что ты уже знаешь, — `app/Dockerfile`:

```dockerfile
FROM python:3.12-slim
WORKDIR /my_code
COPY app/requirements.txt ./
COPY app/ ./app/
RUN python -m pip install --no-cache -r requirements.txt
CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

У Nuxt есть отличие: чтобы **собрать** сайт, нужны все пакеты из `node_modules` (сотни мегабайт), а чтобы **запустить** собранный — только папка `.output` (несколько мегабайт). Тащить сотни мегабайт на сервер незачем. Поэтому Dockerfile делают из **двух этапов**:

1. Этап «сборка»: взять Node, поставить пакеты, собрать сайт.
2. Этап «запуск»: взять чистый Node и скопировать в него **только** `.output` из первого этапа.

Итоговый образ — это второй этап. Первый выбрасывается.

Вот Dockerfile целиком, с разбором каждой строки ниже. Напечатай его сам.

```dockerfile
FROM node:22-slim AS build
WORKDIR /web
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
ARG API_PROXY_TARGET=http://api:8000
ENV API_PROXY_TARGET=$API_PROXY_TARGET
RUN npm run build

FROM node:22-slim
WORKDIR /web
COPY --from=build /web/.output ./.output
ENV HOST=0.0.0.0 PORT=3000 NODE_ENV=production
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

| Строка | Что делает и зачем |
|---|---|
| `FROM node:22-slim AS build` | Начать первый этап с образа Node 22 и назвать этап `build`, чтобы потом на него сослаться. |
| `WORKDIR /web` | Рабочая папка внутри контейнера. |
| `COPY package.json package-lock.json ./` | Сначала только список пакетов. Пока он не меняется, Docker берёт следующий шаг из кеша и не скачивает пакеты заново при каждой правке `.vue`. Тот же приём, что `COPY app/requirements.txt` в `app/Dockerfile`. |
| `RUN npm ci` | Поставить пакеты **ровно** тех версий, что записаны в `package-lock.json`. В отличие от `npm install` никогда не обновляет версии и падает, если `package.json` и lock-файл не совпадают. Для сборки это правильно: на сервере будет то же, что ты проверил. |
| `COPY . .` | Скопировать весь код фронтенда. |
| `ARG API_PROXY_TARGET=http://api:8000` | Параметр сборки со значением по умолчанию `http://api:8000` — адресом API внутри Docker-сети. |
| `ENV API_PROXY_TARGET=$API_PROXY_TARGET` | Превратить параметр в переменную окружения, чтобы её увидел `nuxt.config.ts` во время `npm run build` (4.7). |
| `RUN npm run build` | Собрать сайт в `.output`. Адрес API запекается здесь. |
| `FROM node:22-slim` | Начать второй этап с чистого Node. Ничего из первого этапа здесь нет. |
| `COPY --from=build /web/.output ./.output` | Взять из этапа `build` только готовый сайт. |
| `ENV HOST=0.0.0.0` | Слушать на всех адресах контейнера. Если оставить по умолчанию, Caddy из соседнего контейнера не достучится. |
| `ENV PORT=3000` | Номер двери. |
| `ENV NODE_ENV=production` | Сказать Node и библиотекам, что это боевой режим. |
| `EXPOSE 3000` | Пометка «контейнер слушает 3000». Порт наружу **не** открывает, это просто документация. |
| `CMD [...]` | Что запускать: собранный сервер Nuxt. Та же команда, что ты запускал руками в 2.3. |

**Контекст сборки** у этого образа — папка `frontend/`, а не корень репозитория, как у `api` и `bot`. Поэтому в Dockerfile пути без `frontend/`: `COPY package.json`, а не `COPY frontend/package.json`.

### 5.2. `frontend/.dockerignore`

**Файл:** `frontend/.dockerignore` — **новый**.

```text
node_modules
.nuxt
.output
.data
.env
```

**Зачем.** `COPY . .` копирует всё из папки `frontend`. Без `.dockerignore` туда попадёт твоя домашняя `node_modules`, собранная **под Windows**, поверх той, что `npm ci` только что поставил **под Linux**. Некоторые пакеты содержат программы, собранные под конкретную систему, и сборка упадёт с непонятной ошибкой (или, хуже, соберётся через раз). А `.env` может содержать секреты, которым не место в образе.

## 6. Сервер: сайт, HTTPS и порт базы

### 6.1. Сервис `web`

**Файл:** `deploy/compose.prod.yaml`

**Сейчас там** три сервиса: `api`, `pg_database`, `bot`. Посмотри на `bot` — новый сервис будет устроен так же:

```yaml
  bot:
    image: ghcr.io/enipherlucker-ai/fastapi_train-bot:${IMAGE_TAG:?укажи IMAGE_TAG}
    ...
    depends_on:
      - api
    restart: unless-stopped
    logging: *logging
```

**Что сделать.** После `bot` (перед `volumes:`) добавь сервис `web`:

- `image:` — как у `bot`, только `fastapi_train-web`. Тег тот же `${IMAGE_TAG:?укажи IMAGE_TAG}`: все три образа собираются из одного коммита и выкатываются вместе.
- `depends_on: - api` — запускать после API.
- `restart: unless-stopped` и `logging: *logging` — как у остальных.
- **Никаких `ports`**. Снаружи к `web` ходит только Caddy, а он в той же Docker-сети и обращается к `web:3000` по имени.

### 6.2. Сервис `caddy`

Caddy — единственный, кто будет открыт в интернет. Он делает три вещи:

1. Принимает HTTPS на порту 443 и расшифровывает запросы.
2. **Сам** получает сертификат у Let's Encrypt для твоего домена и сам продлевает его каждые ~2 месяца.
3. Пересылает расшифрованные запросы в `web:3000`.

А на порту 80 (обычный HTTP) отвечает «иди на `https://`», и браузер переходит.

Добавь после `web`:

```yaml
  caddy:
    image: caddy:2
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"
    environment:
      SITE_DOMAIN: ${SITE_DOMAIN:?добавь SITE_DOMAIN в .env}
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - web
    restart: unless-stopped
    logging: *logging
```

| Строка | Зачем |
|---|---|
| `image: caddy:2` | Официальный образ из Docker Hub. `2` — мажорная версия зафиксирована, мелкие обновления приходят сами, как у `postgres:18`. |
| `"80:80"`, `"443:443"` | Без `127.0.0.1:` впереди — **намеренно**: эти порты должны быть открыты в интернет. Это единственное место в файле, где так можно. |
| `"443:443/udp"` | Для HTTP/3 (работает поверх UDP). Без этой строки всё работает, просто по HTTP/2. |
| `SITE_DOMAIN: ${SITE_DOMAIN:?...}` | Домен берётся из `.env` на сервере, а не пишется в git. Если его забыть, `docker compose` сразу остановится с понятной ошибкой. |
| `./Caddyfile:/etc/caddy/Caddyfile:ro` | Файл настроек (6.3) с сервера внутрь контейнера. `:ro` — только чтение. |
| `caddy_data:/data` | Здесь Caddy хранит **сертификаты**. Без этого volume при каждом пересоздании контейнера (то есть при каждом деплое) Caddy просил бы новый сертификат и быстро упёрся бы в лимиты Let's Encrypt. |
| `caddy_config:/config` | Служебные настройки Caddy. |

И в самом низу файла добавь два новых volume к существующему `pg_data`:

```yaml
volumes:
  pg_data:
  caddy_data:
  caddy_config:
```

### 6.3. `deploy/Caddyfile`

**Файл:** `deploy/Caddyfile` — **новый**, без расширения.

```text
{
	# acme_ca https://acme-staging-v02.api.letsencrypt.org/directory
}

{$SITE_DOMAIN} {
	encode zstd gzip
	reverse_proxy web:3000
}

www.{$SITE_DOMAIN} {
	redir https://{$SITE_DOMAIN}{uri} permanent
}
```

| Часть | Что значит |
|---|---|
| `{ ... }` в самом начале | Общие настройки Caddy. Сейчас внутри только закомментированная строка (про неё ниже). |
| `{$SITE_DOMAIN}` | Подставить переменную окружения. Получится `cometa-analytics.com`. |
| `{$SITE_DOMAIN} { ... }` | «Для этого домена делай так». Само упоминание домена включает автоматический HTTPS. |
| `encode zstd gzip` | Сжимать ответы. Страницы грузятся быстрее. |
| `reverse_proxy web:3000` | Пересылать всё в Nuxt. |
| `www.{$SITE_DOMAIN} { ... }` | Отдельно для `www.cometa-analytics.com`. Caddy получит сертификат и на это имя (поэтому нужна A-запись `www`, раздел 3). |
| `redir https://{$SITE_DOMAIN}{uri} permanent` | Ответить «настоящий адрес — без `www`», код `301`. `{uri}` сохраняет путь: `www.cometa-analytics.com/login` → `cometa-analytics.com/login`. `permanent` — браузер запомнит и в следующий раз пойдёт сразу без `www`. |

Отступы в Caddyfile — табуляция или пробелы, неважно.

<details><summary>Зачем закомментированная строка acme-staging</summary>

У Let's Encrypt есть **лимиты**: например, не больше 5 неудачных попыток получить сертификат на одно имя за час. Если DNS ещё не указывает на сервер или порт 80 закрыт, Caddy будет пробовать снова и снова, быстро исчерпает лимит, и даже после исправления придётся ждать.

У Let's Encrypt есть **тестовый** центр (staging): сертификаты у него ненастоящие (браузер покажет предупреждение), зато лимиты очень мягкие. Если при первой выкатке сертификат не получается:

1. Убери `#` перед `acme_ca`, выкати, смотри логи Caddy.
2. Когда в логах `certificate obtained successfully` — всё настроено правильно.
3. Верни `#`, выкати ещё раз. Caddy получит настоящий сертификат.

DNS у тебя уже настроен (3.3), поэтому, скорее всего, staging не понадобится. Строка лежит на случай проблем.
</details>

Проверено: `caddy adapt` разбирает этот файл без ошибок, `www.example.ru` перенаправляется на `https://example.ru{uri}`. В тестовом запуске всего стека с Caddy `http://` отвечает `308` на `https://`, а `www` — `301` на адрес без `www`.

### 6.4. Порт базы для туннеля

Это нужно для раздела 9. Делай сейчас, чтобы выкатить всё одним заходом.

**Файл:** `deploy/compose.prod.yaml`, сервис `pg_database`.

**Сейчас:** у `pg_database` нет `ports`. База доступна только внутри Docker-сети (`api` ходит к ней как `pg_database:5432`). На самом сервере на двери `127.0.0.1:5432` никого нет, и туннелю некуда вести.

**Что сделать.** Добавь в `pg_database` (например, после `environment`):

```yaml
    ports:
      - "127.0.0.1:5432:5432"
```

Сравни с `api`: там уже `"127.0.0.1:8000:8000"`.

<details><summary>Почему это безопасно, а "5432:5432" — нет</summary>

Запись `"А:Б"` — «дверь А на сервере ведёт в дверь Б контейнера». Если перед `А` не указан адрес, дверь открывается на **всех** адресах сервера, включая публичный, — то есть в интернет. Причём Docker делает это **в обход** файрвола `ufw`: даже если в ufw порт закрыт, он будет открыт.

`"127.0.0.1:5432:5432"` открывает дверь только на `127.0.0.1` сервера. Из интернета до неё не достать. А SSH-туннель «выходит» на самом сервере, поэтому ему она доступна.

После выкатки проверь на сервере:

```bash
sudo ss -tlnp | grep 5432
```

Должно быть `127.0.0.1:5432`. Если видишь `0.0.0.0:5432` или `*:5432` — база открыта в интернет, немедленно исправь.

И с твоего компьютера: `Test-NetConnection cometa-analytics.com -Port 5432` → `TcpTestSucceeded : False`.
</details>

При выкатке этой правки контейнер `pg_database` пересоздастся. Данные не пропадут: они в volume `pg_data`, а не в контейнере.

### 6.5. Проверка в `deploy.sh`: сайт тоже должен отвечать

**Файл:** `deploy/deploy.sh`

**Сейчас там** после запуска контейнеров цикл: 30 раз с паузой 2 секунды спрашивает API, отвечает ли он. Если ответил — «API отвечает», конец. Если нет за 60 секунд — показать логи API и выйти с ошибкой (тогда job `deploy` в GitHub станет красной).

```bash
for i in $(seq 1 30); do
  if docker compose exec -T api python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/openapi.json', timeout=2)" 2>/dev/null; then
    echo "API отвечает, версия ${TAG}"
    ...
```

**Что не так.** Если сайт не стартует (например, ошибка в сборке Nuxt), скрипт этого не заметит: API же отвечает. Деплой будет «зелёным», а сайт лежит.

**Что сделать.**

1. Перед циклом заведи функцию `healthy`, которая проверяет **и** API, **и** сайт. Функция в bash выглядит так:

   ```bash
   healthy() {
     команда1 &&
     команда2
   }
   ```

   `&&` — «вторую команду выполнить, только если первая прошла». Функция «успешна», только если прошли обе.

2. Первая команда — твоя текущая проверка API (`docker compose exec -T api python -c ...`).
3. Вторая — проверка сайта. В образе Node нет `curl`, но в Node 22 есть встроенный `fetch`:

   ```bash
   docker compose exec -T web node -e "fetch('http://127.0.0.1:3000/login').then(r => process.exit(r.ok ? 0 : 1), () => process.exit(1))"
   ```

   `node -e "..."` — выполнить кусок JavaScript. Он открывает `/login` внутри контейнера `web` и завершается с кодом 0 («успех»), если страница ответила 200–299, иначе с кодом 1.

4. В цикле замени длинное условие на `if healthy 2>/dev/null; then`. `2>/dev/null` прячет сообщения об ошибках, пока сервисы ещё стартуют.
5. Поправь тексты: «API и сайт отвечают...», «API или сайт не ответили...», а в конце показывай логи обоих: `docker compose logs --tail=50 api web >&2`.

<details><summary>Ответ (deploy.sh целиком)</summary>

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")"

TAG="${1:?передай тег образа: ./deploy.sh <тег>}"

sed -i "s/^IMAGE_TAG=.*/IMAGE_TAG=${TAG}/" .env
grep -q "^IMAGE_TAG=${TAG}$" .env

docker compose pull
docker compose up -d --remove-orphans

healthy() {
  docker compose exec -T api python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/openapi.json', timeout=2)" &&
  docker compose exec -T web node -e "fetch('http://127.0.0.1:3000/login').then(r => process.exit(r.ok ? 0 : 1), () => process.exit(1))"
}

for i in $(seq 1 30); do
  if healthy 2>/dev/null; then
    echo "API и сайт отвечают, версия ${TAG}"
    docker compose ps
    docker image prune -af --filter "until=168h"
    exit 0
  fi
  sleep 2
```

## 7. CI/CD: третий образ

**Файл:** `.github/workflows/ci-cd.yml`

**Сейчас** там четыре job, они идут друг за другом:

```text
lint ──► build ──► images ──► deploy
                  (только push в main)
```

- `lint` — проверяет Python-код (`ruff`).
- `build` — собирает образы `api` и `bot` (чтобы убедиться, что они собираются) и проверяет, что `compose.prod.yaml` написан без ошибок.
- `images` — только для `main`: собирает образы ещё раз и загружает их в GHCR (хранилище образов GitHub) с тегом = хеш коммита.
- `deploy` — только для `main`: заходит на сервер по SSH, копирует туда `compose.prod.yaml`, `deploy.sh` и init-скрипты базы, запускает `deploy.sh <хеш>`.

Сайт нигде не упоминается. Нужно пять правок.

### 7.1. Новая job `frontend`

**Зачем.** Проверять, что Nuxt собирается, отдельно и быстро. Если ты сломаешь `.vue`, ошибка будет в job с понятным названием, а не где-то в середине сборки Docker-образа.

**Куда.** Новая job на том же уровне, что `lint` (с тем же отступом в два пробела), например сразу после `lint`:

```yaml
  frontend:
    runs-on: ubuntu-24.04
    defaults:
      run:
        working-directory: frontend
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: "22"
          cache: npm
          cache-dependency-path: frontend/package-lock.json
      - run: npm ci
      - run: npm run build
```

| Строка | Зачем |
|---|---|
| `defaults: run: working-directory: frontend` | Все `run:` этой job выполняются в папке `frontend`, а не в корне. Иначе `npm ci` не найдёт `package.json`. |
| `actions/setup-node@v5` | Поставить Node на машину GitHub. Это как `actions/setup-python` в `lint`. |
| `cache: npm` | Сохранять скачанные пакеты между запусками. `npm ci` будет идти секунды вместо минуты. |
| `cache-dependency-path` | По какому файлу понимать, что пакеты изменились и кеш устарел. |

### 7.2. `build` ждёт и `frontend`

В job `build` поменяй `needs: lint` на:

```yaml
    needs: [lint, frontend]
```

`needs` — «запускать после этих job и только если они зелёные». В квадратных скобках — список.

### 7.3. `build`: собрать образ сайта и проверить compose с доменом

В шагах `build`, после `docker build -f bot/Dockerfile ...`, добавь:

```yaml
      - run: docker build -t web:ci frontend
```

И в шаге «compose.prod.yaml собирается» добавь строку после `echo "IMAGE_TAG=ci" >> deploy/.env`:

```yaml
          echo "SITE_DOMAIN=example.com" >> deploy/.env
```

<details><summary>Зачем SITE_DOMAIN в CI, если домен настоящий только на сервере?</summary>

`docker compose config` проверяет файл и подставляет переменные. У `caddy` написано `${SITE_DOMAIN:?добавь SITE_DOMAIN в .env}`: «если переменной нет — остановиться с ошибкой». В CI настоящего `.env` нет, шаг собирает временный из `.env.example`. Без этой строки job `build` станет красной с текстом `добавь SITE_DOMAIN в .env`. Значение здесь неважно, CI ничего не открывает в интернет.
</details>

### 7.4. `images`: загрузить образ сайта в GHCR

В job `images`, после шага `bot`, добавь шаг `web` по образцу. Отличие одно: контекст сборки — папка `frontend`, а `-f` не нужен (Dockerfile лежит прямо в ней):

```yaml
      - name: web
        run: |
          docker build -t "$IMAGE_PREFIX-web:$GITHUB_SHA" frontend
          docker push "$IMAGE_PREFIX-web:$GITHUB_SHA"
```

### 7.5. `deploy`: скопировать Caddyfile на сервер

В job `deploy`, шаг «Копируем compose, скрипт и init-скрипты базы», после строки с `deploy.sh` добавь:

```yaml
          scp deploy/Caddyfile "$TARGET:/opt/fastapi-train/Caddyfile"
```

**Зачем.** `scp` копирует на сервер только перечисленные файлы. Новый `Caddyfile` сам туда не попадёт, а `compose.yaml` на сервере ожидает его рядом (`./Caddyfile`). Если файла нет, Docker создаст на его месте пустую **папку** `Caddyfile`, и `caddy` не запустится с ошибкой `not a directory: Are you trying to mount a directory onto a file`. Хуже того, следующий `scp` положит настоящий `Caddyfile` уже **внутрь** этой папки, и ошибка не исчезнет сама (проверено).

<details><summary>Ответ (ci-cd.yml целиком)</summary>

```yaml
env:
  IMAGE_PREFIX: ghcr.io/enipherlucker-ai/fastapi_train

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: false

name: CI/CD

on:
  push:
  pull_request:
  workflow_dispatch:

jobs:
  lint:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"
      - run: python -m pip install ruff==0.16.9
      - run: ruff check app bot
      - run: python -m compileall -q app bot

  frontend:
    runs-on: ubuntu-24.04
    defaults:
      run:
        working-directory: frontend
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: "22"
          cache: npm
          cache-dependency-path: frontend/package-lock.json
      - run: npm ci
      - run: npm run build

  build:
    runs-on: ubuntu-24.04
    needs: [lint, frontend]
    steps:
      - uses: actions/checkout@v5
      - run: docker build -f app/Dockerfile -t api:ci .
      - run: docker build -f bot/Dockerfile -t bot:ci .
      - run: docker build -t web:ci frontend
      - name: compose.prod.yaml собирается
        run: |
          cp .env.example deploy/.env
          echo "IMAGE_TAG=ci" >> deploy/.env

          docker compose -f deploy/compose.prod.yaml config --quiet

  images:
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    needs: build
    runs-on: ubuntu-24.04
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v5
      - name: ВХОД в GHCR
        env:
          GHCR_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: printf '%s' "$GHCR_TOKEN" | docker login ghcr.io -u "$GITHUB_ACTOR" --password-stdin
      - name: api
        run: |
          docker build -f app/Dockerfile -t "$IMAGE_PREFIX-api:$GITHUB_SHA" .
          docker push "$IMAGE_PREFIX-api:$GITHUB_SHA"
      - name: bot
        run: |
          docker build -f bot/Dockerfile -t "$IMAGE_PREFIX-bot:$GITHUB_SHA" .
          docker push "$IMAGE_PREFIX-bot:$GITHUB_SHA"
      - name: web
        run: |
          docker build -t "$IMAGE_PREFIX-web:$GITHUB_SHA" frontend
          docker push "$IMAGE_PREFIX-web:$GITHUB_SHA"
  deploy:
    needs: images
    runs-on: ubuntu-24.04
    environment: production
    steps:
      - uses: actions/checkout@v5
      - name: SSH-ключ
        env:
          SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
          SSH_KNOWN_HOSTS: ${{ secrets.SSH_KNOWN_HOSTS }}

          install -m 700 -d ~/.ssh
          printf '%s\n' "$SSH_PRIVATE_KEY" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519
          printf '%s\n' "$SSH_KNOWN_HOSTS" > ~/.ssh/known_hosts
      - name: Копируем compose, скрипт и init-скрипты базы

          TARGET: ${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}
```

## 8. Выкатка

### 8.1. Сервер: `.env` и файрвол

Зайди на сервер: `ssh fastapi`.

**Открыть 80 и 443 в файрволе:**

```bash
sudo ufw allow 80,443/tcp
sudo ufw allow 443/udp
sudo ufw status
```

- 443 — HTTPS, сам сайт.
- 80 — обычный HTTP. Он нужен, даже если сайт работает только по HTTPS: Let's Encrypt проверяет, что домен твой, именно через порт 80, а ещё Caddy перенаправляет с него на `https://` тех, кто набрал адрес без `https`.

<details><summary>Docker и так обходит ufw. Зачем тогда открывать порты в ufw?</summary>

Ты прав: Docker откроет 80 и 443 и без правил ufw. Правила нужны для честности. `sudo ufw status` — первое, на что смотрят, чтобы понять, что открыто на сервере. Если он показывает не то, что открыто на самом деле, через полгода ты сам себя обманешь.
</details>

**Дописать две строки в `.env`.** Файл принадлежит пользователю `deploy`:

```bash
sudo -iu deploy nano /opt/fastapi-train/.env
```

В конец добавь:

```text
APP_ENV=prod
SITE_DOMAIN=cometa-analytics.com
```

Сохрани: `Ctrl+O`, `Enter`, выйди: `Ctrl+X`.

- `SITE_DOMAIN` — **только имя**: без `https://`, без `www`, без `/` в конце. Caddy ждёт имя.
- `APP_ENV=prod` — посмотри в `app/api/auth.py`, где ставится cookie:

  ```python
        secure=settings.app_env != "dev",
  ```

  А в `app/config.py` `app_env: str = "dev"` по умолчанию. Значит, сейчас на сервере cookie ставится **без** флага `Secure`. С `APP_ENV=prod` флаг появится, и браузер будет отправлять cookie сессии **только** по HTTPS. Без флага cookie может уйти по обычному `http://`, например, если кто-то откроет сайт в кафе по `http://` — и её перехватят.

<details><summary>А если открыть сайт по http://IP-сервера, без домена?</summary>

По голому IP сайт не откроется: Caddy настроен только на домен, а сертификат на IP Let's Encrypt не выдаёт. А если бы и открылся, вход «не держался» бы: сервер ответил бы `200` и прислал cookie с флагом `Secure`, но браузер выбросил бы её, потому что пришла она по `http://`. Следующий запрос `/api/auth/me` получил бы `401`, и тебя вернуло бы на `/login`. Поэтому на сервере сайт открывают только по `https://cometa-analytics.com`.
</details>

Пока пользователи — ты и, может быть, пара близких людей, заводить их должен администратор. «Вход для администратора» — это SSH-туннель: попасть в него можно только с твоим ключом.

1. Открой `https://cometa-analytics.com/login`. В адресной строке — замок. Во вкладке — «Вход».
2. Войди. Ты на главной: «Привет, Jenifer!»
3. **Обнови страницу (F5).** Ты всё ещё на главной.
4. F12 → **Application** → **Cookies** → `https://cometa-analytics.com` → cookie `session`. Галочки **HttpOnly** и **Secure** стоят.
5. Открой `https://www.cometa-analytics.com` — адрес сам сменится на `https://cometa-analytics.com`.
6. Открой `https://cometa-analytics.com/api/docs` — Swagger **не** показывается.
7. С телефона **через мобильный интернет** (Wi-Fi выключи) открой сайт и войди. Так ты видишь сайт, как его видят другие, без кеша своего роутера.

<details><summary>Почему шаг 3 (обновить страницу) обязательный</summary>

После входа `login.vue` сам записывает пользователя в `currentUser` и переходит на `/`. Для этого cookie не нужна. Даже если браузер выбросил cookie (например, из-за `Secure` по `http://`), ты всё равно увидишь главную.

Ошибка проявится только при обновлении: страница загрузится заново, `currentUser` пустой, `auth.global.ts` спросит `/api/auth/me`, а cookie нет → `401` → `/login`. Поэтому «обнови страницу» — обязательная часть любой проверки входа.
</details>

## 9. SSH-туннель к PostgreSQL

### 9.1. Что хотим и как

**Хотим:** открыть боевую базу в PyCharm или DBeaver, видеть таблицы, выполнять `SELECT`.

**Как нельзя:** открыть порт 5432 в интернет. Даже с хорошим паролем: базу начнут перебирать боты в первые же часы, а любая будущая уязвимость Postgres станет твоей проблемой.

**Как можно:** через SSH. Он и так открыт, защищён ключом, и всё внутри него зашифровано.

```text
PyCharm ──► 127.0.0.1:15432 (твой компьютер)
               ║ SSH-туннель, порт 22
               ▼
            сервер ──► 127.0.0.1:5432 (порт из 6.4) ──► контейнер pg_database
```

Три решения и почему они такие:

| Решение | Почему |
|---|---|
| **SSH под `jenifer`, а не `deploy`** | Ключ `deploy` лежит в GitHub Secrets без пароля, и пользователь `deploy` в группе `docker`, а это почти root. Его используют только для деплоя. Работа руками — твоим ключом с паролем. Если ключ `deploy` придётся отозвать, твой доступ к базе не сломается, и наоборот. |
| **Отдельная роль Postgres «только чтение»** | Главный пользователь из `.env` владеет всеми таблицами и может их удалить. В PyCharm одно случайное `DELETE` без `WHERE` или клик «Drop» — и данных нет. Роль только для чтения такого не может физически. |
| **Локальный порт `15432`, а не `5432`** | На твоём компьютере `5432` занят домашней базой (`compose.yaml`: `"127.0.0.1:5432:5432"`). Подробнее — в ловушках. |

Порт базы на сервере (6.4) ты уже выкатил в разделе 8. Проверь на сервере:

```bash
sudo ss -tlnp | grep 5432
```

Должно быть `127.0.0.1:5432`.

### 9.2. Роль «только чтение»

Это делается **один раз руками на сервере**. Не через файлы в `database/init`: они выполняются только на пустой базе, а пароль роли не должен лежать в git.

Зайди на сервер и открой `psql` главным пользователем:

```bash
cd /opt/fastapi-train
sudo docker compose exec pg_database sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

<details><summary>Почему такая длинная команда, а не просто psql -U ...?</summary>

Имя пользователя и базы лежат в `.env` на сервере. Внутри контейнера `pg_database` они есть в переменных `POSTGRES_USER` и `POSTGRES_DB` (так написано в `compose.prod.yaml`, в `environment`). `sh -c '...'` запускает команду **внутри** контейнера, и там `$POSTGRES_USER` подставится. Одинарные кавычки нужны, чтобы `$POSTGRES_USER` не попытался подставить твой shell на сервере, где такой переменной нет.

`sudo` — потому что твой пользователь `jenifer` не в группе `docker`.
</details>

Появится приглашение `имя_базы=#`. Дальше команды по одной. Имя роли придумай сам, но **не начинай с `pg_`**: такие имена Postgres оставляет себе и не даст создать. Ниже — `jenifer_ro` (`ro` — read only). Вместо `имя_базы` — значение `POSTGRES_SETTINGS__DATABASE` из `.env` (оно же видно в приглашении `psql`).

```sql
CREATE ROLE jenifer_ro LOGIN;
\password jenifer_ro
GRANT CONNECT ON DATABASE имя_базы TO jenifer_ro;
GRANT USAGE ON SCHEMA payment_statistic, logs TO jenifer_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA payment_statistic, logs TO jenifer_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA payment_statistic, logs GRANT SELECT ON TABLES TO jenifer_ro;
ALTER ROLE jenifer_ro SET default_transaction_read_only = on;
\q
```

| Команда | Что делает |
|---|---|
| `CREATE ROLE jenifer_ro LOGIN` | Создать роль, которой можно подключаться (`LOGIN`). Пока без пароля и без прав. |
| `\password jenifer_ro` | Команда самого `psql` (начинается с `\`, это не SQL). Дважды спросит пароль и отправит в базу уже **зашифрованным**. Пароль не попадёт ни в историю команд, ни в логи. Если написать `CREATE ROLE ... PASSWORD 'секрет'`, он останется в истории `psql` открытым текстом. |
| `GRANT CONNECT ON DATABASE` | Право подключиться к этой базе. |
| `GRANT USAGE ON SCHEMA` | Право «заходить» в схемы. Таблицы проекта лежат в схемах `payment_statistic` и `logs` (см. `database/init/01_schema_*.sql`). Без этого права `SELECT` ответит `permission denied for schema`, даже если на таблицу права есть. |
| `GRANT SELECT ON ALL TABLES` | Право читать все таблицы, которые есть **сейчас**. |
| `ALTER DEFAULT PRIVILEGES ... GRANT SELECT` | Право читать таблицы, которые главный пользователь создаст **потом**. Без этого новая таблица окажется недоступна, и ты будешь гадать почему. |
| `ALTER ROLE ... SET default_transaction_read_only = on` | Второй замок: каждая транзакция этой роли по умолчанию только для чтения. |
| `\q` | Выйти из `psql`. |

Пароль для роли придумай длинный. Можно сгенерировать на сервере: `openssl rand -base64 24`. Сохрани его в менеджер паролей — он понадобится в PyCharm.

<details><summary>Зачем два замка, если GRANT SELECT и так не даёт писать?</summary>

Каждый замок можно сломать по ошибке. Например, через год ты выдашь роли `INSERT` на одну таблицу «на минутку» и забудешь. Второй замок (`read_only`) всё равно остановит случайное изменение.

Честно: `read_only` защищает от **случайности**, а не от злоумышленника — роль может выключить его сама командой `SET default_transaction_read_only = off`. От злоумышленника защищают права (`GRANT`).

Проверено на PostgreSQL 18 с init-скриптами проекта:
- `SELECT` из `payment_statistic.users` работает;
- `DELETE` → `cannot execute DELETE in a read-only transaction`;
- после `SET default_transaction_read_only = off` → `UPDATE` получает `permission denied for table users`;
- `CREATE TABLE logs.x` → `permission denied for schema logs`;
- таблица, созданная главным пользователем после `ALTER DEFAULT PRIVILEGES`, читается.
</details>

<details><summary>Эта роль видит password_hash и user_sessions. Это нормально?</summary>

Для тебя — да, это твоя база. Хеши паролей нельзя превратить обратно в пароли быстро, а токены сессий хранятся тоже как хеши. Но:

- не выкладывай скриншоты таблиц `users` и `user_sessions` в чаты;
- если когда-нибудь дашь доступ к базе кому-то ещё, ему нужна отдельная роль, которая этих столбцов не видит (уровень 6 тренировки).
</details>

### 9.3. Туннель из PowerShell

На своём компьютере открой туннель в отдельном окне PowerShell:

```powershell
ssh -N -L 15432:127.0.0.1:5432 fastapi
```

Это тот же туннель, что в 2.2, только другие двери: `15432` у тебя → `127.0.0.1:5432` на сервере.

Во **втором** окне проверь, что туннель слушает:

```powershell
Test-NetConnection 127.0.0.1 -Port 15432
```

`TcpTestSucceeded : True` — туннель работает. Теперь к `127.0.0.1:15432` на твоём компьютере можно подключаться как к базе на сервере.

Чтобы не писать `-L` каждый раз, добавь в `C:\Users\Jenifer\.ssh\config` второй блок:

```text
Host fastapi-db
    HostName cometa-analytics.com
    User jenifer
    IdentityFile ~/.ssh/id_ed25519
    LocalForward 15432 127.0.0.1:5432
    ServerAliveInterval 30
    ServerAliveCountMax 3
```

`LocalForward` — то же самое, что `-L`, только записанное в файле. Запуск: `ssh -N fastapi-db`.

### 9.4. PyCharm

Вкладка **Database** есть только в PyCharm с подпиской (бывший Professional). Если её у тебя нет — переходи к DBeaver (9.5), он бесплатный.

PyCharm умеет **сам** открывать туннель, тогда окно PowerShell из 9.3 не нужно.

1. Справа вкладка **Database** → **+** → **Data Source** → **PostgreSQL**.
2. Вкладка **SSH/SSL** → галочка **Use SSH tunnel** → кнопка **...** справа → **+** (новая SSH-конфигурация):
   - **Host:** `cometa-analytics.com`, **Port:** `22`, **Username:** `jenifer`;
   - **Authentication type:** `Key pair`;
   - **Private key file:** `C:\Users\Jenifer\.ssh\id_ed25519`;
   - **Passphrase:** пароль от ключа (тот, что вводишь при `ssh fastapi`);
   - **Test Connection** → «Successfully connected». **OK**.
3. Вкладка **General**:
   - **Host:** `localhost`, **Port:** `5432`;
   - **User:** `jenifer_ro`, **Password:** пароль роли из 9.2;
   - **Database:** имя базы.
4. Внизу **Test Connection**. Если PyCharm предложит скачать драйвер — **Download**.
5. Вкладка **Options** → галочка **Read-only**. Третий замок: PyCharm сам не даст выполнить изменяющий запрос.
6. В поле **Name** вверху напиши `PROD cometa (read-only)`, а рядом выбери **красный цвет**. Так боевую базу невозможно спутать с домашней.

<details><summary>Почему в General стоит 5432, а не 15432?</summary>

С включённой галочкой **Use SSH tunnel** туннель открывает **сам PyCharm** и сам выбирает себе свободную дверь на твоём компьютере. Ты сообщаешь ему только, куда туннель должен вести **на сервере**: `localhost:5432`. Это та же правая часть, что в `-L 15432:127.0.0.1:5432`.

Если ты открыл туннель руками в PowerShell (9.3), можно наоборот: **не** включать **Use SSH tunnel**, а в **General** написать `localhost` и `15432`. Работают оба способа. Не смешивай их в одном подключении: если включить **Use SSH tunnel** и написать `15432`, PyCharm пойдёт на сервер и будет искать там дверь `15432`, где никого нет.
</details>

Открой подключение → `payment_statistic` → таблицы. Двойной клик по `users` — содержимое таблицы с сервера.

## 10. Ловушки

### Две A-записи на одно имя
Браузер выбирает случайную. Половина посетителей попадает на заглушку регистратора, Caddy получает сертификат через раз. Одна A-запись на имя.

### AAAA без работающего IPv6
Let's Encrypt проверяет сначала IPv6. Сертификат не выдаётся, часть посетителей не открывает сайт.

### Сертификат до того, как DNS обновился
Caddy пробует, Let's Encrypt идёт по старому адресу, ошибка. Пять ошибок за час — и ждать. Сначала `Resolve-DnsName` через `1.1.1.1` и `8.8.8.8`, потом выкатка. На крайний случай — staging (6.3).

### `SITE_DOMAIN=https://cometa-analytics.com`
Caddy ждёт имя, а не адрес. Только `cometa-analytics.com`.

### Файл `config.txt` вместо `config`
ssh читает только файл без расширения. Ошибка выглядит как `connect to host fastapi port 22`. Проверка — `ssh -G fastapi`.

### `LoginIn` с `login: str`
При регистрации длина ограничена, при входе — нет, потому что ограничения висят на типах `Login` и `Password`, а `LoginIn` их не использует. Пароль на мегабайты загружает argon2. `max_length` у полей `LoginIn`.

### 500 вместо 401 для пользователя без пароля
Посторонний по коду ответа узнаёт, что логин существует. Нет хеша = как будто нет пользователя.

### Страница показывает то, чего сервер не подтвердил
«Вышел», а cookie живёт. Меняй состояние на странице только после успешного ответа сервера.

### `'/api/**'` на сервере
Через сайт становится публичным всё API: регистрация, пользователи, чеки, Swagger. Только белый список.

### `127.0.0.1` в адресе API внутри контейнера
Для контейнера `web` адрес `127.0.0.1` — это он сам. На входе «Сервер не отвечает», в `docker compose logs web` — `ECONNREFUSED 127.0.0.1:8000`. Адрес в Docker — `http://api:8000`, и задаётся он **при сборке** образа.

### Нет `.dockerignore` у Nuxt
Домашняя `node_modules` с Windows попадает в Linux-образ. Сборка падает непонятно или работает через раз.

### Новый файл не копируется на сервер
`scp` в workflow копирует только перечисленное. Забыл `Caddyfile` → Docker создаёт на его месте пустую папку → `caddy` не стартует с ошибкой `Are you trying to mount a directory onto a file`.

### `APP_ENV` не задан
По умолчанию `"dev"`, cookie без `Secure`. На сервере `APP_ENV=prod`.

### Проверка входа без обновления страницы
«Вошёл» ещё не значит «вход держится». Всегда F5.

### `"5432:5432"` в боевом compose
Без `127.0.0.1:` база открыта в интернет в обход ufw. Проверка — `sudo ss -tlnp | grep 5432`.

### Туннель на локальный порт `5432`
У тебя дома `5432` занят базой из `compose.yaml`. В лучшем случае ssh скажет `Address already in use` / `cannot listen to port: 5432`. В худшем (Docker и ssh займут разные адреса) PyCharm молча подключится к **домашней** базе, и ты будешь искать боевые чеки не там. Для туннеля — `15432`.

### Туннель под `deploy`
Ключ без пароля, почти root. Только для GitHub Actions.

### Главный пользователь базы в PyCharm
Один клик «Drop» — и данных нет. Для просмотра — `jenifer_ro`.

### Пароль роли в `CREATE ROLE ... PASSWORD '...'`
Остаётся в истории `psql` открытым текстом. Используй `\password`.

### В PyCharm `15432` при включённом SSH-туннеле
PyCharm ищет дверь `15432` на сервере, там никого. При встроенном туннеле — `5432`.

### `deploy.sh` с окончаниями строк CRLF
`bash\r: No such file or directory`. Внизу справа в PyCharm — `LF`.

## 11. Диагностика: сначала найди этап

### SSH и DNS

| Симптом | Где смотреть | Частая причина |
|---|---|---|
| `connect to host fastapi port 22` | `ssh -G fastapi` | Файл `config` не прочитан: называется `config.txt` или лежит не в `C:\Users\Jenifer\.ssh` |
| `Connection timed out` при `ssh jenifer@cometa-analytics.com` | `Resolve-DnsName`, `ssh jenifer@<IP>` | DNS указывает не туда, или сервер выключен |
| `Permission denied (publickey)` | `IdentityFile` в config | Не тот ключ или не тот пользователь |
| `Resolve-DnsName` у `1.1.1.1` и `8.8.8.8` разные ответы | подожди TTL | Запись обновилась ещё не везде |

### Сайт

| Симптом | Где смотреть | Частая причина |
|---|---|---|
| Браузер: «сайт недоступен» | `sudo docker compose ps` | `caddy` не запущен; не открыты 80/443 |
| Ошибка сертификата в браузере | `sudo docker compose logs caddy` | DNS ещё не обновился; закрыт порт 80; включён staging |
| `502 Bad Gateway` на всей странице (белая страница с текстом) | `logs web` | `web` не запустился или упал |
| Страница есть, вход: «Сервер не отвечает» | `logs web`, F12 → Network | `api` лежит, или `API_PROXY_TARGET` запёкся как `127.0.0.1` |
| Вход проходит, после F5 выкидывает на `/login` | F12 → Application → Cookies | Сайт открыт по `http://` |
| `www` не открывается | `logs caddy` | Нет A-записи `www` или блока `www.` в Caddyfile |
| `deploy` в Actions: ошибка про `fastapi_train-web` при `pull` | GitHub → Packages | Видимость нового пакета (8.2) |
| `deploy`: `Are you trying to mount a directory onto a file` | `ls -la /opt/fastapi-train` | `Caddyfile` не скопирован, на его месте папка. Удали папку (`sudo rm -r /opt/fastapi-train/Caddyfile`), перезапусти deploy |

```bash
sudo docker compose logs --tail=50 web
sudo docker compose logs --tail=50 api
curl -I https://cometa-analytics.com/login
```

### Туннель и база

| Симптом | Где | Причина |
|---|---|---|
| `Test-NetConnection 127.0.0.1 -Port 15432` → False | окно туннеля | Туннель не открыт или закрылся (окно закрыто, ноутбук уснул) |
