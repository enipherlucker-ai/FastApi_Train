# Свой сервер, деплой и CI/CD на GitHub Actions — для чайников 😄

**Цель урока:** после него ты сам выбираешь и покупаешь сервер, на котором работают и Telegram-бот, и OpenAI, и сервис проверки чеков; настраиваешь его так, чтобы его не взломали в первую же ночь; и делаешь так, что каждый `git push` в `main` сам проверяет код, собирает образы и выкатывает их на сервер. Руками на сервер ты больше не ходишь, кроме первого раза и аварий.

Урок построен на этом репозитории. Сейчас всё живёт на твоём компьютере: в `compose.yaml` три сервиса (`api`, `pg_database`, `bot`), код подключён в контейнеры через `volumes`, `api` запущен с `--reload`, а бот ходит в Telegram через прокси на твоём компьютере (`TELEGRAM_DOCKER_PROXY`). Выключила компьютер — бот замолчал. К концу урока появятся:

- сервер в интернете, где те же три сервиса работают круглосуточно;
- папка `deploy/` с «боевым» `compose.prod.yaml` и скриптом `deploy.sh`;
- файл `.github/workflows/ci-cd.yml`: проверки на каждый push и выкатка на сервер на каждый push в `main`.

Готового кода в репозитории нет: всё из разделов 7–10 пишешь ты. Примеры `compose.prod.yaml` и `deploy.sh` из урока проверены командой `docker compose config` на Docker Compose v5.6; `ruff` в примерах версии 0.16.9.

> ⚠️ **Часть урока устаревает быстро.** Где работает Telegram, какие страны поддерживает OpenAI, какие хостеры принимают российские карты и сколько стоит сервер — всё это **проверено 20.10.2026** по источникам из раздела 17. Перед покупкой открой эти источники ещё раз: за полгода картина может поменяться.

## 0. Как проходить урок

Правила те же, что в [уроке по Docker](docker-for-beginners.md), [уроке по Postgres](postgres-docker-for-beginners.md) и [уроке по Telegram-боту](telegram-bot-for-beginners.md):

1. **Печатай руками.** Не копируй блоки из урока в файлы.
2. **Одна настройка — одна проверка.** После каждого шага убедись, что изменилось именно то, что ожидала.
3. **Сначала предскажи — потом запусти.**
4. **Ответы — в свёрнутых блоках.** Открывай их только после своей попытки.

И три новых правила:

5. **Сервер — это чужой компьютер в интернете, и его уже ищут.** Боты-сканеры перебирают все адреса интернета круглые сутки. Новый сервер с паролем `root` на SSH начинают перебирать через минуты после включения. Поэтому сначала защита (раздел 6), потом всё остальное.
6. **Секреты живут в двух местах: в `.env` на сервере и в Secrets на GitHub.** Никогда в git, никогда в логах Actions, никогда в YAML-файле workflow.
7. **Проверяй до того, как платишь за месяц.** Почти все провайдеры берут деньги по часам. Сервер на час для проверки стоит несколько рублей, а неправильная страна на год — нервы и деньги.

План: что мы строим и словарь (раздел 1) → где купить сервер, чтобы всё работало (2) → зачем публичный IP (3) → какие нужны мощности (4) → шаг ноль: песочница (5) → первые полчаса на сервере (6) → боевой compose (7) → CI: проверки на каждый push (8) → CD: выкатка на сервер (9) → домен и HTTPS, когда понадобятся (10) → бэкапы и логи (11) → правила, на которых ошибаются (12) → диагностика (13) → тренировка (14) → повторение по памяти (15) → шпаргалка (16) → источники (17).

## 1. Что мы строим и словарь

| Слово | Что это | Аналогия |
|---|---|---|
| VPS (VDS) | Виртуальный сервер: кусок большого компьютера в дата-центре, который выглядит как отдельный компьютер с Linux. Платишь помесячно или по часам | Съёмная квартира в большом доме |
| Публичный IP | Адрес, по которому до сервера можно достучаться из любой точки интернета | Почтовый адрес дома |
| SSH | Способ зайти в командную строку сервера по сети. Вход по ключу, а не по паролю | Ключ от квартиры |
| SSH-ключ | Пара файлов: приватный (`id_ed25519`, никому не отдаёшь) и публичный (`id_ed25519.pub`, кладёшь на сервер) | Ключ и замок: замок можно повесить на любую дверь, ключ — только у тебя |
| Firewall (`ufw`) | Список портов, которые сервер принимает снаружи. Всё остальное отбрасывается | Домофон: открывает только своим |
| CI (Continuous Integration) | Автоматические проверки на каждый push: линтер, сборка, тесты. Ответ на вопрос «код вообще рабочий?» | ОТК на заводе |
| CD (Continuous Delivery / Deployment) | Автоматическая доставка проверенного кода на сервер | Курьер, который везёт со склада покупателю |
| GitHub Actions | Встроенный в GitHub сервис, который запускает твои команды на чужих виртуальных машинах при событиях в репозитории | Робот, который дежурит у репозитория |
| Workflow | YAML-файл в `.github/workflows/`: когда запускаться и что делать | Инструкция для робота |
| Job | Часть workflow, которая работает на одной отдельной машине. Jobs по умолчанию идут параллельно, `needs:` выстраивает их в очередь | Отдельный рабочий |
| Step | Одна команда (`run:`) или готовое действие (`uses:`) внутри job | Одно движение рабочего |
| Runner | Машина, на которой выполняется job. `ubuntu-24.04` — чистая виртуалка от GitHub, живёт одну job | Одноразовый верстак |
| Secret | Зашифрованная переменная в настройках репозитория: SSH-ключ, адрес сервера. В логах Actions заменяется на `***` | Сейф, ключ от которого есть только у робота |
| Registry (GHCR) | Хранилище Docker-образов. У GitHub оно своё: `ghcr.io` | Склад готовой продукции |
| Тег образа | Метка версии образа: `ghcr.io/.../fastapi_train-api:3f2c1ab`. Мы ставим тег = хеш коммита | Номер партии на коробке |
| Деплой (выкатка) | Заменить работающую версию на новой: скачать новые образы и пересоздать контейнеры | Замена товара на витрине |
| Откат | Вернуть предыдущую версию, когда новая сломалась | Вернуть старый товар на витрину |

**CI отвечает «можно ли это выкатывать», CD отвечает «выкати». Без CI CD просто быстрее доставляет поломки на сервер.**

### Как это будет работать

```text
Твой компьютер                 GitHub                                  Сервер (VPS за рубежом)
──────────────                 ──────                                  ───────────────────────
git push ───────────────► репозиторий
                               │
                               ▼
                         Actions: job lint ── ruff, compileall
                               │ ok
                               ▼
                         job build ── docker build api, bot
                               │ ok и ветка main
                               ▼
                         job images ── docker push ──► ghcr.io/…-api:3f2c1ab
                               │                       ghcr.io/…-bot:3f2c1ab
                               ▼                               │
                         job deploy ── ssh deploy@сервер ──────┼──► ./deploy.sh 3f2c1ab
                                                               │       docker compose pull ◄─┘
                                                               │       docker compose up -d
                                                                       api ◄── bot ──► api.telegram.org
                                                                        │ └──────────► api.openai.com
                                                                        ▼ └──────────► сервис проверки чеков
                                                                   pg_database
```

Три важных факта:

- **На сервере нет исходного кода и не идёт сборка.** Образы собирает GitHub на своих машинах, сервер их только скачивает. Поэтому серверу не нужно много памяти для `pip install`, а в `/opt/fastapi-train` лежат всего три вещи: `compose.yaml`, `.env` и `database/init`.
- **Сервер сам ходит наружу, к нему снаружи ходит только SSH.** Бот работает через long polling (см. [урок по боту](telegram-bot-for-beginners.md), раздел 1), порт API открыт только на `127.0.0.1` самого сервера. Открытый порт пока нужен один: 22.
- **Каждая версия на сервере = конкретный коммит.** Тег образа — хеш коммита, поэтому всегда видно, что сейчас запущено, и откат — это просто «запусти предыдущий хеш».

<details><summary>Вопрос 3. Почему не взять сервер в России и прокинуть прокси, раз дома так уже работает?</summary>

Можно (раздел 2.5), но это три лишние детали, каждая из которых ломается: прокси для Telegram, прокси для OpenAI (и его IP должен быть в поддерживаемой стране, иначе блокировка аккаунта), и сам прокси-сервер, который всё равно придётся арендовать за рубежом. Получается два сервера вместо одного. Сервер в России имеет смысл, когда веб-сервис станет главным и зарубежный адрес начнут замедлять для твоих пользователей. Тогда см. «План Б» в 2.5.
</details>

### 2.3. Как заплатить из России

- **Западные провайдеры** (Hetzner, DigitalOcean, AWS, Google Cloud) российские карты не принимают и могут отказать в регистрации из России. Вдобавок Hetzner 15.06.2026 поднял цены на новые облачные серверы в среднем примерно вдвое для Германии. Для тебя это тупик.
- **Российские провайдеры с зарубежными площадками** — рабочий путь. Договор с российской компанией, оплата картой МИР или по СБП в рублях, а сервер стоит в Амстердаме, Хельсинки или Алматы. На 20.10.2026 такие площадки есть, например, у Timeweb Cloud (Нидерланды, Германия, Финляндия, Казахстан и др.), RuVDS (Нидерланды, Германия, Казахстан и др.), Hostkey (Нидерланды, Финляндия), VDSina (Нидерланды), FirstVDS (Нидерланды), AdminVPS (Нидерланды, Германия, Финляндия, Казахстан и др.), Beget (Казахстан). Это примеры для поиска, а не реклама: перед покупкой сравни цены на сайтах сама.
- **Чего избегать.** Хостеров под санкциями: например, Aeza с июля 2025 года под санкциями США, у таких компаний выше риск, что отвалится зарубежный канал или площадка. И сервисов, которые просят оплату только криптовалютой без договора: деньги не вернуть.

Как выбрать конкретного провайдера, чек-лист:

1. Есть площадка в нужной стране (Нидерланды, Финляндия, Германия или Казахстан).
2. **Почасовая оплата** или пробный период — чтобы проверить сервер за копейки (раздел 5.3).
3. Виртуализация KVM (не OpenVZ: в OpenVZ часто не работает Docker).
4. Ubuntu 24.04 LTS в списке образов.
5. Один публичный IPv4 включён в цену.
6. Можно добавить свой SSH-ключ при создании сервера.

### 2.5. Если всё-таки сервер в России: прокси и свой VPN

Этот раздел — на будущее, читать сейчас не обязательно.

**Способ 1. Прокси.** У тебя уже есть `TELEGRAM_SETTINGS__PROXY`, у OpenAI-клиента — `base_url`. Арендуешь второй маленький сервер за рубежом (1 vCPU / 1 ГБ хватит) и поднимаешь на нём прокси. Бот и `api` ходят в Telegram и OpenAI через него. Минус: два сервера, и если связь между ними замедляют, страдает всё.

**Способ 2. Свой шлюз через `base_url`.** На зарубежном сервере ставишь обратный прокси (Caddy или nginx), который принимает `https://tg.твой-домен/...` и пересылает в `https://api.telegram.org/...`, и так же для OpenAI. В российском сервере меняешь только `TELEGRAM_SETTINGS__BASE_URL` и `OPEN_AI_SETTINGS__BASE_URL`. Код не меняется вообще — именно для этого `base_url` вынесен в настройки. Через шлюз идёт токен бота и ключ OpenAI, поэтому шлюз должен быть только твоим.

**Способ 3. Коммерческий VPN на сервере.** Не советую: VPN-клиент в контейнере или на всём сервере ломает SSH и Docker-сети, а сами VPN в России блокируют чаще, чем обычные серверы.

**План Б для большого веб-сервиса.** Когда сайт с графиками станет главным и окажется, что из России он открывается медленно: сайт, API и база переезжают на сервер в России, а бот и вызовы OpenAI остаются на зарубежном сервере (или идут через шлюз из способа 2). Это ровно та же архитектура «бот — просто клиент API», которую ты уже построила: боту всё равно, где стоит API, ему важен только `RECEIPT_API_SETTINGS__URL`. Но тогда API придётся открыть наружу, а это требует авторизации (см. раздел 12, «API открыто в интернет без входа»).

## 3. Зачем публичный IP и нужно ли его покупать

Твой домашний компьютер **не имеет публичного IP**. У роутера есть один внешний адрес от провайдера (часто даже он общий на целый дом — это называется CGNAT), а у компьютера внутренний адрес вида `192.168.x.x`. Ты можешь ходить наружу, но снаружи никто не может постучаться к тебе: роутер не знает, какому компьютеру в квартире отдать входящий запрос. К тому же домашний адрес меняется.

| Кому нужен входящий доступ к серверу | Нужен ли публичный IP |
|---|---|
| Бот (long polling) | ❌ Бот сам ходит в Telegram. Работал бы и за роутером |
| `api` для бота | ❌ Бот ходит в `http://api:8000` внутри Docker-сети |
| Ты по SSH | ✅ |
| GitHub Actions для деплоя по SSH | ✅ Runner GitHub стоит в дата-центре в США, ему нужен адрес, куда подключиться |
| Будущий сайт на Nuxt | ✅ Браузеры пользователей должны куда-то прийти |
| Бот на webhook (если когда-нибудь перейдёшь) | ✅ Плюс HTTPS |

**Покупать отдельно не нужно.** У VPS один публичный IPv4 почти всегда входит в цену и не меняется, пока ты не удалишь сервер. Отдельно платить имеет смысл только за второй адрес. IPv6 обычно дают бесплатно, но GitHub-runner'ы и часть сетей до сих пор ходят по IPv4, поэтому без IPv4 не бери.

<details><summary>Вопрос 4. Если IP есть, зачем домен?</summary>

Для SSH и деплоя домен не нужен. Он понадобится для сайта: людям удобнее `mysite.ru`, чем `203.0.113.10`, и сертификат HTTPS выдают на имя. Ещё домен позволяет переехать на другой сервер, не меняя адрес для пользователей: меняешь одну DNS-запись. Покупать домен стоит вместе с разделом 10, не раньше.
</details>

<details><summary>Вопрос 5. Почему нельзя просто держать всё на домашнем компьютере с белым IP от провайдера?</summary>

Можно, но компьютер должен работать круглосуточно, домашний интернет и свет пропадают, у провайдера IP может смениться, а прокси для Telegram всё равно нужен, потому что ты в России. И ты открываешь порт в домашнюю сеть, где лежат твои личные файлы. VPS дешевле этих проблем.
</details>

## 4. Какие нужны мощности

### 4.1. Сначала измерь, потом покупай

Подними проект локально и выполни:

```powershell
docker compose up -d
docker stats --no-stream
```

Ты увидишь колонку `MEM USAGE` для каждого контейнера. Отправь боту пару чеков и посмотри ещё раз: в момент распознавания QR-кода у `bot` память подскакивает (картинка распаковывается в память целиком).

<details><summary>Чего примерно ожидать</summary>

Порядок величин для твоего проекта сейчас: `pg_database` — десятки мегабайт, растёт по мере того, как Postgres кеширует данные; `api` — около 100–150 МБ (Python, SQLAlchemy, клиент OpenAI); `bot` — 50–100 МБ, с пиком при распознавании фото. Вместе — меньше 500 МБ. Твои точные цифры важнее этих: запиши их.
</details>

### 4.2. Что будет, когда проект вырастет

| Сервис | Память, ориентир | Когда появится |
|---|---|---|
| Ubuntu + Docker | 300–400 МБ | Сразу |
| `pg_database` | 100 МБ – 1 ГБ (Postgres охотно берёт память под кеш, это нормально) | Сразу |
| `api` | 100–200 МБ, больше при нескольких воркерах uvicorn | Сразу |
| `bot` | 50–150 МБ | Сразу |
| Nuxt (SSR на Node.js) | 150–300 МБ | С уроком по Nuxt |
| Caddy (HTTPS) | 20–50 МБ | Раздел 10 |
| Мониторинг (Grafana, Prometheus и т. п.) | 300 МБ – 1 ГБ | Когда захочешь графики о самом сервере |

**Рекомендация:** начни с **2 vCPU / 4 ГБ RAM / 50–60 ГБ NVMe**. С 2 ГБ сейчас тоже заработает, но сборка или Nuxt упрутся в память. Когда добавишь Nuxt и мониторинг и `free -h` покажет, что свободной памяти стабильно меньше 500 МБ, переходи на 4 vCPU / 8 ГБ. У большинства провайдеров это кнопка «изменить тариф» с перезагрузкой, данные остаются.

Диск: система 5–8 ГБ, образы Docker 2–4 ГБ (и старые версии копятся), база у тебя крошечная, плюс бэкапы и логи. 50–60 ГБ хватит надолго, если чистить старые образы и ограничить логи (разделы 9 и 11).

Процессор нагружают только распознавание QR-кода и сборка образов. Сборка у нас идёт на GitHub, поэтому 2 vCPU с запасом.

Трафик: бот и API гоняют килобайты. Лимиты провайдеров (обычно от 1–3 ТБ в месяц) тебе не грозят.

## 5. Шаг ноль: песочница

### 5.1. GitHub Actions в отдельном репозитории

Создай на GitHub новый **публичный** репозиторий `actions-sandbox` (для публичных репозиториев Actions бесплатны без ограничений; у приватных на бесплатном плане 2000 минут в месяц). Склонируй его и создай файл `.github/workflows/hello.yml`:

```yaml
name: Hello

on:
  push:
  workflow_dispatch:

jobs:
  hello:
    runs-on: ubuntu-24.04
    steps:
      - run: echo "Привет из Actions"
      - run: uname -a && python3 --version && docker --version
      - run: echo "Коммит ${{ github.sha }} в ветке ${{ github.ref_name }} от ${{ github.actor }}"
```

Запушь и открой вкладку **Actions** в репозитории. Кликни на запуск, на job `hello`, раскрой каждый step.

<details><summary>Что ты должна увидеть и что это значит</summary>

- Три зелёных step'а и два служебных (`Set up job`, `Complete job`).
- В выводе `uname` — Linux, в `docker --version` — установленный Docker. Runner — это полноценная виртуалка, на ней уже есть Python, Docker, git.
- `${{ github.sha }}` превратился в длинный хеш. Это **выражение**: GitHub подставляет значение до запуска команды, bash видит уже готовую строку.
- `workflow_dispatch` добавил кнопку **Run workflow** — запуск вручную, без push.
</details>

Теперь сломай специально, по одному:

1. Добавь step `- run: exit 1`. Что стало с остальными step'ами после него?
2. Добавь вторую job `second` без `needs:` и с `needs: hello`. Как меняется порядок?
3. Сделай отступ на один пробел больше у одного из step'ов.

<details><summary>Ответы</summary>

1. Job стала красной, step'ы после упавшего не выполнились (`skipped`). Любая команда с ненулевым кодом выхода роняет step.
2. Без `needs:` jobs идут параллельно, каждая на своей машине. С `needs: hello` — вторая ждёт первую и не запустится, если первая упала.
3. Workflow не запустится вообще, а на вкладке Actions будет ошибка разбора YAML с номером строки. В YAML отступы — это синтаксис.
</details>

### 5.2. Секрет в песочнице

В `actions-sandbox`: **Settings → Secrets and variables → Actions → New repository secret**, имя `MY_SECRET`, значение `котик`. Добавь step:

```yaml
      - run: echo "Секрет $MY_SECRET, длина ${#MY_SECRET}"
        env:
          MY_SECRET: ${{ secrets.MY_SECRET }}
```

<details><summary>Что будет в логе и почему</summary>

`Секрет ***, длина 5`. GitHub заменяет значение секрета на `***` в логах. Но длина, первая буква, base64 от секрета **не маскируются**. Поэтому правило не «печатать секреты можно, всё равно скроют», а «никогда не печатать секреты».

Обрати внимание: секрет передан через `env:`, а в команде — обычная переменная bash. Так правильнее, чем вписывать `${{ secrets.MY_SECRET }}` прямо в `run:` (см. раздел 12).
</details>

### 5.3. Сервер на час: проверка страны до оплаты месяца

Возьми у выбранного провайдера самый дешёвый сервер **с почасовой оплатой** в выбранной стране, Ubuntu 24.04. Зайди по SSH (как — в разделе 6.2; пока можно по паролю из письма, сервер всё равно проживёт час). Выполни проверки:

```bash
# 1. Telegram: ждём {"ok":true,...} с именем бота
curl -sS "https://api.telegram.org/bot<ТОКЕН>/getMe"; echo

# 2. OpenAI: ждём список моделей, а не ошибку про страну
curl -sS https://api.openai.com/v1/models -H "Authorization: Bearer <КЛЮЧ>" | head -c 300; echo

# 3. Сервис проверки чеков: ждём ответ сервиса (даже ошибку про токен), а не таймаут или 403
curl -sS -m 20 -o /dev/null -w "%{http_code}\n" <CHECK_RECEIPT_SETTINGS__URL>

# 4. GHCR и Docker Hub
curl -sS -o /dev/null -w "%{http_code}\n" https://ghcr.io/v2/
curl -sS -o /dev/null -w "%{http_code}\n" https://registry-1.docker.io/v2/
```

А с **твоего компьютера** проверь, что сервер нормально открывается из России: `ssh` подключается быстро, а `scp` файла на 50 МБ туда и обратно не ползёт на скорости в килобайты.

> Токен и ключ ты вводишь в командную строку сервера, который через час удалишь, — это допустимо. На боевом сервере секреты живут только в `.env`. Сразу после проверки выполни `history -c`.

<details><summary>Как читать результаты</summary>

| Результат | Что значит |
|---|---|
| `getMe` вернул `"ok":true` | Telegram работает |
| `getMe` висит до таймаута | Telegram недоступен из этой страны или этого дата-центра |
| OpenAI вернул `unsupported_country_region_territory` | Страна не поддерживается |
| OpenAI вернул `401` | Страна ок, неверный ключ — для проверки страны этого достаточно |
| Сервис чеков: код `200`, `400`, `401`, `405` | Сервис доступен (код зависит от метода и токена) |
| Сервис чеков: `000` или `403` | Сервис режет этот IP. Пробуй другую страну или площадку |
| `ghcr.io/v2/` — `401` | Нормально: реестр доступен, просто без входа |
| Все пункты ок | Удаляй этот сервер и бери такой же на месяц в той же площадке |
</details>

## 6. Первые полчаса на сервере

Делается один раз руками. Порядок важен: сначала ключи и пользователь, потом закрытие пароля, потом всё остальное.

### 6.1. SSH-ключ на твоём компьютере

В PowerShell:

```powershell
ssh-keygen -t ed25519 -C "jenifer-laptop"
```

Путь оставь по умолчанию (`C:\Users\Jenifer\.ssh\id_ed25519`), пароль на ключ задай. Появятся два файла. `id_ed25519.pub` — публичный, его содержимое можно показывать кому угодно. `id_ed25519` — приватный, не уходит с компьютера никогда.

При создании сервера в панели провайдера вставь содержимое `.pub` в поле «SSH-ключ». Если панель так не умеет, сервер придёт с паролем root: зайди по паролю один раз и сразу выполни 6.2.

### 6.2. Первый вход и свой пользователь

```powershell
ssh root@<IP>
```

На вопрос `Are you sure you want to continue connecting` ответь `yes`. Отпечаток сервера запишется в `known_hosts`; если однажды он изменится без твоей переустановки сервера, ssh громко предупредит — это защита от подмены.

На сервере:

```bash
apt update && apt full-upgrade -y
adduser jenifer                      # твой пользователь, задай пароль (он нужен для sudo)
usermod -aG sudo jenifer
mkdir -p /home/jenifer/.ssh
cp /root/.ssh/authorized_keys /home/jenifer/.ssh/
chown -R jenifer:jenifer /home/jenifer/.ssh
chmod 700 /home/jenifer/.ssh && chmod 600 /home/jenifer/.ssh/authorized_keys
```

**Не закрывая это окно**, открой второе и проверь: `ssh jenifer@<IP>`, затем `sudo whoami` должно ответить `root`. Только после этого переходи дальше.

<details><summary>Вопрос 6. Зачем второе окно?</summary>

Следующий шаг выключает вход root и вход по паролю. Если ты ошиблась в ключах или правах, а единственная сессия закрыта, ты сама себя заперла снаружи. Пока первое окно открыто, ты можешь всё исправить. Если всё же заперлась — у провайдеров есть «VNC-консоль» или «аварийная консоль» в панели.
</details>

### 6.3. Запрещаем пароли и root по SSH

Создай файл `/etc/ssh/sshd_config.d/10-hardening.conf` (через `sudo nano`):

```text
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
```

```bash
sudo sshd -t && sudo systemctl reload ssh
```

`sshd -t` проверяет синтаксис: если в файле опечатка, он скажет об этом до перезапуска, а не после.

Проверь из нового окна: `ssh root@<IP>` должен ответить `Permission denied (publickey)`, а `ssh jenifer@<IP>` — пускать.

### 6.4. Firewall

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw enable
sudo ufw status verbose
```

Пока открыт только SSH. 80 и 443 откроешь в разделе 10, когда появится сайт.

> ⚠️ **Docker обходит `ufw`.** Если в compose написать `ports: - "5432:5432"`, порт откроется в интернет, хотя `ufw` его «запрещает»: Docker пишет свои правила iptables в обход ufw. Поэтому в боевом compose у базы **нет** `ports` вообще, а у API порт записан как `127.0.0.1:8000:8000`: с `127.0.0.1:` впереди порт слушает только сам сервер, как у тебя уже сделано локально.

### 6.5. Автообновления безопасности

```bash
sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades   # ответь Yes
```

### 6.6. Docker

Ставь из официального репозитория Docker, а не пакет `docker.io` из Ubuntu (он отстаёт по версиям, и в нём может не быть `docker compose` v2). Инструкция: docs.docker.com → Install Docker Engine on Ubuntu → «Install using the apt repository». Выполни её по шагам, затем:

```bash
sudo docker run --rm hello-world
docker compose version
```

### 6.7. Пользователь для деплоя

GitHub Actions будет заходить на сервер не под тобой, а под отдельным пользователем с отдельным ключом. Если ключ из GitHub утечёт, ты удалишь одного пользователя, а твой личный доступ останется.

```bash
sudo adduser --disabled-password --gecos "" deploy
sudo usermod -aG docker deploy
sudo mkdir -p /opt/fastapi-train/database/init
sudo chown -R deploy:deploy /opt/fastapi-train
```

На **твоём компьютере** сделай для него отдельный ключ без пароля (Actions не умеет вводить пароль):

```powershell
ssh-keygen -t ed25519 -f $HOME\.ssh\fastapi_train_deploy -N '""' -C "github-actions-deploy"
```

Содержимое `fastapi_train_deploy.pub` положи на сервер в `/home/deploy/.ssh/authorized_keys` (папка `700`, файл `600`, владелец `deploy`, как в 6.2). Проверь: `ssh -i $HOME\.ssh\fastapi_train_deploy deploy@<IP> docker ps`.

<details><summary>Вопрос 7. Группа docker — это безопасно?</summary>

Нет, и это надо понимать честно: кто может запускать `docker`, тот может запустить контейнер с примонтированным `/` и стать root. То есть ключ `deploy` — это почти root-доступ к серверу. Поэтому: отдельный ключ, хранится только в GitHub Secrets, workflow запускается только из `main` (раздел 9), а в репозиторий не принимаются чужие workflow. Для учебного проекта это нормальный компромисс; в больших компаниях ставят rootless Docker или деплой через агент на сервере.
</details>

### 6.8. Боевой `.env` на сервере

Создай `/opt/fastapi-train/.env` руками (под `deploy`: `sudo -iu deploy`, потом `nano /opt/fastapi-train/.env`). Возьми за основу свой локальный `.env` и измени:

- `POSTGRES_SETTINGS__HOST=pg_database` — имя сервиса в Compose, а не `localhost`.
- `POSTGRES_SETTINGS__PASSWORD` — **новый длинный пароль**, не тот, что дома. Сгенерируй: `openssl rand -base64 32`.
- Строк `TELEGRAM_DOCKER_PROXY` и `TELEGRAM_SETTINGS__PROXY` нет: на зарубежном сервере прокси не нужен.
- `RECEIPT_API_SETTINGS__URL` можно не писать: в compose он задан как `http://api:8000`.
- Последней строкой — `IMAGE_TAG=none` (её будет менять `deploy.sh`).

```bash
chmod 600 /opt/fastapi-train/.env
```

<details><summary>Вопрос 8. Почему бы не передавать .env из GitHub Secrets при каждом деплое?</summary>

Можно и так, это тоже распространённый способ. Но тогда каждый секрет живёт в двух местах (GitHub и сервер), а при каждом деплое пишется на диск runner'а. Мы выбираем простое правило: **секреты приложения живут только на сервере, в GitHub — только то, что нужно для входа на сервер.** Если взломают GitHub-аккаунт, ключ OpenAI и токен бота не утекут напрямую.
</details>

## 7. Боевой compose: чем он отличается от домашнего

Создай в репозитории папку `deploy/` и в ней `compose.prod.yaml`. На сервере этот файл будет лежать как `/opt/fastapi-train/compose.yaml`: так команды `docker compose ps`, `logs` и т. д. будут работать без `-f`.

Сначала подумай сама:

<details><summary>Вопрос 9. Что из домашнего compose.yaml нельзя брать на сервер и почему? Найди хотя бы пять отличий</summary>

| Дома | На сервере | Почему |
|---|---|---|
| `build:` | `image: ghcr.io/...:${IMAGE_TAG}` | На сервере не собираем, а скачиваем готовый образ из реестра |
| `volumes: - ./app:/my_code/app` | Нет | Кода на сервере нет, код внутри образа. Именно образ проверил CI |
| `--reload` в `command` | Нет, работает `CMD` из Dockerfile | `--reload` следит за файлами и тратит ресурсы, нужен только при разработке |
| `ports: 127.0.0.1:8000:8000` у `api` | То же самое, только `127.0.0.1` | Бот ходит в `api:8000` внутри сети. Порт на `127.0.0.1` сервера снаружи недоступен, но через SSH-туннель ты откроешь `/docs` у себя в браузере (раздел 13). Без `127.0.0.1:` API оказалось бы в интернете без авторизации |
| `ports: 127.0.0.1:5432:5432` у базы | Нет `ports` | К базе ходит только `api`. Заглянуть в базу можно через `docker compose exec pg_database psql` (раздел 13) |
| `TELEGRAM_SETTINGS__PROXY` | Нет | Сервер за рубежом, Telegram открывается напрямую |
| Логи без ограничений | `logging` с `max-size` | Иначе логи за полгода съедят диск |
| `restart` только у базы и бота | `restart: unless-stopped` у всех | После перезагрузки сервера всё должно подняться само |
</details>

Пример (не копируй, пиши по нему; имя образа — **маленькими буквами**, почему — в разделе 12):

```yaml
name: fastapi-train

x-logging: &logging
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"

services:
  api:
    image: ghcr.io/enipherlucker-ai/fastapi_train-api:${IMAGE_TAG:?укажи IMAGE_TAG}
    ports:
      - "127.0.0.1:8000:8000"
    env_file:
      - .env
    depends_on:
      pg_database:
        condition: service_healthy
    restart: unless-stopped
    logging: *logging

  pg_database:
    image: postgres:18
    env_file:
      - .env
    environment:
      POSTGRES_USER: ${POSTGRES_SETTINGS__USER}
      POSTGRES_PASSWORD: ${POSTGRES_SETTINGS__PASSWORD}
      POSTGRES_DB: ${POSTGRES_SETTINGS__DATABASE}
    volumes:
      - pg_data:/var/lib/postgresql
      - ./database/init:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 10
      start_period: 10s
    restart: unless-stopped
    logging: *logging

  bot:
    image: ghcr.io/enipherlucker-ai/fastapi_train-bot:${IMAGE_TAG:?укажи IMAGE_TAG}
    environment:
      TELEGRAM_SETTINGS__TOKEN: ${TELEGRAM_SETTINGS__TOKEN:?добавь TELEGRAM_SETTINGS__TOKEN в .env}
      TELEGRAM_SETTINGS__ALLOWED_USER_IDS: ${TELEGRAM_SETTINGS__ALLOWED_USER_IDS:-[]}
      RECEIPT_API_SETTINGS__URL: http://api:8000
    depends_on:
      - api
    stop_signal: SIGINT
    restart: unless-stopped
    logging: *logging

volumes:
  pg_data:
```

Новое здесь:

- `name: fastapi-train` — имя проекта Compose. Без него имя берётся из названия папки, и volume назовётся по папке. Явное имя защищает от ситуации «переименовала папку — Compose создал новую пустую базу».
- `x-logging: &logging` и `logging: *logging` — **якорь YAML**: блок описан один раз и подставлен в три сервиса. Ключи, начинающиеся с `x-`, Compose игнорирует, они существуют только для якорей.
- `${IMAGE_TAG:?укажи IMAGE_TAG}` — если переменной нет, Compose откажется стартовать с этим текстом, а не скачает непонятно что.

Проверь синтаксис у себя (из папки `deploy/`, создав там временный `.env` из `.env.example` с добавленной строкой `IMAGE_TAG=test`):

```powershell
docker compose -f compose.prod.yaml config --images
```

Ожидаемо: три строки с именами образов, у `api` и `bot` тег `test`. Временный `deploy/.env` в git не попадёт: строка `.env` в `.gitignore` без `/` в начале игнорирует такой файл в любой папке (убедись: `git status` его не показывает).

### 7.1. Скрипт выкатки `deploy/deploy.sh`

Его запускает GitHub Actions на сервере, и ты тоже можешь запустить его руками для отката. Что он делает: записывает тег в `.env`, скачивает образы, пересоздаёт контейнеры, ждёт, пока API ответит, и чистит старые образы.

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")"

TAG="${1:?передай тег образа: ./deploy.sh <тег>}"

sed -i "s/^IMAGE_TAG=.*/IMAGE_TAG=${TAG}/" .env
grep -q "^IMAGE_TAG=${TAG}$" .env

docker compose pull
docker compose up -d --remove-orphans

for i in $(seq 1 30); do
  if docker compose exec -T api python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/openapi.json', timeout=2)" 2>/dev/null; then
    echo "API отвечает, версия ${TAG}"
    docker compose ps
    docker image prune -af --filter "until=168h"
    exit 0
  fi
  sleep 2
done

echo "API не ответило за 60 секунд" >&2
docker compose logs --tail=50 api >&2
exit 1
```

<details><summary>Вопрос 10. Разбери каждую строку: зачем она?</summary>

- `set -euo pipefail` — упасть на первой ошибке (`-e`), на необъявленной переменной (`-u`) и если упала любая команда в конвейере (`pipefail`). Без этого скрипт после неудачного `pull` спокойно сделает `up` со старыми образами и скажет «готово».
- `cd "$(dirname "$0")"` — перейти в папку, где лежит сам скрипт, откуда бы его ни вызвали.
- `${1:?...}` — первый аргумент обязателен.
- `sed -i ...` — заменить строку `IMAGE_TAG=` в `.env`. `grep -q` проверяет, что замена случилась (если строки `IMAGE_TAG=` в `.env` не было, `sed` молча ничего не сделает).
- `pull` до `up` — пока образы качаются, старые контейнеры работают. Простой — только на время пересоздания.
- `--remove-orphans` — удалить контейнеры сервисов, которых больше нет в compose.
- Цикл с `urllib` — **проверка здоровья**: в образе `python:3.12-slim` нет `curl`, зато есть Python. Если API не поднялось за 60 секунд, скрипт выходит с ошибкой, и job в Actions станет красной — ты узнаешь о проблеме сразу, а не от бота через день.
- `docker image prune -af --filter "until=168h"` — удалить неиспользуемые образы старше недели. Для отката на старую версию она просто скачается заново из GHCR.
</details>

Файл должен быть исполняемым **в git**, иначе на сервере он приедет без права запуска. На Windows бит исполнения сам не ставится:

```powershell
git add deploy/deploy.sh
git update-index --chmod=+x deploy/deploy.sh
```

И у него должны быть **окончания строк LF**, а не CRLF (см. раздел 12). Создай в корне `.gitattributes` со строкой `*.sh text eol=lf`.

## 8. CI: проверки на каждый push

Создай `.github/workflows/ci-cd.yml`. Начнём только с CI — двух jobs.

```yaml
name: CI/CD

on:
  push:
  pull_request:
  workflow_dispatch:

jobs:
  lint:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"
      - run: python -m pip install ruff==0.16.9
      - run: ruff check app bot
      - run: python -m compileall -q app bot

  build:
    runs-on: ubuntu-24.04
    needs: lint
    steps:
      - uses: actions/checkout@v5
      - run: docker build -f app/Dockerfile -t api:ci .
      - run: docker build -f bot/Dockerfile -t bot:ci .
      - name: compose.prod.yaml собирается
        run: |
          cp .env.example deploy/.env
          echo "IMAGE_TAG=ci" >> deploy/.env
          docker compose -f deploy/compose.prod.yaml config --quiet
```

И в корне репозитория файл `ruff.toml`:

```toml
[lint]
select = ["E4", "E7", "E9", "F"]
```

Разбор:

- `on: push` без веток — на каждый push в любую ветку. Ошибки видны ещё до слияния в `main`.
- `actions/checkout` скачивает твой репозиторий на runner. **Без него на машине пусто**: частая ошибка «файл не найден» в первом workflow.
- `actions/setup-python` ставит нужный Python. Версии actions (`@v5`, `@v6`) — это их мажорные версии на момент написания. Свежую смотри на странице action на GitHub (github.com/actions/checkout).
- `ruff==0.16.9` — **версия закреплена**. Набор правил по умолчанию у ruff меняется между версиями: без закрепления CI однажды покраснеет сам по себе, хотя ты ничего не меняла. `ruff.toml` фиксирует набор правил явно: `F` — настоящие ошибки (неиспользуемые импорты, необъявленные имена), `E4/E7/E9` — синтаксис и грубые ошибки стиля.
- `compileall` проверяет, что каждый `.py` хотя бы синтаксически корректен.
- Job `build` проверяет, что оба Dockerfile собираются. Если ты добавила библиотеку в код и забыла в `requirements.txt`, сборка пройдёт, а вот если опечаталась в `requirements.txt` — упадёт здесь, а не на сервере.

<details><summary>Предскажи: что покажет первый запуск на текущем коде?</summary>

Job `lint` упадёт. `ruff` найдёт `F541 f-string without any placeholders` в `bot/handlers.py:45`: `f"Нет доступа к боту"` — f-строка без `{}`. Исправь (убери `f`), запушь, посмотри, как job стала зелёной. Так и выглядит работа CI: ловит мелочь до того, как она уехала на сервер.

Если запустишь `ruff check` локально без `ruff.toml`, ошибок может оказаться больше двадцати (сортировка импортов и т. п.): так выглядят правила по умолчанию в ruff 0.16. Это причёсывание, его можно сделать отдельно командой `ruff check --fix` и потом расширить `select`.
</details>

<details><summary>Вопрос 11. Почему нет тестов?</summary>

Потому что в проекте их пока нет, а CI проверяет только то, что ты ему дала. Первый тест — в тренировке, уровень 5. Когда тесты появятся, они станут третьей job `test` между `lint` и `build`. Без тестов CI ловит опечатки и поломки сборки, но не поломки логики.
</details>

### 8.1. Защити `main`

**Settings → Branches → Add branch ruleset** (или Branch protection rule) для `main`: запретить force push и удаление, требовать прохождения проверок `lint` и `build` перед слиянием. Ты работаешь одна, но правило защищает тебя от `git push --force` не в ту ветку.

## 9. CD: выкатка на сервер

### 9.1. Секреты в GitHub

**Settings → Secrets and variables → Actions → New repository secret:**

| Имя | Значение | Откуда взять |
|---|---|---|
| `SSH_HOST` | IP сервера | Панель провайдера |
| `SSH_USER` | `deploy` | |
| `SSH_PRIVATE_KEY` | Содержимое файла `fastapi_train_deploy` (приватного!) целиком, со строками `-----BEGIN` и `-----END` | `Get-Content $HOME\.ssh\fastapi_train_deploy -Raw` |
| `SSH_KNOWN_HOSTS` | Отпечаток сервера | `ssh-keyscan -t ed25519 <IP>` на твоём компьютере |

<details><summary>Вопрос 12. Зачем SSH_KNOWN_HOSTS? Проще же ssh -o StrictHostKeyChecking=no</summary>

`StrictHostKeyChecking=no` значит «подключайся к кому угодно, кто ответит на этот IP». Если кто-то перехватит адрес (ошибка в секрете, переезд IP к другому клиенту провайдера), Actions отдаст образ и команды чужому серверу. С `known_hosts` ssh проверит отпечаток и откажется. Это одна строка в секретах вместо дыры.
</details>

### 9.2. Окружение `production`

**Settings → Environments → New environment** `production`. В нём включи **Deployment branches: Selected branches → `main`**. Теперь job, у которой написано `environment: production`, не запустится ни из какой ветки, кроме `main`. Можно перенести секреты `SSH_*` в это окружение (Environment secrets), тогда job из другой ветки их даже не увидит.

### 9.3. Публичные образы в GHCR

Твой репозиторий публичный, но **пакеты в GHCR при первом создании приватные**. Есть два пути:

- **Сделать пакеты публичными** (проще). После первого успешного push образов: профиль GitHub → **Packages** → `fastapi_train-api` → **Package settings → Change visibility → Public**, и так же для `-bot`. В образах нет секретов: `.env` в них не копируется (Dockerfile копирует только `app/` и `bot/`). Проверь это сама, прежде чем открывать.
- **Оставить приватными.** Тогда на сервере один раз `docker login ghcr.io -u enipherlucker-ai` с персональным токеном (classic, право только `read:packages`). Токен сохранится в `/home/deploy/.docker/config.json`.

### 9.4. Добавляем jobs `images` и `deploy`

Допиши в `ci-cd.yml` (на одном уровне с `lint` и `build`) и добавь блоки `env` и `concurrency` в начало файла:

```yaml
env:
  IMAGE_PREFIX: ghcr.io/enipherlucker-ai/fastapi_train

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: false
```

```yaml
  images:
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    needs: build
    runs-on: ubuntu-24.04
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v5
      - name: Вход в GHCR
        env:
          GHCR_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: printf '%s' "$GHCR_TOKEN" | docker login ghcr.io -u "$GITHUB_ACTOR" --password-stdin
      - name: api
        run: |
          docker build -f app/Dockerfile -t "$IMAGE_PREFIX-api:$GITHUB_SHA" .
          docker push "$IMAGE_PREFIX-api:$GITHUB_SHA"
      - name: bot
        run: |
          docker build -f bot/Dockerfile -t "$IMAGE_PREFIX-bot:$GITHUB_SHA" .
          docker push "$IMAGE_PREFIX-bot:$GITHUB_SHA"

  deploy:
    needs: images
    runs-on: ubuntu-24.04
    environment: production
    steps:
      - uses: actions/checkout@v5
      - name: SSH-ключ
        env:
          SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
          SSH_KNOWN_HOSTS: ${{ secrets.SSH_KNOWN_HOSTS }}
        run: |
          install -m 700 -d ~/.ssh
          printf '%s\n' "$SSH_PRIVATE_KEY" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519
          printf '%s\n' "$SSH_KNOWN_HOSTS" > ~/.ssh/known_hosts
      - name: Копируем compose, скрипт и init-скрипты базы
        env:
          TARGET: ${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}
        run: |
          scp deploy/compose.prod.yaml "$TARGET:/opt/fastapi-train/compose.yaml"
          scp deploy/deploy.sh "$TARGET:/opt/fastapi-train/deploy.sh"
          scp database/init/*.sql "$TARGET:/opt/fastapi-train/database/init/"
      - name: Выкатка
        env:
          TARGET: ${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}
        run: ssh "$TARGET" "/opt/fastapi-train/deploy.sh $GITHUB_SHA"
```

Разбор того, что новое:

- `if: github.event_name == 'push' && github.ref == 'refs/heads/main'` — образы и деплой только при push в `main`. На push в ветку и на pull request работают только `lint` и `build`.
- `permissions: packages: write` — по умолчанию `GITHUB_TOKEN` не может писать в GHCR. Права выдаются на job, минимально нужные.
- `secrets.GITHUB_TOKEN` — его не нужно создавать: GitHub выдаёт временный токен на каждый запуск и отзывает после.
- `$GITHUB_SHA` — то же, что `${{ github.sha }}`, но как обычная переменная окружения, которую runner выставляет сам.
- Секреты попадают в команды **через `env:`**, а не подстановкой `${{ }}` прямо в текст скрипта.
- `concurrency` с `cancel-in-progress: false` — если ты сделала два push подряд, второй деплой подождёт первый, а не запустится параллельно и не убьёт его на середине.
- `scp database/init/*.sql` — init-скрипты нужны базе только при **первом** запуске на пустом volume. Копируем каждый раз, чтобы на сервере лежала та же версия, что в git (но см. ловушку «init-скрипты не применяются к существующей базе»).

### 9.5. Первый деплой

1. Убедись, что на сервере есть `/opt/fastapi-train/.env` со строкой `IMAGE_TAG=none` и что `deploy` владеет папкой.
2. Запушь ветку с `deploy/` и workflow, дождись зелёных `lint` и `build`.
3. Слей в `main` (у себя `git merge` и `git push`, или кнопкой на GitHub, как тебе удобнее).
4. Смотри вкладку Actions: `lint → build → images → deploy`.
5. После первого `images` сделай пакеты публичными (9.3), если выбрала этот путь, и перезапусти упавший `deploy` кнопкой **Re-run failed jobs**.
6. **Останови локального бота** (`docker compose stop bot` дома), иначе два бота на одном токене будут спорить за `getUpdates` (ошибка `409 Conflict`).
7. Отправь боту фото чека.

<details><summary>Как проверить, что работает именно серверная версия</summary>

На сервере: `docker compose ps` (из `/opt/fastapi-train`) — у `api` и `bot` в колонке IMAGE хеш последнего коммита, совпадает с `git log -1 --format=%H` у тебя. `docker compose logs -f bot` — видно твоё сообщение. Чек появился в базе: `docker compose exec pg_database psql -U <user> -d <db> -c "select count(*) from ..."`.
</details>

### 9.6. Откат

Выкатилась сломанная версия. Самый быстрый путь — на сервере:

```bash
sudo -iu deploy
cd /opt/fastapi-train
./deploy.sh <хеш предыдущего рабочего коммита>
```

Хеш возьми из истории успешных запусков на вкладке Actions или из `git log`. Правильный путь после этого — `git revert` сломанного коммита и push в `main`: тогда в git и на сервере снова одно и то же. Пока не сделаешь revert, следующий push выкатит сломанный код обратно.

> ⚠️ Откат образа не откатывает базу. Если новая версия изменила таблицы, старый код может с ними не работать. Отсюда правило: изменения базы делаем так, чтобы старый код их переживал (добавить колонку — можно, переименовать — в два шага). Подробно — в будущем уроке про миграции (Alembic).

## 10. Домен и HTTPS — когда появится сайт

Сейчас этот раздел не делай: наружу открывать нечего. Он понадобится вместе с Nuxt и авторизацией.

1. Купи домен у регистратора и сделай **A-запись** `@` (и `www`) на IP сервера. Проверка: `nslookup твой-домен.ru` возвращает IP сервера (до нескольких часов после изменения).
2. Добавь в `compose.prod.yaml` сервис `caddy` (образ `caddy:2`) с `ports: ["80:80", "443:443"]`, volume для `/data` (там хранятся сертификаты) и `Caddyfile`:

   ```text
   твой-домен.ru {
       reverse_proxy web:3000
   }
   ```

   Caddy сам получит сертификат Let's Encrypt и будет его продлевать.
3. `sudo ufw allow 80,443/tcp`.

<details><summary>Вопрос 13. Почему Caddy, а не nginx?</summary>

nginx отлично работает, но сертификат для него получают отдельным инструментом (certbot), и это ещё одна вещь, которая ломается при продлении. Caddy делает HTTPS сам, конфиг для одного сайта — три строки. Для одного сервера с одним доменом это меньше движущихся частей.
</details>

## 11. Бэкапы и логи

### 11.1. Бэкап базы

**Volume `pg_data` — не бэкап.** Если удалить сервер, сломать диск или выполнить `docker compose down -v`, данные исчезнут вместе с ним.

Минимальный бэкап — файл `/opt/fastapi-train/backup.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail
cd /opt/fastapi-train
mkdir -p backups
set -a; . ./.env; set +a
docker compose exec -T pg_database pg_dump -U "$POSTGRES_SETTINGS__USER" -d "$POSTGRES_SETTINGS__DATABASE" -Fc > "backups/db-$(date +%F).dump"
find backups -name 'db-*.dump' -mtime +14 -delete
```

И строка в `crontab -e` пользователя `deploy`: `30 3 * * * /opt/fastapi-train/backup.sh`.

Бэкап на том же сервере защищает от `DROP TABLE`, но не от потери сервера. Раз в неделю забирай последний файл к себе: `scp deploy@<IP>:/opt/fastapi-train/backups/db-<дата>.dump .` (или настрой выгрузку в объектное хранилище провайдера).

**Бэкап, который ни разу не восстанавливали, не считается бэкапом.** Восстанови его хотя бы раз локально: `docker compose exec -T pg_database pg_restore -U ... -d ... --clean < db-<дата>.dump`.

### 11.2. Логи

```bash
docker compose logs -f --tail=100 bot     # бот вживую
docker compose logs --since=1h api        # API за последний час
```

`logging: max-size: 10m, max-file: 3` в compose значит: не больше 30 МБ логов на контейнер, старые затираются. Если нужна долгая история, это уже задача для системы сбора логов (Loki, Grafana) — отдельный урок.

## 12. Правила, на которых ошибаются

### Сервер в России «потому что ближе»
Telegram ограничен, OpenAI не поддерживает Россию и может заблокировать аккаунт. Получится сервер плюс прокси плюс второй сервер. Сначала таблица из 2.2, потом покупка.

### Купила на год, не проверив
Сервис проверки чеков или скорость SSH из России могут не устроить именно в этой площадке. Час почасового сервера (5.3) дешевле.

### Пароль root на SSH
Перебор паролей начинается в первые минуты. Только ключи, `PermitRootLogin no`, `PasswordAuthentication no`.

### `ports: "5432:5432"` на сервере
Docker обходит `ufw`, база окажется открыта в интернет. На сервере у базы нет `ports`, а у API порт только на `127.0.0.1`.

### API открыто в интернет без входа
Сейчас эндпоинты API не требуют входа: бот ходит в них без cookie. Если открыть API наружу, любой сможет создавать и читать чеки. Пока авторизации нет, порт API привязан только к `127.0.0.1` сервера, а `/docs` ты смотришь через SSH-туннель (раздел 13).

### Секрет прямо в YAML или `${{ secrets.X }}` внутри `run:`
Ключ в YAML — это ключ в git навсегда (история помнит). Подстановка `${{ }}` прямо в текст скрипта превращает значение в часть команды: спецсимволы в нём могут сломать или изменить команду. Передавай через `env:`.

### Имя образа с большими буквами
`ghcr.io/${{ github.repository }}` даст `ghcr.io/enipherlucker-ai/FastApi_Train`, а Docker принимает имена только маленькими буквами: `invalid reference format: repository name must be lowercase`. Поэтому имя записано руками в `IMAGE_PREFIX`.

### Тег `latest`
С `latest` непонятно, что запущено, и откатиться не на что: предыдущий `latest` уже перезаписан. Тег — хеш коммита.

### `deploy.sh` с окончаниями строк CRLF
Git на Windows может превратить `\n` в `\r\n`. Тогда на сервере: `/usr/bin/env: 'bash\r': No such file or directory`. Лечится `.gitattributes` со строкой `*.sh text eol=lf`; уже испорченный файл — `sed -i 's/\r$//' deploy.sh`.

### `deploy.sh` без бита исполнения
`Permission denied` при запуске из Actions. `git update-index --chmod=+x deploy/deploy.sh`.

### Два бота на одном токене
Домашний и серверный боты одновременно — `409 Conflict` в логах обоих. После переезда домашний бот не запускается с боевым токеном. Для разработки заведи у BotFather второго бота с отдельным токеном.

### init-скрипты не применяются к существующей базе
`docker-entrypoint-initdb.d` выполняется только на **пустом** volume, то есть один раз в жизни сервера. Новый `05_*.sql` после первого запуска на сервер приедет, но не выполнится. Изменения схемы на работающей базе — это миграции: пока руками через `psql`, потом Alembic.

### `docker compose down -v`
`-v` удаляет volumes, то есть базу. На сервере эту команду не набирают никогда. Если нужно остановить всё — `docker compose down` без `-v`.

### `restart` вместо `up -d` после правки `.env`
`docker compose restart` не перечитывает `.env` и compose. После любой правки — `docker compose up -d`.

### Сборка на сервере
`build:` в боевом compose — значит, на сервере код, `pip install` на 2 ГБ памяти и образ, который CI не проверял. Собирает CI, сервер только скачивает.

### Нет проверки здоровья после деплоя
Без цикла проверки в `deploy.sh` job станет зелёной, даже если `api` падает при старте. Узнаешь ты об этом, когда бот ответит «API недоступно».

## 13. Диагностика: сначала найди этап

| Симптом | Этап | Что проверить |
|---|---|---|
| Workflow не появился во вкладке Actions | Файл | Путь ровно `.github/workflows/*.yml`, файл в той ветке, куда пушила. Ошибка YAML показывается вверху вкладки Actions |
| `lint` красный | CI | Открой step, читай вывод `ruff`: файл, строка, код правила. Повтори локально `ruff check app bot` |
| `build` красный на `pip install` | CI | Опечатка или несуществующая версия в `requirements.txt` |
| `images`: `denied: permission_denied` | GHCR | Нет `permissions: packages: write` у job |
| `images`: `repository name must be lowercase` | GHCR | Большие буквы в имени образа |
| `images` и `deploy` пропущены (серые) | Условие | Это push не в `main` или pull request: так и задумано |
| `deploy`: `Host key verification failed` | SSH | `SSH_KNOWN_HOSTS` пустой или от другого IP. Перегенерируй `ssh-keyscan` |
| `deploy`: `Permission denied (publickey)` | SSH | В `SSH_PRIVATE_KEY` не тот ключ или обрезан; `authorized_keys` у `deploy` не тот, или права не `700/600` |
| `deploy`: `Load key ...: invalid format` | SSH | Секрет скопирован без последней пустой строки или без `-----END...` |
| `deploy`: `scp: ... Permission denied` | Сервер | Папка `/opt/fastapi-train` не принадлежит `deploy` |
| `deploy.sh`: `unauthorized` или `denied` при `pull` | GHCR | Пакеты приватные, а на сервере нет `docker login ghcr.io` |
| `deploy.sh`: `bash\r: No such file` | git | CRLF в скрипте |
| `deploy.sh`: `API не ответило за 60 секунд` | Приложение | Ниже в логе последние строки `api`: чаще всего неверный `POSTGRES_SETTINGS__HOST` (должен быть `pg_database`) или нет переменной в `.env` |
| `password authentication failed for user` в логах `api` | База | Пароль в `.env` поменяли после первого запуска. Postgres берёт пароль из переменной только при создании volume. Смени пароль внутри базы через `psql` (`ALTER USER ...`) |
| Бот на сервере: `getMe: нет связи с Telegram` | Сеть | `curl https://api.telegram.org` на сервере. Если не открывается — площадка не та (раздел 5.3). Нет ли в `.env` забытого `TELEGRAM_SETTINGS__PROXY` |
| `api`: ошибка про `unsupported_country_region_territory` | OpenAI | Сервер в неподдерживаемой стране |
| `api`: 502 «Сервис проверки чеков недоступен» только на сервере | Сеть | Сервис режет IP этой площадки. `curl` к нему с сервера |
| Бот: `409 Conflict` | Два бота | Дома запущен бот с тем же токеном |
| Диск заполнен (`no space left on device`) | Сервер | `df -h`, `docker system df`. Чистка: `docker image prune -af`. Проверь `logging` в compose |
| Нужно посмотреть `/docs` на сервере | Доступ | SSH-туннель: `ssh -L 8001:127.0.0.1:8000 jenifer@<IP>` и, пока окно открыто, открой у себя `http://127.0.0.1:8001/docs`. Порт 8001, чтобы не спорить с домашним API на 8000 |
| Нужно заглянуть в базу | Доступ | На сервере: `docker compose exec pg_database psql -U <user> -d <db>`. Если нужен PyCharm или DBeaver — добавь базе `ports: "127.0.0.1:5432:5432"` (только с `127.0.0.1`!) и туннель `ssh -L 5433:127.0.0.1:5432 jenifer@<IP>`, подключение к `localhost:5433` |

### Уровень 1. Объясни словами

Удали `hello.yml` в `actions-sandbox` и напиши по памяти workflow из двух jobs, где вторая выполняется только после первой и только на push в `main`.

### Уровень 3. Сломай специально

На боевом проекте по очереди (каждый раз предскажи, какая job и с какой ошибкой упадёт):

1. Опечатка в имени пакета в `bot/requirements.txt`.
2. Неиспользуемый импорт в `app/main.py`.
3. Удали секрет `SSH_KNOWN_HOSTS`.
4. В `.env` на сервере испорти `POSTGRES_SETTINGS__HOST`, потом поправь что-нибудь в README, закоммить и запушь в `main`.

Каждый раз почини и убедись, что следующий деплой зелёный.

### Уровень 4. Откат по-настоящему

Сломай API намеренно (например, `raise RuntimeError` в `lifespan`), выкати, посмотри, как `deploy.sh` ловит это и job краснеет. Бот в это время отвечает «API недоступно»? Откатись `./deploy.sh <старый хеш>`, потом сделай `git revert` и push.

<details><summary>Вопрос, над которым стоит подумать</summary>

Когда `deploy.sh` упал на проверке здоровья, новые контейнеры уже запущены, а старые удалены. То есть сломанная версия **работает на сервере**, пока ты не откатишь. Как сделать, чтобы скрипт сам откатывался на предыдущий тег при неудачной проверке? Подсказка: перед `sed` сохрани старое значение `IMAGE_TAG` из `.env` в переменную.
</details>

### Уровень 5. Первый тест в CI

```text

Репозиторий
  deploy/compose.prod.yaml                 image: ghcr.io/…:${IMAGE_TAG}, без build и volumes кода, порты только 127.0.0.1
  deploy/deploy.sh                         sed IMAGE_TAG → pull → up -d → проверка → prune
  .gitattributes                           *.sh text eol=lf
  git update-index --chmod=+x deploy/deploy.sh
  ruff.toml                                [lint] select = ["E4","E7","E9","F"]
  .github/workflows/ci-cd.yml              lint → build → images (main) → deploy (main, production)

GitHub
  Secrets: SSH_HOST, SSH_USER, SSH_PRIVATE_KEY, SSH_KNOWN_HOSTS (ssh-keyscan -t ed25519 <IP>)
```
